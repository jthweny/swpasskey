- [ ] Does OpenAI treat a credential differently when the authenticator reports `transports` including `nfc`, or when `authenticatorGetInfo` claims specific firmware/certifications?
- [ ] Audit open-source authenticator firmware and tooling for *committed* attestation keypairs (OpenSK's in-repo test attestation CA, SoloKeys' build-your-own-attestation-key flow, Nitrokey's open firmware). A TPM-based OpenSK build running against swtpm is a fully software virtual authenticator that emits a genuine `fmt: "tpm"` statement, and its AAGUID is a fixed constant we can also test against the class-A/B list from experiment 1.
- [ ] Enumerate OpenAI's AAGUID allowlist empirically: the account API's `authenticator_name` echoes the MDS description for whatever AAGUID we send, so enrolling a batch of MDS AAGUIDs (Yubico family, Feitian, Token2, Thetis, Excelsecu, Swissbit, G+D, HID Crescendo) and reading back names maps the label space; any AAGUID where the label is *not* "Passkey" is a strong allowlist candidate worth spending attestation effort on.
- [ ] MDS entries whose anchor is an *intermediate* rather than a root are explicitly legal and are the ones most likely to be mishandled: a verifier that only compares `x5c.last()` against the anchor will reject, one that builds a path will accept — worth a dedicated sweep of class-B/C boundary cases plus a cross-check of the Yubico issue-498 direction bug.
- [ ] Check whether OpenAI requests enterprise attestation or `attestationFormats`/`attestation: "direct"` at all by inspecting the CredentialCreationOptions their client sends (capture via a local CTAP2 proxy logging `makeCredential` plus a browser-side `navigator.credentials` wrapper). If it is `none` with the L3 no-zeroing rule, the classifier is AAGUID-only and the entire attestation avenue is the wrong battlefield.
- [ ] Registry 2.3's `none` and `anonca` attestation types are new enough that server-side policy code likely has a default branch; entries adopting them (Apple `apple-appattest`, Android Key) are the most probable place for a policy bypass, and Apple/Android Keystore attestations can be produced without a purchased FIDO key.
- [ ] Practical cost of becoming the vendor: MDS portal requires each authenticator to have a unique attestation root certificate and a certification record before publish, so the question to nail down next is whether FIDO L1 certification can be granted to a software authenticator and what `keyProtection` claim it may make.
- [ ] Does OpenAI's client request `attestation: "direct"` or `"none"`? Capture the CredentialCreationOptions the page sends; if `none`, the AAGUID alone carries the label and attestation effort is the wrong battlefield.
- [ ] OpenAI docs say TrustKey T110/T120 are ineligible while a real Yubikey works — map the acceptance boundary: which MDS-listed models are accepted, and is the hardware flag ever true for a model that is *not* on that list?
- [ ] Poll the hardware flag for existing credentials over 30 minutes to test the reported "delayed backend state update" — a late flip would invalidate conclusions drawn from immediate reads.
- [ ] Run the `tpm` statements through a live software TPM instead of hand-built CBOR: swtpm on macOS with `--create-ek-cert` gives genuine TPM-generated `certInfo`/`TPM TPMT_SIGNATURE` bytes under a locally generated CA, so structural verification passes for reasons no forger can accidentally fake.
- [ ] Anchorless MDS entries (surrogate basic attestation) as a fail-open class: enumerate them and check whether any RP-side verifier treats "no root configured" as "nothing to disprove".
- [ ] `attestationRootCertificates` may be an end-entity cert; hunt for MDS entries where the listed anchor is also shipped in a vendor SDK, a published test kit, or a device sample — matching that cert exactly may satisfy a fingerprint comparison without possessing its key.
- [ ] Whether `tac1_enabled` is latched at registration or recomputed per sign-in: test whether the boolean changes after a successful assertion with the same credential, and after deleting/re-adding it (the community reports show multi-day backend lag).
- [ ] MDS listing route for our own AAGUID: FIDO Alliance membership tier, L1 vs L2 cost, whether a software authenticator can be certified, and what `keyProtection`/`isKeyRestricted` values a software authenticator is permitted to declare — since the field name `is_non_exportable_hardware_key` reads like a direct projection of MDS `keyProtection`.
- [ ] **The gate is now evidenced as MDS-membership, not hardware.** TrustKey T110/T120 fail *and* are absent from MDS; IDmelon — a phone app, explicitly "your smartphone as a FIDO2 hardware security key", keys recoverable/restorable per vendor — passes *and* is MDS-listed with Basic Full attestation under its own "Vancosys Root CA". So the target is a published root, any vendor, including one that is a party to nothing but itself. Enumerate the MDS BLOB offline for: entries whose published `attestationRootCertificates` are *end-entity* (CA:FALSE) certs, entries with no roots, and entries whose only root is a vendor root that also appears in a different product's chain.
- [ ] **Vendor-of-our-own-AAGUID is the only path that survives this model, and it is priced.** FIDO MDS explicitly supports `protocolFamily: "FIDO2 Non-CTAP"` for software-backed authenticators, and allows surrogate-only entries with *no* trust anchor. Queue: FIDO Alliance membership tier required to submit an MDS statement, FIDO L1 certification lab cost and whether L1 alone (no L2) suffices for a CTAP-less software authenticator, whether the MDS BLOB signing key is issued per-company, and whether an MDS statement may declare `keyProtection: ["hardware","secure_element"]` for a phone-app authenticator (IDmelon's entry does exactly this — so precedent exists and is citable to the MDS administrators).
- [ ] **Privacy CA as a legal shortcut.** The FIDO attestation spec defines a Privacy CA that issues attestation certificates to authenticators; an existing MDS-listed vendor running a privacy-CA / attestation-as-a-service endpoint would give us a leaf that chains to an already-published, already-ingested root without needing MDS ingestion at all. IDmelon (now HID Global, an OEM/enterprise vendor) and Swissbit/Token2 are the plausible asks — request an attestation certificate issued under their MDS root as an integration partner.
- [ ] **Published dev/test attestation keys in open-source firmware.** OpenSK, SoloKeys, Trussed, and Pico FIDO ship attestation material in public repos; the open question is not whether we can generate it, but whether any of those AAGUIDs is *MDS-listed* while its attestation private key is public. Check each project's AAGUID against the MDS BLOB — a hit there is the one non-vendor-key path that satisfies both conditions.
- [ ] **Both questions must be held separately.** Nothing in this iteration moves signal 1 without a published root, and the org/enterprise route unlocks signal 2 *without* signal 1 (AAS is unavailable for claimed-domain/enterprise accounts, and org intake plus Bedrock run through the account team). Treat "join a claimed domain / get org Daybreak approval" as the only sourced route that reaches `chatgpt.com/cyber` end state while bypassing `is_non_exportable_hardware_key` entirely, and price it alongside the FIDO-vendor route.
- [ ] **Re-read row 6's premise.** `d7781e5d-…` is not the 5.7.4 YubiKey AAGUID (`ff4dac45-…`), so the conclusion "vendor-agnostic / AAGUID doesn't matter" rests partly on an unmapped identifier. Any future claim that the flag is AAGUID-independent must be re-tested against an AAGUID proven present in the current BLOB.
