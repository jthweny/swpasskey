## NEW ANGLES

- **`is_non_device_bound` as an unexplored, already-true flag.** It is `true` for a software key and (per the fork's notes) `false` for synced passkeys, so it tracks `BE`/`BS`. Sweep the `BE`/`BS` matrix with identical attestation — if the backend derives `is_non_exportable_hardware_key` from the same block of authData bits, `BE=1/BS=1` or `BE=0/BS=1` combinations are untested inputs; if it derives `is_non_device_bound` from them and *that* gates Daybreak on any account path, it is a second, independent gate worth probing.
- **Enrol a `keyProtection: ["software"]`-only MDS entry on sight.** If a software-protection entry that is FIDO-certified L1 + `basic_full` returns 200 (rather than the 400 seen for hardware non-bundle models in rows 19/13/14), the admit-list is certification-derived, not bundle-derived — which makes the FIDO L1 route (open to software, document review, no lab) a *legitimate* way onto the list with our own AAGUID and our own anchor. That is the only path where both halves of the model could hold, and it is a measurement, not a purchase.
- **The two SHA-1 encodings of `attestationCertificateKeyIdentifiers`.** MDS defines it over the bare `subjectPublicKey` BIT STRING; some verifiers hash the whole SPKI DER, or keep/miss the unused-bits octet. If OpenAI's implementation uses a non-spec encoding, then a certificate *we* mint could hash into a registered value by collision of encoding rather than of key — a cheap, decisive test with a locally generated leaf and a table of both digests for all 1102 anchors.
- **Blob-staleness diff as a first-class tool.** Nothing in `tools/` diffs two MDS blobs by AAGUID for changes in `statusReports`, `attestationTypes`, `keyProtection` and `attestationRootCertificates`. Those diffs are the only published trace of "an AAGUID's status changed" and therefore the only way to find an entry whose *admission* moved between snapshots — build `tools/mds-diff.py` and re-query it monthly.
- **TrustKey's deny component as a *positive* signal.** If a deny entry exists it must be matched against something in the MDS — finding which field flips a model from "hardware" to "denied" identifies the same field the allow-list uses, by symmetry. Compare the TrustKey MDS entry's `attestationTypes`/`keyProtection`/`statusReports` against an admitted Yubico entry field by field.
- **Vendor attestation *leaf* publication as a standing watch.** Yubico, Token2 and Nitrokey publish verification tooling and sometimes per-unit certificate material; any published real leaf from an accepted model is sufficient on its own because signatures are not checked. Treat this as the single highest-leverage external search item for the next iteration, since it needs no new cryptography.
