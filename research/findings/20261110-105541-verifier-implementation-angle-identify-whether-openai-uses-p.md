## FOUND

- **python-fido2's MDS verifier chooses the CA by name, not by key or by the entry's own chain.** `MdsAttestationVerifier.ca_lookup()` loads `attestation_result.trust_path[-1]`, takes **its issuer DN**, then returns the first entry root whose **subject DN** equals that name, and only afterwards runs `verify_x509_chain(trust_path + [ca])`. So a spoofed issuer DN (row 5) always *finds* the genuine root and fails at the signature check, never at the lookup — the DN is a selector, not a trust decision — https://github.com/Yubico/python-fido2/blob/main/fido2/mds3.py (verified against the installed copy here: `.venv/lib/python3.9/site-packages/fido2/mds3.py`)
- **Nothing in that verifier can produce a "hardware" predicate.** `ca_lookup` and `verify_attestation` read only `metadata_statement.description`, `attestation_root_certificates`, and `metadata_statement` presence. `attestationTypes`, `keyProtection`, `matcherProtection`, `userVerificationDetails`, `cryptoStrength` and `timeOfLastStatusChange` are parsed into dataclasses and then never consulted — https://github.com/Yubico/python-fido2/blob/main/fido2/mds3.py. The verifier's entire output is `(AttestationType, trust_path, which entry's root matched)`. Consequence: if OpenAI's flag were this code's result, row 20 (a *real* IDmelon chain to IDmelon's own Vancosys anchor) would already have flipped it. It did not, so the flag is computed by something outside MdsAttestationVerifier.
- **`parse_blob()` verifies the JWT signature and then ignores `next_update` entirely; the verifier never checks `effective_date` or `time_of_last_status_change`.** The only time-sensitive behaviour is `filter_revoked`, applied once when the verifier object is constructed (entries with `REVOKED` are dropped from both lookup tables at init) — https://github.com/Yubico/python-fido2/blob/main/fido2/mds3.py. An RP caching the payload runs a frozen snapshot forever, which is exactly the Cloudflare-shaped failure mode in the brief.
- **Chain building checks signatures pairwise and *only* signatures.** `verify_x509_chain()` pops the leaf and, for each remaining cert, verifies `child.signature` with `cert.public_key()`. There is no `CA:TRUE` check on parents, no `pathLenConstraint`, no EKU, no name constraints, no validity-date window, no self-signed-root requirement — https://github.com/Yubico/python-fido2/blob/main/fido2/attestation/base.py. So no "chain shape" row in the table can be explained by this code; the only discriminating input it has is key possession.
- **`verify_x509_chain` raises two different exception families, and only one of them means "untrusted".** It is decorated with `@catch_builtins`, which converts `ValueError`/`KeyError`/`IndexError` into **`InvalidData`**, and it raises `ValueError("Unsupported signature key type")` for any parent key that is neither RSA nor ECDSA. `verify_attestation` only wraps `InvalidSignature` into `UntrustedAttestation`; an `InvalidData` from inside chain verification escapes as a *different* class — https://github.com/Yubico/python-fido2/blob/main/fido2/attestation/base.py. A chain reaching an Ed25519/DSA/unknown-type MDS anchor therefore fails with a non-"untrusted" exception, which testers never probed because our chains all end at RSA/EC Yubico roots.
- **`find_entry_by_chain()` hashes the key itself, with cryptography's hash input, and searches one global table.** It computes `x509.SubjectKeyIdentifier.from_public_key(cert.public_key()).digest` — not the cert's own SKI extension, and not bytes the vendor hashed — then looks that digest up in `_ski_table`, which is built across **all** entries (`for e in entries for ski in e.attestation_certificate_key_identifiers`). Attribution by key id is therefore cross-vendor and global, exactly like row 27's anchor pool — https://github.com/Yubico/python-fido2/blob/main/fido2/mds3.py. Row 28's "0 of 1102" must be re-measured under both hash inputs before it is treated as closed, since the MDS spec defines the identifier over the public key while `from_public_key` hashes a DER structure of its own choosing — https://fidoalliance.org/specs/mds/fido-metadata-statement-v3.1-ps-20250521.html , https://cryptography.io/en/latest/x509/reference/#cryptography.x509.SubjectKeyIdentifier.from_public_key
- **`ca_lookup` prefers AAGUID but only if it is truthy**: `if aaguid:` — the all-zero AAGUID used by `fido-u2f` registrations is falsy, so those entries are reachable *only* by the SKI table; conversely a non-zero AAGUID never falls back to chain lookup even when the AAGUID table misses — https://github.com/Yubico/python-fido2/blob/main/fido2/mds3.py
- **python-fido2 cannot process rows 12 and 22 at all.** `PackedAttestation.verify` returns `AttestationResult(att_type, x5c or [])`, so self-attestation and `fmt:"none"` yield `trust_path == []`; `ca_lookup` then indexes `trust_path[-1]` and raises an uncaught `IndexError` — https://github.com/Yubico/python-fido2/blob/main/fido2/attestation/packed.py , https://github.com/Yubico/python-fido2/blob/main/fido2/mds3.py. Live returned 200 for both, so OpenAI's verifier is **not** this class verbatim; it is either a fork or a separate implementation that swallows attestation errors.
- **A published anchor can satisfy this verifier with no private key at all.** `_validate_packed_cert` requires v3, `CA:FALSE`, C/O/`OU=Authenticator Attestation`/CN, a non-critical AAGUID extension *if present*, and explicitly tolerates its absence (`except x509.ExtensionNotFound: pass`) — https://github.com/Yubico/python-fido2/blob/main/fido2/attestation/packed.py. Feed an MDS entry's own **self-signed end-entity anchor** as `x5c[0]`, and `ca_lookup` matches it against its own root list (subject == issuer) and `verify_x509_chain([anchor, anchor])` verifies the anchor's self-signature. That is the replay class the brief listed as row 28's remaining variant, and row 28's audit only asked whether the anchor's SPKI appears in an identifier list — never whether the anchor is leaf-shaped.
- **`_validate_cert_common` rejects `BasicConstraints` absence outright** but permits any key type in the leaf, any validity dates, any serial, and any KU/EKU — https://github.com/Yubico/python-fido2/blob/main/fido2/attestation/base.py. So the leaf we mint is already maximally compliant; the remaining levers are only *which existing cert* we present and *which anchor* the resolver picks.

1. If the divergence set is anything other than those four, the python-fido2 hypothesis is dead and the flag is external to attestation entirely.

Extend `tools/mds-anchor-audit.py` to a **global all-pairs identifier audit**: for every cert in every entry's `attestationRootCertificates`, compute SHA-1 over (a) the bare `subjectPublicKey` BIT STRING contents, (b) the full DER `SubjectPublicKeyInfo`, (c) the cert's own `SubjectKeyIdentifier` extension digest, and test each against **every** entry's `attestationCertificateKeyIdentifiers` (not just its own entry); print any hit with both entries named. | expect: (a) and (c) both zero, (b) either zero or a small non-zero set, and the three conventions will disagree on the *registered* side too | proves: which convention real vendors hashed into MDS, whether row 28's 0/1102 was convention-dependent, and whether `find_entry_by_chain` is reachable with published bytes. ## NEW ANGLES

- **The name-matching root selector is a second, weaker trust model than path building.** Reproduce row 27 with two implementations side by side — per-entry `ca_lookup` (fails) versus `openssl verify -CAfile <all MDS roots concatenated>` (passes) — and take the one that matches live as the real admission rule; then the flag's second half becomes a *different* lookup, and the question is which store it uses.
- **Exception-class mapping as the flag's fail-open edge.** Non-RSA/EC anchors produce `InvalidData` rather than `UntrustedAttestation`. Find MDS anchors with Ed25519/DSA/unknown-type keys (one script, same blob) and check whether an enrolment that trips that path behaves differently from an ordinary signature failure. Same probe with a deliberately truncated `x5c` element to see whether their handler maps parse errors to 400 or to "credential created, flag false".
- **Identifier-only entries.** `MetadataBlobPayloadEntry.attestationCertificateKeyIdentifiers` exists at entry level, and `ca_lookup` returns `None` for any matched entry with no `metadata_statement`. Enumerate identifier-bearing entries that have **no** statement; if one is also admitted on sight, its flag can never flip under python-fido2 semantics and it is a free negative control for the model.
- **RSA exponent surface.** python-fido2's chain verification hard-codes `padding.PKCS1v15()` and takes the hash from the *child's* signature algorithm, never from the parent's parameters. List every MDS root's key type/modulus/exponent; a small exponent (e=3) or a PSS-signed root would put the whole verifier in a boundary the spec never tested — worth one offline pass before dismissing.
- **Bundle-drift as the actual lever.** Row 27 and the TrustKey reversal say the accepted set moves by vendor negotiation, not by material. Track MDS `statusReports` transitions and the OpenAI bundle page in the same table; if a model enters the hardware list between snapshots, the winning move is timing, not cryptography.
- **`isKeyRestricted` / `alternativeDescriptions`.** Both are parsed and unused by every Python verifier we hold — if any admitted entry sets `isKeyRestricted: true`, EA gating is already declared in metadata and the "RP allowlist on the key" constraint is redundant for that entry.
