## FOUND
- OpenAI publishes a **model-level** ineligibility list, not a capability test: "TrustKey T110 and T120 security keys are currently ineligible for individual Daybreak access" — https://help.openai.com/en/articles/20001259-troubleshooting-openai-daybreak
- Genuine physical FIDO2 keys that are not on that list enrol successfully (PIN + physical touch, `plat:false`, `packed`, CTAP2.1) yet are stored as **"Passkey"** and never qualify; the eligibility page stays at "To continue, add a hardware key" and Continue stays disabled — https://community.openai.com/t/daybreak-does-not-recognize-trustkey-t110-physical-fido2-keys-as-hardware-security-keys/1401917
- Same outcome for a Thetis hardware key alongside one Windows Hello passkey: `passkeys: {qualifying_count: 0, non_qualifying_count: 2}`; the user describes the Thetis as FIDO2-compatible and cannot reach 1 qualifying — https://community.openai.com/t/trusted-access-for-cyber-disappeared-from-my-account/1391143?page=3
- The gate is observable per-credential and per-account without the browser: `POST /backend-api/cyber_verification/refresh_status` (and `/backend-api/cyber_verification/status`) returns `aas.status`, `passkeys.qualifying_count`, `passkeys.non_qualifying_count`, `individual_eligibility_status` — https://community.openai.com/t/trusted-access-for-cyber-disappeared-from-my-account/1391143?page=3
- `qualifying_count: 2` occurs for real accounts, so the hardware classification **does** reach true in production — it is not a permanently-false field — https://community.openai.com/t/daybreak-blue-backend-says-eligible-but-verification-is-blocked-with-no-persona-inquiry/1401191
- The flag is not sufficient by itself: the same account showed `qualifying_count: 2`, `aas.status: true`, `individual_eligibility_status: "eligible"` while `verification_status: "blocked"` — so signal 1 and Daybreak are separable, as the brief suspected — https://community.openai.com/t/daybreak-blue-backend-says-eligible-but-verification-is-blocked-with-no-persona-inquiry/1401191
- For accepted AAGUID `f4ce5fc0`, MDS `attestationRootCertificates` contains **two CA certs**: `CN=Yubico FIDO Attestation A 1` (issued by `Yubico Attestation Intermediate A 1`) and self-signed `Yubico Attestation Root 1`, both `CA:TRUE`; statement is `basic_full`, keyProtection `hardware, secure_element`, `FIDO_CERTIFIED_L2` — https://www.token2.com/tools/fido2-mds/f4ce5fc057d346f5a736efb7d5bc63b5
- For accepted AAGUID `a25342c0` the anchor is the **older** self-signed `CN=Yubico U2F Root CA Serial 457200631` (serial `1B4053F7`), i.e. the anchor pool is per-AAGUID, not a single Yubico root — https://www.token2.com/tools/fido2-mds/a25342c03cdc44148e46f4807fca511c
- A genuine `f4ce5fc0` credential's `x5c` is therefore leaf + intermediate (`Yubico FIDO Attestation A 1`), a **2-cert chain, not a self-signed/3-deep one** — which is exactly the shape row 9 did not test — https://www.token2.com/tools/fido2-mds/f4ce5fc057d346f5a736efb7d5bc63b5
- Yubico states the FIDO attestation leaf is **per production batch, not per device**: "all YubiKey 5 series devices created within the same production batch possess the same attestation certificate" — https://developers.yubico.com/Developer_Program/WebAuthn_Starter_Kit/Attestation.html
- Batch sharing is large-scale: "shared between all YubiKeys in batches of at least 100,000 units" — https://www.reddit.com/r/yubikey/comments/1bb29dz/yubikey_and_website_tracking
- Firmware 5.7.4+ YubiKeys switched to the new root (`Yubico Attestation Root 1`); pre-5.7.4 devices chain to `Yubico U2F Root CA Serial 457200631` / `Yubico FIDO Root CA Serial 450203556` — https://developers.yubico.com/U2F/Attestation_and_Metadata
- The hardware spend is standard consumer-grade: YubiKey 5C NFC = FIDO2 L2, fw 5.8, secure element, serialized — https://www.yubico.com/product/yubikey-5c-nfc
- A *sourced* exception to "you need the vendor's attestation key" exists for exactly the AAGUID family OpenAI refuses: EUCLEAK extracts ECDSA secret keys from the Infineon secure element on YubiKey 5 Series **< firmware 5.7**, and the paper states that "in the case of the FIDO protocol, this allows to create a clone of the FIDO device" — https://eprint.iacr.org/2024/1380 ; CVE-2024-45678 — https://nvd.nist.gov/vuln/detail/cve-2024-45678
- Relying-party chain handling genuinely differs in the wild (real bug: x5c that "must contain the end-entity certificate at position 0 and MAY have additional chain certificates", YubiKey Bio case) — https://github.com/OpenConext/Stepup-Webauthn/issues/225
- The `is_non_exportable_hardware_key` field name appears **nowhere** in public docs, spec text, or code; there is no published definition of its predicate — https://www.google.com/search?q=%22non_exportable_hardware_key%22 (no spec/doc hits; only unrelated phrasing)

## EXPERIMENTS
1. Capture a real `attestationObject` from any YubiKey 5C NFC on fw ≥ 5.7.4 (ask an owner to run `python-fido2` `make_credential` with `attestation="direct"` on any origin and paste the base64 — the leaf is batch material, contains no secret), then enrol locally with `x5c` = that genuine [leaf, `Yubico FIDO Attestation A 1`], `aaguid = f4ce5fc0`, our own software credential keypair, and `attStmt.sig` left as arbitrary bytes | expect: 200 on enrolment **and** `is_non_exportable_hardware_key: true` (because row 3 proved sig is not verified) | proves: the flag is MDS-anchored-chain-based, and it is defeated by replaying public batch cert material with a software private key — full break of signal 1
2. Same as (1) but with `x5c` = [leaf, intermediate, root] (3-deep) and then a third run with `x5c` = [leaf] only (intermediate omitted) | expect: 200/false for the truncated chain, and 200/true-or-false for the 3-deep — whichever differs identifies whether their verifier uses the supplied partial chain or its own MDS anchor pool | proves: whether a partial chain suffices (fewer public artifacts needed) and localises the X.509 path-building step
3. Same as (1) but cross-pair the anchors: genuine old-root leaf (pre-5.7.4 device, chains to `Yubico U2F Root CA Serial 457200631`) submitted under `aaguid = f4ce5fc0` (whose MDS anchor is the *new* root), and genuine new-root leaf under `aaguid = a25342c0` | expect: 200/false on both if anchors are per-AAGUID; 200/true if the verifier accepts any known Yubico root regardless of AAGUID | proves: per-AAGUID anchor binding vs a single global vendor-root pool — this decides whether *any* vendor's public batch leaf is usable
4. Re-submit the genuine-`f4ce5fc0`-leaf case with `sig` of length 0 and with `alg` set to a wrong COSE value (e.g. `-7` → `-8`), keeping the genuine `x5c` | expect: still 200/true if the classification path ignores `attStmt` entirely; 400/`passkey_verification_failed` or 200/false if `attStmt` shape is validated at classification time | proves: exactly which bytes of `attStmt` the classifier reads, and whether a zero-length signature is an even cheaper bypass
5. Probe the accepted-set boundary with the two brands users report *both* working and failing: query CTAP2 for a Thetis key's AAGUID (and TrustKey `e3512a8a-62ae-11ea-bc55-0242ac130003`), then enrol each AAGUID with our own self-signed leaf | expect: 400 for both (model gate) — if either returns 200, the "short allowlist of current models" conclusion is wrong and the gate is broader | proves: whether the accepted set is a formal allowlist or "any model with a chain that validates"; also resolves the contradictory Thetis reports in https://www.reddit.com/r/bugbounty/comments/1wbzbiv/daybreak_verification_failed_are_my_passkeys_the
6. For any enrolment in (1)–(4), snapshot all four signals at t+0, t+2 m, t+10 m, t+30 m: `GET /api/accounts/advanced-account-security/passkeys` (`is_non_exportable_hardware_key`), `POST /backend-api/cyber_verification/status` and `/refresh_status` (`passkeys.qualifying_count`, `tac1_enabled`), then the `chatgpt.com/cyber` page | expect: classification is monotone-settling (false→true within 30 m) or stable-false; `qualifying_count` and `is_non_exportable_hardware_key` should agree | proves: whether the flag is written by an async job (supports "delayed backend state") and whether the two signals share one predicate — required before recording any failure
7. Create one credential with `BE=0, BS=0` and one with `BE=1, BS=1` (flags `0x41` vs `0x59`, same accepted AAGUID, `fmt:"none"`) and diff the classification | expect: both false (BE hint is not the predicate) | proves: the flag is not derived from the WebAuthn backup-eligibility bits, closing the cheapest non-attestation hypothesis

## NEW ANGLES
- **Batch-leaf replay as the primary path.** Because leaves are batch-scoped (≥100k devices share one cert) and `attStmt.sig` is unchecked, the missing input is one *public certificate*, not a private key. Source candidates: GitHub issues/StackOverflow pastes of `attestationObject`, passkey-debugger exports, `python-fido2`/`py_webauthn` issue threads, and any YubiKey owner. Collect 3–5 independent `f4ce5fc0` leaves and treat them as a corpus.
- **The anchor shape for `f4ce5fc0` is an intermediate CA, not a root.** Rows 2/4/9 all failed to present `[leaf → Yubico FIDO Attestation A 1]` with a leaf that actually verifies to it; every prior attempt either self-signed the leaf or appended roots without a valid signature edge. Retest the *edge*, not the names.
- **EUCLEAK as the sourced vendor-key exception — but check the AAGUID overlap.** Extraction is documented only for fw < 5.7 (`2fc0579f`, `a25342c0` era), which are exactly the AAGUIDs already refused (rows 17–18). Look for any *accepted* AAGUID that shares silicon/cryptolib with an extractable model, and for reports of cloned 5.7+ devices.
- **Per-AAGUID vs global anchor pool** (experiment 3) is the highest-leverage unknown: if the verifier accepts any known FIDO vendor root, the accepted-model wall collapses into "find any vendor leaf", including vendors that publish device attestation certs.
- **`qualifying_count` is an oracle the project is not using.** It reports counts directly, before any UI or Daybreak step, and appears in a public thread. Instrument every enrolment with it instead of relying on the passkeys array alone.
- **Enterprise attestation path.** Yubico implements FIDO2 enterprise attestation (vendor `authenticatorConfig`), which changes what the RP receives and sets the EA flag in `authData`; worth checking whether the classifier keys on standard vs enterprise statements, and whether EA changes the leaf it presents — https://developers.yubico.com/WebAuthn/Concepts/Enterprise_Attestation/Getting_Started.html
- **Model-gate enumeration via MDS mirror.** The Token2 MDS explorer exposes per-AAGUID `attestationTypes`, `keyProtection`, and anchor shapes, so the accepted set can be brute-forced cheaply by enrolling MDS entries and recording 200 vs 400 — the 400/200 matrix is the actual allowlist, and it is inferable rather than published.
- **Open question not covered by any source found:** whether `tac1_enabled` depends on anything besides `qualifying_count ≥ 1` — the one public counter-example has qualifying keys and is still blocked, which points at identity-verification state as the second gate.
