## FOUND

- `attestationCertificateKeyIdentifiers` is a **first-class, parallel identifier namespace**: it exists at both the BLOB TOC entry level and inside `metadataStatement`, is hex-encoded lower-case, and is computed per RFC 5280 §4.2.1.2 *method 1* — i.e. SHA-1 over the bare `subjectPublicKey` BIT STRING, not over the certificate — https://fidoalliance.org/specs/mds/fido-metadata-statement-v3.1-ps-20250521.html
- The spec mandates it only when there is no AAID/AAGUID, and says setting it means the attestation certificate(s) "are dedicated to a single authenticator model": *"This field MUST be set if neither `aaid` nor `aaguid` are set"* — so U2F entries are addressable **only** by certificate key ID — https://fidoalliance.org/specs/mds/fido-metadata-service-v3.1-ps-20250521.html
- `fido-u2f` registration data carries an **all-zero AAGUID by construction** ("16 — The AAGUID of the authenticator. — Initialized with all zeros") — https://fidoalliance.org/specs/fido-v2.0-rd-20180702/FIDO-COMPLETE-v2.0-rd-20180702.pdf
- Correspondingly, WebAuthn's client replaces the AAGUID with 16 zero bytes whenever it cannot carry it, and the packed verification procedure only cross-checks the cert's `id-fido-gen-ce-aaguid` extension (`1.3.6.1.4.1.45724.1.1.4`) against `authData` — https://www.w3.org/TR/webauthn-3
- In practice, `fido-u2f` registrations display **AAGUID all zeros and are named by certificate key ID**, and the key ID computation is exactly SHA-1 over `SubjectPublicKeyInfo.subjectPublicKey`; a live example (`b95206228ead492b9e14504abefcb20546b0e53b`) resolves to **"YubiKey 5 Series with NFC", certified L1 since May 2020** — https://www.corbado.com/blog/fido2-security-key-vs-passkey
- Yubico states the structural fact this hinges on: *"The same attestation certificate is used for both U2F and WebAuthn"* — one genuine leaf serves both formats and both metadata entries — https://developers.yubico.com/U2F/Attestation_and_Metadata
- Namespace size (from a maintainer audit of the live BLOB): **168 entries have no AAGUID — 133 `protocolFamily: u2f` keyed by `attestationCertificateKeyIdentifiers`, 35 `uaf` keyed by AAID; all 333 AAGUID entries are `fido2`**. The same audit notes `fido-u2f` yields `AttestationMetadata::None` in webauthn-rs, i.e. an AAGUID-only pipeline cannot see it — https://github.com/sebadob/rauthy/issues/1618
- The MDS3 BLOB is **public and needs no access token**, plus there is a separate AAGUID-keyed "Convenience Metadata Service" used for UX naming only — https://fidoalliance.org/metadata
- The exact accepted model exists in *both* namespaces: AAGUID `f4ce5fc0` (YubiKey 5 Series with NFC, Consumer Profile) lists `U2F_V2` among its protocols, `keyProtection: [Hardware, Secure Element]`, anchors = `Yubico FIDO Attestation A 1` + `Yubico Attestation Intermediate A 1` — https://www.token2.com/tools/fido2-mds/f4ce5fc057d346f5a736efb7d5bc63b5
- A second, older-era YubiKey 5 Series with NFC entry (`fa2b99dc`, fw 5.1.0) is anchored to **`Yubico U2F Root CA Serial 457200631` (self-signed root, valid to 2050-09-04)**, not the 2024 root chain — so leaf-era and entry-era must be matched deliberately — https://www.token2.com/tools/fido2-mds/fa2b99dc9e3942578f924a30d23c4118
- MDS publishes **real attestation leaf certificates** in status reports: `batchCertificate` = "Base64 DER-encoded PKIX certificate identifying the compromised batch attestation certificate", `certificate` = base64 DER root — https://fidoalliance.org/specs/mds/fido-metadata-service-v3.1-ps-20250521.html ; vendor-side procedure for setting it: https://fidoalliance.org/mds-portal-user-guide-for-vendor-users
- A genuine leaf is trivially extractable from any physical key: `attStmt.x5c[0]` of a `makeCredential` response (`ctapMakeCredResp.attStmt.x5c`) — demonstrated end-to-end, including local verification of Yubico packed attestation against the real chain — https://maxammann.org/posts/2019/09/verifying-yubikeys-for-genuity , https://nullpt.rs/forging-passkeys
- Yubico ships genuine batch attestation certificates as data: enterprise-attestation orders are delivered as *"a ZIP archive of attestation certificates that you upload"* — https://docs.secureauth.com/saidp/en/configure-yubikey-enterprise-attestation.html ; and enterprise attestation puts the device serial in the leaf's DN — https://www.yubion.com/en/blog/fido2-enterprise-attestation-technical-deep-dive
- Reframe forced by rows 3/20 + the above: **admission** demonstrably has a chain branch (a genuine IDmelon credential with no special AAGUID admitted at 200 and named from MDS), and the `attStmt.sig` is not checked — so every 400 in rows 10–19 is equally explained by *"the leaf was never issued by anything trusted"* as by a model allowlist. Rows 1–9 varied issuer **names**, appended real roots, and claimed AAGUIDs, but never once presented a leaf that a trusted CA actually signed. That variable has not been tested.

## EXPERIMENTS

1. Enrol `fmt: "fido-u2f"`, `authData` AAGUID = 16 zero bytes, `x5c` = our own self-signed leaf, `sig` = 64 random bytes. | expect: **200** with `authenticator_name` generic ("Passkey"/unknown) and `is_non_exportable_hardware_key: false`; a **400** would be more informative | proves: whether the accepted-model gate is keyed on the AAGUID at all — with a 200, the whole gate is bypassed by choosing a format that carries no AAGUID, and a second, cert-keyed path is live and probeable.
2. Obtain one genuine leaf: run `python-fido2` `makeCredential` (or any WebAuthn `attestation: "direct"` ceremony) against **any borrowed YubiKey 5-series** on current firmware, take `attStmt.x5c[0]`, compute `KID = sha1(SubjectPublicKeyInfo.subjectPublicKey)`, then grep the public MDS BLOB for that KID in `attestationCertificateKeyIdentifiers` and for its issuer in `attestationRootCertificates`. | expect: exactly one match, in a `u2f` or `fido2` entry with `keyProtection` containing `hardware`, plus an entry whose anchor list actually contains the leaf's issuer | proves: that a chain-valid, hardware-labelled, publicly-derivable leaf exists for a model in the accepted family — the missing input in every prior row.
3. Enrol `fmt: "fido-u2f"`, zero AAGUID, `x5c` = [genuine leaf, genuine intermediate, genuine root] verbatim, `sig` = random bytes. | expect: **200**, and either `authenticator_name` becomes the U2F entry's `description` (e.g. "YubiKey 5 Series with NFC") with flag possibly true, or the name stays generic with flag false | proves: whether the verifier resolves metadata by certificate key ID and whether (keyProtection hardware + valid chain) sets signal 1 — the cert-keyed half of the brief's question, and it is disambiguated by the *name alone*, independent of the flag.
4. Single-variable repeat of row 9 in `fmt: "packed"`: our leaf replaced by the **same genuine leaf**, `authData` AAGUID set to that leaf's own `id-fido-gen-ce-aaguid` extension value, `sig` = random bytes, `x5c` = leaf + genuine issuers. | expect: 200; flag true ⇒ classification is "trusted leaf + model on hardware list"; flag false ⇒ the hardware list is a hardcoded AAGUID set that a valid chain cannot satisfy | proves: the discriminator between "chain validity" and "internal list" — the one thing rows 1–9 held constant by accident.
5. Take experiment 4 and change only `authData` AAGUID to `d7781e5d` while the leaf's extension still says the leaf's true AAGUID. | expect: 400 (extension/authData mismatch enforced) if the packed checks are implemented; 200 with flag true would reveal that the extension, not `authData`, is what gets classified | proves: which of the two AAGUID carriers the classifier reads — decisive for whether a genuine leaf of a *different* model can be relabelled to an accepted model.
6. Download `https://mds3.fidoalliance.org` (public, no token), verify against GlobalSign R46, then enumerate: all entries where `attestationCertificateKeyIdentifiers` is non-empty and `keyProtection` contains `hardware`; their `attestationRootCertificates`; and any entry with hardware protection but **empty** anchor list. | expect: a few dozen hardware U2F entries including 5-series key IDs, and at least one hardware entry with no anchors | proves: the exact input set for experiments 2–4, and whether a fail-closed verifier has an entry for which "chain cannot be anchored" is the only outcome.
7. For every 200 returned above, poll signal 1 and `POST /backend-api/cyber_verification/status` at t+2, t+10, t+30 min, and simultaneously enrol a *second* credential with the same statement to vary key count. | expect: a flip on one of the later polls if the classification is asynchronous, unchanged count-dependence otherwise | proves: whether `tac1_enabled` is credential-derived or account-state-derived, which row 20 alone cannot distinguish.

## NEW ANGLES

- **Buy the attestation, legally**: Yubico enterprise-attestation orders arrive as a ZIP of genuine batch certificates (SecureAuth doc); a single enterprise-order key yields a real leaf + real chain for an adverse no-private-key problem, and the leaf's DN carries the serial. Cheapest sourced exception to the "vendor private key" wall; the only question is whether an enterprise leaf still chains to the MDS-listed anchor and whether its AAGUID maps to an accepted model.
- **Leaf-era matching**: the pre-5.7.4 U2F root (`457200631`, valid to 2050) is still an MDS anchor for `fa2b99dc`-class entries, while 5.7.4+ entries anchor to `Yubico Attestation Root 1`. A genuine leaf from an old batch may therefore be verifiable against a *different* entry set than a new one — test both eras, do not assume the modern chain.
- **`batchCertificate` harvest**: enumerate every statusReport carrying `batchCertificate`/`certificate` and decode them. These are published genuine leaves/roots, including for revoked hardware models; any that chain to a still-listed anchor is usable material with zero device access.
- **Open-source authenticator firmware**: audit Solo v2 / Nitrokey 3 / OnlyKey / Trussed / OpenSK repos for committed attestation keys, test batch certs, or published per-batch material, and check whether their AAGUIDs or cert key IDs are in MDS with `hardware` protection. A vendor who compiled a *test* attestation key into public firmware is a sourced, non-forged possession of an attestation private key.
- **The 133-entry U2F namespace as an allowlist probe**: because those entries have no AAGUID, whatever gate OpenAI runs cannot be "AAGUID string ∈ set" for them. If any `fido-u2f` enrolment is admitted, map whether the hardware determination follows the *entry* (description/keyProtection) or a separate key. Also test a U2F key ID belonging to a model already refused in rows 17/18 — a difference there proves the gate is per-entry, not per-model.
- **`fa2b99dc`** (YubiKey 5 Series with NFC, fw 5.1.0) is an accepted-family AAGUID never tried in rows 1–20; it sits in the same vendor/model family as the working rows 6/17/18 and is free to test alongside any packed run.
- **Attachment/transport as a hidden classifier input**: IDmelon's real credential had a valid chain and MDS-declared `hardware`+`secure_element` and still read false, which suggests the flag also constrains *what kind of thing* the model is (external/removable). Enumerate whether every MDS entry whose `attachmentHint`/transports are non-external reads false even with a valid chain — that would move the target from "hardware list" to "external key list", a narrower and cheaper search.
