## FOUND

- MDS metadata statements explicitly permit a trust anchor to be "a root certificate, an intermediate CA certificate **or even the attestation certificate itself**" — https://fidoalliance.org/specs/mds/fido-metadata-statement-v3.1-ps-20250521.html (quoted verbatim at `tools/mds-anchor-audit.py:9-11`, so the self-signed end-entity anchor class is spec-sanctioned, not vendor error).
- `attestationCertificateKeyIdentifiers` is hex SHA-1 over the bare `subjectPublicKey` BIT STRING, and exists as a *parallel* attribution namespace because `fido-u2f` registrations carry an all-zero AAGUID — https://fidoalliance.org/specs/mds/fido-metadata-statement-v3.1-ps-20250521.html
- The MDS BLOB is a JWT (`no`, `entries[]`) served from https://mds3.fidoalliance.org/ ; our own loader already decodes it (`tools/mds-anchor-audit.py:load_blob`), so identifier-list enumeration needs no new tooling.
- Our existing audit tool compares MDS-published certs only: it classifies each entry as `EE-ANCHOR` / `NO-ANCHOR` and dumps DER, but never intersects against public cert/key material — `tools/mds-anchor-audit.py:60-94`. Row 28 tested MDS-published certs against identifier lists; **published-repo certs were never tested against identifier lists.** That intersection is the untested measurement this angle actually needs.
- Anchor matching is global across entries (row 27: Securitag AAGUID + Yubico-signed tail → 200, named "Securitag Assembly Group FIDO Authenticator NFC"), so if identifier matching is likewise global, a registered key from *any* entry — not the claimed AAGUID's own — is a candidate. https://github.com/madeye/swpasskey (row 27 in `docs/COMPAT.md` evidence table)
- FIDO conformance tooling ships an EA batch certificate **and its private key**, but its root is absent from the MDS — https://github.com/fido-alliance/conformance-test-tools-resources/blob/main/docs/FIDO2/Authenticator/README.md
- `fmt: "android-key"` has never been submitted: measured formats are `packed` (accepted), `tpm` (400, both encodings), `apple` (400), `none` (200, flag false) — rows 1-29, `docs/COMPAT.md`. `fido-u2f` is likewise unsubmitted.
- [tooling] This iteration's web search and fetch backends returned plan-quota errors on every call, so the repo-published-key inventory below is specified as executable experiments rather than fetched this round; nothing in FOUND claims a key that was not read from a primary source.

## EXPERIMENTS

1. **Identifier ↔ published-key intersection (the untested row).** `curl -s https://mds3.fidoalliance.org/ > /tmp/mds.jwt`; collect every `metadataStatement.attestationCertificateKeyIdentifiers` value into a set; `git clone --depth 1` google/OpenSK, solokeys/solo2, Nitrokey/nitrokey-3-firmware, polhenares/pico-fido, conorpp/u2f-zero, fido-alliance/conformance-test-tools-resources; for every PEM/DER cert and every private key in those trees, compute SHA-1 over the `subjectPublicKey` BIT STRING contents and (`a`) intersect with the identifier set, (`b`) intersect with the SPKI hash of every EE anchor dumped by `tools/mds-anchor-audit.py --dump`. | expect: (`b`) empty or 0-2 hits, (`a`) empty — but any hit is a registered key or registered anchor whose private half is public | proves: whether *any* model can be chained to legitimately by a non-vendor. A hit in (`b`) is the direct route to signal 1: the EE anchor *is* the attestation leaf, so holding its key means holding a registered leaf key without a vendor relationship.
2. **Global-identifier probe (cheap, decisive on scope).** Take the four admitted AAGUIDs (`f4ce5fc0`, `d7781e5d`, `a25342c0`, `42b4fb4a`), dump their full metadata statements, and check whether any declares `attestationCertificateKeyIdentifiers` at all; then for one non-admitted identifier-bearing entry (any old `fido-u2f` dongle), arm `tools/probe.sh` with AAGUID `f4ce5fc0` + a packed `x5c` whose leaf SPKI is replaced by the certificate from that entry's identifier namespace (a random key is fine — row 3 shows `attStmt.sig` is unchecked). | expect: 200, flag false (identifier pool not global) or 400 (identifier mismatch is a hard gate) | proves: whether the *key hash* is checked globally like anchors (row 27) or per-AAGUID. If global and permissive, the flag test is reachable with any registered public key, which turns experiment 1 into a classification test rather than an admission test.
3. **EE-anchor class sweep beyond Securitag.** Run the audit tool, list all EE-anchored entries, and for each of the first five enrol with that AAGUID and `x5c = [anchor cert]` (anchor presented as its own leaf, since anchor == attestation cert by definition). | expect: 400 `passkey_verification_failed` on all five (generalising row 10/11) — unless one EE entry's AAGUID happens to sit in OpenAI's admitted set, in which case 200 and a flag read | proves: whether the EE class is uniformly model-gated or whether Securitag was refused for an unrelated reason; also whether an admitted-Yubico-AAGUID entry ever ships an EE anchor (that would be a genuine-chain route with no vendor contact).
4. **Untested attestation formats.** `fmt: "android-key"` (spec-shaped `attStmt` with `alg`, `sig`, `x5c` = any Android key-attestation chain; the Google Hardware Attestation Root is published at https://developer.android.com/privacy-and-security/security-key-attestation) and `fmt: "fido-u2f"` (CTAP1-style `sig`/`x5c`), each on AAGUID `f4ce5fc0` and on a real `fido-u2f`-era identifier-bearing AAGUID. | expect: 400 for both, mirroring rows 15-16 and 29 | proves: whether only `packed` is parsed at all. If `android-key` is admitted, a real phone's StrongBox chain (obtainable without buying a key) enters scope while signal-1 classification stays an open question.
5. **`qualifying_count` oracle readability.** On the Daybreak page, read the bearer token in-page (`JSON.parse(localStorage.getItem(...))`, `/api/auth/session`, or the `Authorization` header of the `/backend-api/cyber_verification/status` request in DevTools → Copy as cURL), then poll `POST /backend-api/cyber_verification/refresh_status` before and after each enrolment in experiments 1-4. | expect: token readable from the session cookie/JWT, counts stable at 0 while `is_non_exportable_hardware_key` is false | proves: whether counts move at *admission* (a second, earlier oracle than the per-credential flag) or only at classification — this distinguishes "model gate passed" from "flag pending".
6. **Re-evaluation through time, on credentials we already hold.** For the row 27 credential (Securitag AAGUID, Yubico tail, 200) and any experiment-1 hit, re-query signal 1 at t+2 min, t+10 min, t+30 min, t+24 h, plus one credential enrolled >3 weeks ago. | expect: false at all points for software creds | proves: whether "flips days later" is a real re-evaluation pass or community noise; a flip would mean the flag is time-deferred and admission-adjacent rather than stateless.

## NEW ANGLES

- Submit `fmt: "fido-u2f"` deliberately: the identifier namespace exists *only* for that format, so if the endpoint parses CTAP1 attestation it may resolve the credential through the identifier table rather than the AAGUID table, sidestepping the model gate entirely.
- Enumerate MDS `attestationTypes` across all entries and check whether `attca` / `anonca` / `ecdaa` entries differ structurally from `basic_full`; no admitted model we have tested carries `attca`, so the flag could be an attestation-*type* test that our Yubico-shaped leaves fail by declaring `basic_full`.
- Check the MDS BLOB's `statusReports` for entries whose certification status changed across blobs 270-290 (the Cloudflare thread shows RPs pinned to a snapshot, https://community.cloudflare.com/t/fido2-security-key-enrollment-fails-with-attestation-certificate-chain-is-not-sign/959209); a newly-added or re-certified entry is the cheapest way to catch an admission-list addition.
- Android StrongBox `android-key` chain from a physical phone (Google's published root) as the only remaining certificate authority a non-vendor can legitimately obtain issuance from — worth a dedicated row whether or not the format gate admits it.
- SoftHSM/`swtpm`-style local CAs are worthless, but Yubico's *test* attestation material (any published Yubico batch cert whose private key shipped in demo code) is worth a targeted grep in Yubico's own repos, separate from the conformance-PKI dead end.
