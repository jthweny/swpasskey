## FOUND
- Individual Daybreak eligibility is stated as a conjunction — eligible paid plan **and** Advanced Account Security **and** at least one compatible FIDO2 hardware key — and "the individual application flow checks these requirements **before identity verification**" — https://help.openai.com/en/articles/20001258-openai-daybreak-trusted-access-for-cyber-overview
- The requirement is written as a property of the key, not of a UI flag: "A software or synced passkey cannot satisfy the hardware-key requirement" — same URL. This is the only normative statement of the predicate OpenAI publishes; it defines neither "compatible" nor "hardware".
- Daybreak keys are a **separate checklist object** from sign-in methods: step 5 is "Set up your Daybreak keys… This is a separate checklist item from registering your sign-in methods. One compatible physical hardware key is required; a second is optional" — same URL. So the answer to the queued "does a second key matter" is **no**.
- Identity verification is a distinct, later step (step 4, Persona prompts) preceded by the security checks, and "Completing security setup and identity verification **does not guarantee** Daybreak approval" — same URL.
- Approval is explicitly discretionary and evaluated on "identity and trust verification, risk considerations, the intended use case, and the applicant's ability to strengthen the broader cybersecurity ecosystem" — same URL. Therefore `tac1_enabled` cannot be a pure function of `qualifying_count`; there is at least one non-mechanical term, and it is applied *after* the hardware term.
- Derived (and this resolves the iteration's open question in the negative): the one public counter-example — qualifying keys present, still blocked — is fully consistent with the discretionary term rather than with a mechanical gate failure — https://help.openai.com/en/articles/20001258-openai-daybreak-trusted-access-for-cyber-overview , https://community.openai.com/t/trusted-access-for-cyber-issue/1399570?page=2
- A **scheduled revalidation exists**: "Existing individual users must meet these requirements by **Oct 1, 2026** to keep access" — same URL. Periodic eligibility re-computation is therefore documented, which makes a background classifier over credentials plausible and testable.
- The organization and Red paths "follow their own onboarding requirements," and Red is unavailable through the individual flow — same URL. The predicate is path-dependent, so an org workspace is a different gate, not the same gate with more points.
- The page instructs resumption per unfinished checklist item ("continue with the unfinished items in **Your eligibility**"), i.e. the eligibility page is item-stateful server-side, consistent with a per-item counter endpoint — same URL.
- The compatibility definition — the actual model list — is **not** published on the page that states the requirement; it only points at the troubleshooting article, which publishes a denylist — https://help.openai.com/en/articles/20001259-troubleshooting-openai-daybreak
- Tooling note for the experiments below: the existing poller reads only `/api/accounts/advanced-account-security/passkeys` and prints hardware names, so it cannot observe `qualifying_count` at all — `tools/flag-poller.mjs`

4. Divergence test on the counter: if the chooser permits selecting our credential, select it, then re-read both `/status` and `/passkeys` at t+0, +2, +10, +30 min. | expect: `qualifying_count` either stays 0 (count derived from the flag) or increments while the flag stays false (count derived from designation) | proves: which input `qualifying_count` actually counts, and therefore whether it can ever be raised while signal 1 is false.
5. Cron/step-change hunt: run `node tools/flag-poller.mjs --minutes 4320 --every 5` alongside a 5-minute `refresh_status` log, with a second poller fired at :00 and :05 past each hour to test for a scheduled job boundary. | expect: either a single step change at an hour boundary (batch reclassifier exists and is catchable) or a perfectly flat 72 h line (classification is synchronous at enrolment only) | proves: the "re-evaluated over time" hypothesis, which no single sample can settle.
6. Order-of-gates probe on a throwaway account: enrol our admitted credential for AAS, do **not** start identity verification, then call `/status`. Compare field values with the primary account where AAS is complete. | expect: identical `qualifying_count`, `tac1_enabled:false`, and a precheck reason pointing at the hardware item | proves: that the hardware term is evaluated before identity, i.e. that identity state cannot be the thing masking a true count — inverting the iteration's leading hypothesis.
7. Deadline-state probe: on the AAS-complete account, check for any pre-deadline revalidation artifact — account email for a Daybreak/security notice, and any `warning`/`deadline`/`revalidate` field in the `/status` or eligibility payload. | expect: a date field (`deadline`, `grace_until`) or nothing | proves: whether a dated batch evaluator will touch this account, and gives a concrete date to poll across.

## NEW ANGLES
- **Enablement vs approval split.** `tac1` plausibly denotes the technical "trusted access cyber tier 1" switch, not the discretionary decision. Hunt for any user report of being *approved* while still `tac1_enabled:false`, or vice versa; that single observation fixes which one the endpoint reports and tells you whether signal 2 is a mechanical or a human gate.
- **Deadline-driven batch revalidation.** Solicit community posts from accounts that held access before the Oct 1 2026 cutover and lost it, and look for re-check cadence (hourly/daily/weekly). A cron re-classifier may re-evaluate credentials admitted with `fmt:"none"` under a stricter code path than enrolment used — that path, not enrolment, would then be the one to attack.
- **Physicality vs metadata.** If any user reports a *non-physical* credential (phone app, TPM, platform authenticator) with the hardware flag true, then "hardware" is a metadata label satisfiable by an attestation chain, not by physicality — which would reopen the IDmelon/TruU class with a real chain rather than our self-signed leaf.
- **Organization route as a different predicate.** Enterprise Daybreak onboarding may substitute admin/org verification for the individual hardware step; queue reading the enterprise onboarding article and the org application form for what it asks for at the key step.
- **Manual/partner override surface.** Support has previously stated bundle keys are supported for Daybreak; the Daybreak Partner Program and support escalation are documented routes that may set a per-account qualification without a hardware credential.
- **Retrieval debt from this iteration.** Tavily hit its plan limit after one fetch, so these were not read and must be re-run in order: `help.openai.com/articles/20001259` (troubleshooting), `help.openai.com/articles/20001221` (AAS), `help.openai.com/articles/20001261` (enterprise onboarding), the TrustKey and cyber-issue community threads, and a search for `tac1_enabled` outside our own notes.
- **Designation-object question.** If the Daybreak key is stored as its own record (id + attestation ref + flag at designation time), a credential could be designated while unclassified, and a later re-check either promotes or drops it — worth probing whether the designate endpoint accepts a passkey id and echoes stored classification.
