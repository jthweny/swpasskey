## EXPERIMENTS

1. Enrolment matrix, one daemon run, five untried AAGUIDs in this order: `e77e3c64` (Security Key NFC 5.7, L2, **legacy** anchor), `b7d3f68e` (Security Key NFC 5.7.4, L2, **Root 1** anchor), `a4e9fc6d` (Security Key NFC 5.4, L2, legacy anchor), `19083c3d` (5C/5 Nano 5.7, L2), `4599062e` (5C Nano 5.7.4, L2, OpenAI bundle model). Same self-signed packed leaf for all five, nothing else changed; delete the credential between rows. | expect: `e77e3c64`/`b7d3f68e`/`19083c3d`/`4599062e` → 200; `a4e9fc6d` is the tiebreaker (200 ⇒ gate is *certification level*; 400 ⇒ gate is *5.7+ generation*). Flag false everywhere. | proves: whether admission is L2, generation, or a hardcoded list, and whether anchor root or form factor matter at all — the exact question of this iteration, answered in one session.

2. Anchor-invariance control on one accepted AAGUID: enrol `d7781e5d` three times with (a) self-signed leaf, (b) leaf + the exact MDS-published `Yubico Attestation Intermediate A 1` + `Yubico Attestation Root 1` PEMs from the MDS entry as `x5c`, (c) leaf whose issuer DN is `CN=Yubico Attestation Intermediate A 1` plus the `id-fido-gen-ce-aaguid` extension and `CA:FALSE`/KU/SKI/AKI copied from the published intermediate. | expect: 200 ×3, `is_non_exportable_hardware_key:false` ×3 across t+0/2/10/30 min. | proves: the flag is not "chain reached the published anchor set" and not "leaf carries the AAGUID extension" — it is either a signature it can verify against Yubico's key or a field we are not sending.

3. Instrument the bridge to dump the actual `PublicKeyCredentialCreationOptions` the OpenAI pages send — log `attestation`, `attestationFormats`, `extensions` (look for `enterprise`/`id-fido-gen-ce-aaguid`), `authenticatorSelection`, and `excludeCredentials` from the "Add a hardware security key" page and from `auth.openai.com/advanced-account-security/secure-methods`. | expect: either `attestation:"direct"` with no enterprise extension (⇒ flag cannot depend on EA), or `attestation:"enterprise"` for an EA-capable AAGUID (⇒ EA is the trigger and rows 1–19 never tested the right shape). | proves: which attestation conveyance the verifier is actually asking for, and therefore which of the two remaining flag hypotheses is even reachable.

4. Enterprise-attestation shot, only if (3) shows `enterprise` or EA extensions: enrol `6ab56fad` (5C NFC 5.7.4, EA-capable) and produce packed attestation marked enterprise, with `id-fido-gen-ce-aaguid` in the leaf, EA-shaped AAGUID in authData, and a serial-shaped identifier in the packed `attStmt` extension. | expect: 200 admission; flag flips to `true` if the check is "we were shown EA", stays `false` if it needs a verifiable Yubico signature over the serial. | proves: whether EA-ness alone is the hardware classifier — a hypothesis none of the 19 rows tested.

5. Grep Oracle: `curl` the chatgpt.com / auth.openai.com JS bundles and the `/api/accounts/advanced-account-security/passkeys` response schema, then grep for `aaguid`, `is_non_exportable_hardware_key`, `tac1`, `hardware`, and any literal UUIDs. | expect: either an embedded AAGUID→class map (⇒ the accepted list is readable), or the flag name appearing only in the API response (⇒ classification is server-side only). | proves: whether the accept list is *published* in the client, which converts the whole problem from guessing to reading.

Non-attestable-entry probe: take an accepted model's **EA/alt-profile** AAGUID whose MDS entry publishes no `attestationRootCertificates` (verify from the MDS entry before enrolling), enrol it with `fmt:"none"` and then with a self-signed packed leaf. | expect: 200; flag `true` for the anchorless entry if a fail-closed verifier treats "nothing to verify against" as pass. | proves: whether the flag is reachable by picking the right *entry shape* rather than the right signature.

## NEW ANGLES

- OpenAI's partner bundle is `5C NFC` + `5C Nano` (Forrester) — the 5C Nano 5.7.4 AAGUID `4599062e` has never been tried and is the cheapest confirmation that "in the bundle" == "on the accept list".
- The accepted `d7781e5d` entry publishes an end-entity-shaped cert ("Yubico FIDO Attestation A 1", CA:TRUE, issued by Intermediate A 1) alongside the roots. That is the row-10 class (end-entity anchor) but inside an *accepted* model — check whether any accepted AAGUID's published set contains a cert whose key is derivable/public (test certs, preview CA material) rather than Yubico's production key.
- "Yubico FIDO EE" leaf naming implies per-batch EE certs are issued from the CA; check whether Yubico's developer programme ever ships a customer-provisioned attestation path (YubiKey as a Service, custom-programmed enterprise orders) — this is the operator's "vendor issues leaves to customers" exception, and EA keys are literally custom-programmed per customer.
- OpenSK (Google's open FIDO2 firmware) and Nitrokey 3 / Solo v2: customer-flashable firmwares where the attestation cert is provisioned at build/provisioning time — check whether any of them can present an MDS-listed AAGUID with a self-provisioned leaf, which would be the first *legitimate* self-held leaf.
- `keyProtection`/`attestationTypes` differential: enumerate every MDS entry with `attestationTypes:["basic_surrogate"]` or empty roots, cross-reference against OpenAI's observed 200/400 behaviour, and see whether "attested but unverifiable" is a class OpenAI treats as hardware.
- The Daybreak doc is the only published artefact that names models. Monitor it as a versioned oracle — the T110/T120 carve-out appeared *after* launch and after purchases, which means the list is mutable and support-visible; a support ticket asking "which models qualify" is a cheaper oracle than enrolment probing.
