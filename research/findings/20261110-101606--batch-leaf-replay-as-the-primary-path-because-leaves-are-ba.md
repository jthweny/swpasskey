## FOUND
- Yubico states plainly that "all YubiKey 5 series devices created within the same production batch possess the same attestation certificate", and FIDO guidance sets batch size at ≥100,000 devices — so a leaf attests a *production batch identity*, never a unit. This is a property of the format, published by the vendor itself — https://developers.yubico.com/Developer_Program/WebAuthn_Starter_Kit/Attestation.html , https://yubicolabs.github.io/passkey-workshop/docs/advanced_use_cases/attestation/overview
- W3C WebAuthn §13.3.2. ("Attestation Certificate and Attestation Certificate CA Compromise") documents the exact consequence of batch sharing: the manufacturer anonymizes users "at the risk of not being able to revoke a particular attestation certificate if its private key is compromised" — the spec itself treats batch-level replay as a named threat with per-batch blast radius — https://www.w3.org/TR/webauthn-2
- The MDS `StatusReport` dictionary defines `ATTESTATION_KEY_COMPROMISE` and carries `batchCertificate` / `certificate` / `UPDATE_AVAILABLE` fields with `timeOfLastStatusChange` — batch-scoped revocation exists as a first-class mechanism, meaning any credential built on a shared batch leaf remains permanently exposed to after-the-fact invalidation — https://fidoalliance.org/specs/mds/fido-metadata-service-v3.1-ps-20250521.html
- A primary-source FIDO dev-list thread on a custom RP2040 authenticator contains the reasoning in the vendor/designers' own words: "If a shared attestation key can be extracted from one unit, it can be reused to impersonate the batch's attestation identity… my concern is how much confidence an RP can place in that attestation as evidence of hardware provenance" — the ecosystem's own engineers frame batch attestation as batch-provenance evidence only — https://groups.google.com/a/fidoalliance.org/g/fido-dev/c/QZ4z0OVuPb0
- `keyProtection` in a metadata statement is vendor-authored and mutually exclusive by definition (`KEY_PROTECTION_SOFTWARE` cannot coexist with `HARDWARE`/`SECURE_ELEMENT`), and the certification that lends it weight at L1 is documentation review — "Any device, software or hardware… None/Review by FIDO security secretariat" — so the "hardware" bit a verifier reads from MDS is a *reviewed self-assertion*, not an observed property of the credential — https://developers.google.com/android/reference/com/google/android/gms/fido/fido2/api/common/KeyProtectionTypes , https://fidoalliance.org/security-certification-authenticator-security-levels , https://fidoalliance.org/specs/fido-security-requirements/fido-authenticator-security-requirements-v1.5-fd-20211102.html
- L1+ is a software-only certification tier (white-box crypto, anti-tampering), and FIDO explicitly certifies software authenticators at L1 — the certification path is genuinely open to a software authenticator; what it cannot do is truthfully assert hardware key protection, which is exactly the bit `is_non_exportable_hardware_key` appears to key on — https://fidoalliance.org/fido-user-authentication-certification-programs , https://fidoalliance.org/certification/authenticator-certification-levels
- Entra's implementation notes confirm the industry's trust model: AAGUID-based key restrictions "can't be used as a security control" without enforced attestation, since the AAGUID is otherwise unverifiable, and without attestation Entra "can't guarantee any attribute about the passkey, including its type, make, model" — OpenAI's gate deviates from this by admitting bundle models on AAGUID sight alone — https://hybridbrothers.com/posts/entra-synced-passkeys , https://janbakker.tech/prepare-for-passkeys-in-entra-id
- Yubico's PIV attestation key (slot F9) is documented as **customer-replaceable** (generate on device or import), whereas WebAuthn/FIDO2 attestation is factory batch-fixed — the two Yubico "attestation" surfaces have entirely different key-custody models, and only the replaceable one is ever customer-held — https://docs.yubico.com/yesdk/users-manual/application-piv/attestation.html , https://developers.yubico.com/PIV/Introduction/PIV_attestation.html
- Yubico's 2025 root rotation is documented with firmware-bound chain assignment (5.7.4+ → `Yubico Attestation Root 1` via intermediates; older → `Yubico PIV Root CA Serial 263751`) — chain vintage is fingerprintable per firmware family, which is a *detectable* attribute of any reused batch material — https://developers.yubico.com/PIV/Introduction/PIV_attestation.html
