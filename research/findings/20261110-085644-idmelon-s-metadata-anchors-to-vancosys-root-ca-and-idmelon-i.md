## EXPERIMENTS
1. **Genuine batch leaf, our own signing key.** Obtain a real attestation leaf for an accepted AAGUID (`d7781e5d` / `a25342c0` / `f4ce5fc0`) — from a borrowed bundle YubiKey via `makeCredential` with `attestation=direct`, or from any published batch cert — then enrol the emulator with `x5c = [genuine leaf, Yubico intermediates, Yubico Attestation Root 1]` and `attStmt.sig` signed by **our** key. | expect: 200 and `is_non_exportable_hardware_key: true` if verification is chain-only (reinforced by brief row 3, sig unverified); 200/`false` or 400 if leaf-key possession is actually proven | proves: whether the attestation **private key** is checked at all, i.e. whether one shareable batch cert converts the whole gate into a copy operation
2. **Anchor-rotation correction.** Our rows 1–9 appended the *pre-2025* Yubico roots. Re-run with the accepted-generation material: leaf with `id-fido-gen-ce-aaguid = d7781e5d`, issuer DN set to the 5.7.4+ intermediate, `x5c` = [leaf, `yubico-intermediate.pem`, `yubico-ca-1.pem`], self-signed leaf key. | expect: 400 → chain is cryptographically validated, making experiment 1 decisive; 200 + `false` → chain is not validated and the flag derives from something other than the chain | proves: whether the anchor used for the bundle generation was ever actually tested (it likely was not)
3. **Full AAGUID sweep of the gate.** Take the MDS v3 BLOB AAGUID set plus the firmware-variant Yubico AAGUIDs we never tried (`4599062e` 5C Nano 5.7.4 EA-capable, `20ac7a17`, `fcc0118f`, `79f3c8ba`, `662ef48a`, `b2c1a50b`, `19083c3d`, `ff4dac45`), enrol each with a fixed minimal statement, log 200/400. | expect: more 200s than the three known, plausibly including `4599062e` since C Nano is in the bundle | proves: the exact allowlist, and whether it is "bundle SKUs" or "all 5.7.x-generation AAGUIDs"
4. **Extension vs authData AAGUID cross-check.** Using whichever AAGUID enrols, submit `authData.aaguid = X` while the leaf's `id-fido-gen-ce-aaguid` extension says `Y` (both inside the accepted set). | expect: 400 or flag `false` → both are compared; 200 + `true` → the extension is ignored and only authData matters | proves: which field the classifier trusts, i.e. whether a leaf for a *different* accepted model can be borrowed
5. **BE/BS and UP-only flag matrix.** Enrol identical statements differing only in `authData` flags: `0x41` (UP only, no AT), `0x45` (AT), `0x45|BE|BS` (backup-eligible), and `AT` omitted entirely. | expect: no change to `is_non_exportable_hardware_key`; any change proves the label is read from syncable-credential bits rather than attestation | proves: whether "passkey vs hardware" is decided from credential properties we already control
6. **`tac1_enabled` dependency probe.** After the best result from 1–4, poll `POST /backend-api/cyber_verification/status` at t+2/10/30 min with (a) one hardware-classified credential, (b) two, (c) a synced passkey present, (d) synced passkey deleted. | expect: gate follows hardware-credential presence and clears when the software passkey is removed, per the Support-vs-docs contradiction | proves: whether Daybreak is credential-derived (engineering problem) or review-derived (not solvable by artefacts)

## NEW ANGLES
- Stop hunting vendor keys; hunt **batch-cert reuse**. If experiment 1 lands, the entire gate is defeated by one 100k-device-shared public cert, and the interesting follow-up is whether OpenAI pins *anything* per-credential (leaf serial, SPKI hash, challenge binding) — test by rotating the borrowed leaf between two credentials on the same account.
- **Vendor of our own AAGUID** via the MDS Portal is administratively real (self-service listing, FIDO-signed BLOB). Scope only two things: FIDO L1 certification cost/evidence for a software authenticator, and whether metadata can lawfully claim `keyProtection: hardware` — note Vancosys' phone-app entry already claims `Hardware + Secure Element`, so the claim bar in MDS is historically low.
- **Ask IDmelon/Vancosys directly** (sales/support, not docs) whether they issue per-tenant AAGUIDs or attestation certs for their FIDO-as-a-service deployments, and whether HID's IAMS unit inherits the Vancosys CA. Nothing public exists; this is a one-email question worth more than another certificate experiment.
- **Yubico custom-AAGUID ordering**: Yubico supports custom configuration/custom AAGUIDs for RPs. Test whether OpenAI's gate keys on the *AAGUID value* or on the *model DN in the leaf issuer/subject*: a custom-AAGUID key chained to the accepted intermediate would separate those two.
- Re-read the TrustKey refusal as the sharpest anomaly: an MDS-listed, L1, hardware key with a valid chain is refused, so the accepted set cannot be "valid chain + hardware metadata". Enumerate what the accepted trio shares that TrustKey lacks (5.7.x generation, "Consumer Profile" SKU, OpenAI bundle SKU) and test each as an independent variable.
- Third-party attestation-verification code paths (python-fido2, webauthn4j, java-webauthn-server, fido2-lib) are the likeliest place for an X.509 edge case — specifically whether a leaf that is *itself* a CA (`CA:TRUE` + `keyCertSign`) can terminate the path before the real anchor is reached, given row 10 showed end-entity anchors are rejected for a different reason (model gate, not chain).
