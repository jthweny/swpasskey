## NEW ANGLES

- **TAC may be an out-of-band grant, not an in-product setting.** Look for a Daybreak/TAC *application* surface — a form, a trust-team contact, an "apply for your organization" page — and check whether the grant is issued against an org (business verification, domain, contract) rather than a credential. If so, the correct exploit shape is "get the account onto the org grant", and the credential flag becomes cosmetic.
- **Precedent machinery:** OpenAI already runs an org-level trusted-access programme for biological risk. If that one is granted per-organization by a human, TAC almost certainly reuses the same entitlement object — find that object's name and you find TAC's writer.
- **Feature-flag forensics:** compare `tac1_enabled` across accounts that differ only in plan or org membership. If it is a literal boolean in the account payload rather than a computed field, ask what else in that payload is a literal boolean and who sets those (beta flags have client-visible toggles).
- **Bundle programme as an org contract:** the OpenAI/Yubico bundle is a procurement relationship. Check whether the bundle ships with an *org onboarding* step (claim codes, an admin redemption flow). If keys are activated against a workspace, the binding event is org-side and worth capturing.
- **Support-answer archaeology:** the Support reply in the TrustKey thread is the only place vendor support has described the acceptance rule. Search that forum and the community for other Support replies containing "Daybreak" + "supported", "approved", or "organization" — a single such reply naming an admin action would settle this angle outright.
- **Denylist mechanics as a tell:** if TrustKey was flipped off in a week, whatever flips entries is a live config, not code. A config that an admin can reach is a policy; one that only staff can reach is a grant. Determine which store `tac1_enabled` and `is_non_exportable_hardware_key` live in by observing a flip in real time on a known-good key.
