## FOUND
- **Verification gap:** `web_search` and `web_fetch` both returned `This request exceeds your plan's set usage limit` for every query this iteration; no live fetch was possible. Claims below are marked `[re-read]` (I have read the source before) or `[unverified this run]`.
- **Attestation does not exist at assertion time.** `navigator.credentials.create()` returns an `attestationObject`; `navigator.credentials.get()` returns only `authenticatorData` + `signature` + `userHandle` + `clientExtensionResults`. A relying party that decides anything "per session" from the key cannot see the certificate, the AAGUID extension, or `x5c` at that moment — only the flag byte. `[re-read]` https://www.w3.org/TR/webauthn-3/#sctn-authenticator-data
- **The only hardware-shaped bits in an assertion are UP, UV, BE, BS.** `backupEligible`/`backupState` were added in WebAuthn Level 3 precisely so an RP can distinguish a synced (exportable) credential from a device-bound one at authentication time, and they are **asserted by the authenticator, not attested by anyone**. `[re-read]` https://www.w3.org/TR/webauthn-3/ (§ Credential backup eligibility / backup state)
- **The protocol-level name for this already exists and is per-authentication:** RFC 8176 registers `hwk` ("proof-of-possession of a hardware-secured key") and `swk` as `amr` values — carried in the ID token / access token for the *authentication event*, not stored on the credential. `[re-read]` https://www.rfc-editor.org/rfc/rfc8176#section-2
- **OIDC scopes `amr` to the authentication, not the enrolment.** `amr` is defined as "identifiers for authentication methods used in the authentication"; `acr` and `auth_time` are likewise per-token. So a per-session hardware term could be delivered by a server that maps the ceremony → `amr`, regardless of what was registered. `[re-read]` https://openid.net/specs/openid-connect-core-1_0.html#IDToken
- **A large RP already implements exactly the per-session model, and it is not attestation-based:** Microsoft Entra *authentication strengths* (incl. "phishing-resistant MFA") are evaluated at authentication and re-evaluated for each token, from the method used in that ceremony — the credential record is not what is scored. `[re-read]` https://learn.microsoft.com/en-us/entra/identity/authentication/concept-authentication-strengths
- **TLS-level hardware binding to a session is not available:** Token Binding (RFC 8471) is the only standard mechanism that would bind a session secret to a hardware key at the transport layer; it was dismantled in browsers and is unusable for this. `[unverified this run]` https://www.rfc-editor.org/rfc/rfc8471
- **Recoverable session secret bound to the key is already implemented here:** swpasskey supports `hmac-secret` with dual `credRandom` — the mechanism a server would use if it wanted a per-session proof only a fixed key can produce. https://github.com/… (local `README.md`, §Status) `[local]`
- **No Forrester primary source for the "live ceremony" read was locatable**, and I will not paraphrase one into existence. What is verifiable is the *structure* of the claim: Forrester's phishing-resistant-MFA guidance consistently frames the control as an authentication event, and OpenAI's own AAS description frames the key step as something you *perform*. Without the document, treat "live ceremony" as the hypothesis under test, not a finding. `[unverified this run]`
- **Measured gap in our own instrumentation:** every row in the table scores signal 1 (credential list) and signal 2 (`status`) on a session whose provenance is never recorded. `tools/flag-poller.mjs` reads `/api/accounts/advanced-account-security/passkeys` from whichever tab is signed in and never records how that session authenticated, nor decodes the session token. `[local]`
- **Logical consequence worth carrying:** rows 1–29 killed every path where *enrolment-time* evidence carries the flag. If any per-session term exists, the only hardware signal available in it is an unverified self-asserted flag (UP/UV/BE/BS) — the one place a software authenticator can truthfully present hardware-shaped data. That makes the per-session hypothesis the only remaining one whose evidence requirement we can actually satisfy.

## EXPERIMENTS
1. **Session claim diff.** In the debuggable Chrome: on a password/Google session, evaluate `(await (await fetch('/api/auth/session',{credentials:'include'})).json())`, base64url-decode the `accessToken` payload, record the full claim set. Sign out, sign in with swpasskey armed as `f4ce5fc0` (`tools/probe.sh p4 f4ce5fc0`), repeat. Diff claim names and values. | expect: identical claim names but a different method/time value (a `passkey`-ish `amr` entry, `auth_time`, or a method-specific provider claim) — or a byte-identical claim set, which is the informative negative | proves: whether a per-session method claim exists at all, and its exact value for a *software* key; if none exists, the per-session hypothesis is dead before any CTAP work.
2. **Stale vs fresh session, same credential state.** Enrol the key, keep the pre-enrolment session alive, poll `POST /backend-api/cyber_verification/status` at t+0/2/10/30 with it. Then sign out and sign in *with the key*, poll again on the identical credential state. | expect: `tac1_enabled` identical across both (per-credential) or true only on the key-minted session (per-session) | proves: signal 2's granularity — the single cheapest discriminator between the two models, and it needs no new attestation.
3. **Assertion census at the gate.** Run `tools/flag-poller.mjs --minutes 10` alongside a daemon log at `SWPASSKEY_LOG=debug`, then load the "Add a hardware security key" page and `/cyber`, capture every CTAP2 `getAssertion` (rpId, `allowCredentials` count, extension inputs) the page provokes. | expect: 0 assertions on the hardware-key page; possibly one on `/cyber` | proves: if the gate never requests an assertion, no assertion-time term can exist and signal 2 is purely account/credential-side; if it does, the BE/BS/UV values in that response are the candidate inputs.
4. **BE/BS bit matrix.** With the same credential, submit four gate passes: (BE=0,BS=0), (BE=1,BS=0), (BE=0,BS=1), (BE=1,BS=1), daemon patched to report each, everything else identical. | expect: all four 200 with signal 1 unchanged and `tac1_enabled` unchanged | proves: `backupEligible` is not read by their verifier (closing the last self-assertable hardware bit) — or, if any combination moves signal 2, we have located the only input a software key controls.
5. **`refresh_status` shape capture.** Read the page's `Authorization` header off a wrapped `fetch` (not from storage), call `POST /backend-api/cyber_verification/refresh_status` and save the full JSON from both a password-minted and a key-minted session. | expect: response contains account-level counts only (`qualifying_count` etc.), no session or credential identifier | proves: whether the endpoint is an account oracle or leaks a per-session term; also settles the "does it disagree with per-credential flags" question.
6. **Fresh-ceremony delta on signal 3.** Compare the "Continue" state on the hardware-key page when reached from (a) a session created before any FIDO ceremony, (b) a session created by asserting with the key. | expect: identical disabled state | proves: the (b) half of the question — whether classification alone unlocks Daybreak — independently of signal 1.

## NEW ANGLES
- Harvest `amr`/`acr`/`auth_time` across *all* providers the account can authenticate with (password, Google OAuth, Apple, passkey) to build the taxonomy of session claims; the passkey-vs-password diff is the only place a hardware term can enter, and it may be absent entirely.
- Whether a **step-up** (`prompt=login` / `max_age=0` / a forced assertion on the AAS page) re-runs classification: if `auth_time` freshness matters to the Daybreak gate, an old session could be masking a term that a fresh ceremony sets.
- Enumerate RPs that already treat self-asserted `BE=0` as equivalent to hardware (Cloudflare, Entra, GitHub) versus RPs that ignore it — a map of where the only software-controllable hardware bit is actually believed, which bounds how likely OpenAI is to use it.
- Read the CTAP extension requests OpenAI's page makes (`prf`, `hmac-secret`, `largeBlob`) — a server wanting a per-session key-bound proof must ask for one, and the ask is visible in `getAssertion` inputs even when the result is unused.
- Check whether `tac1_enabled` is `tac1`-specific: is there a `tac0`/`tac2` or a tier field in the same response, and does AAS completion alone move any of them? A conjunction model predicts tier fields move independently of the key.
- FIDO MDS `userVerificationDetails` / `keyProtection` at *assertion* granularity: does any accepted entry declare UV requirements that their page would surface per ceremony, giving a legitimate per-session distinction we could satisfy with software UV?
- Sourced check on OpenAI's passkey login path (Auth0-style provider claims for passkeys) — if their own login emits no method claim for passkeys, hypothesis 1 collapses cheaply and the queue should stop spending on per-session.
