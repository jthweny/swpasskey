## FOUND

- The Metadata Statement spec states the trust anchor for an entry "can be a root certificate, an intermediate CA certificate or even the attestation certificate itself" — i.e. an end-entity cert as `attestationRootCertificates[0]` is spec-legal, not malformed — https://fidoalliance.org/specs/mds/fido-metadata-statement-v3.0-ps-20210518.html
- The same spec makes absence mandatory for one class: for surrogate/self attestation "no attestation trust anchor is required/used. So this array MUST be empty in that case" — https://fidoalliance.org/specs/mds/fido-metadata-statement-v3.0-ps-20210518.html
- The FIDO MDS vendor portal tells vendors exactly that: "When supporting surrogate basic attestation only, no attestation trust anchor is required/used, so you just need to update the metadata statement with no certificates specified" — https://fidoalliance.org/mds-portal-user-guide-for-vendor-users
- MDS validation rules were *relaxed* to permit empty roots: Registry 2.3 / MDS changelog — "Updated `ValidateAttestationRootCertificates` to allow empty certificate arrays if the attestation type is `none` or `anonca`", plus two new attestation types `none` and `anonca` — https://fidoalliance.org/mds-changelog
- `anonca` is defined as per-credential certs from an Anonymization CA, applicable to `android-safetynet`, `android-key`, `apple`, `apple-appattest` — i.e. formats whose chains cannot be anchored to the RP's MDS entry at all — https://fidoalliance.org/specs/common-specs/fido-registry-v2.3-rd-20260105.html
- Population, from an implementation that parsed the live blob: 500 entries total; `basic_full` 475, `basic_surrogate` 36, `attca` 2; statuses include 116 `NOT_FIDO_CERTIFIED` and exactly one `REVOKED` (`ba86dc56-635f-4141-aef6-00227b1b9af6`, TruU Windows Authenticator, 2023-12-20) — https://github.com/sebadob/rauthy/issues/1618
- Same source: `basic_surrogate` self-attestation "carries no x5c" — so for ~36 MDS entries there is no certificate chain to validate at all, and the AAGUID is the only label — https://github.com/sebadob/rauthy/issues/1618
- A concrete public example of an entry with `"attestationRootCertificates": []` and `attestationTypes` = self attestation (`basic_surrogate`, 15880), and an RP that happily maps AAGUID→metadata from it, showing "empty roots" entries are used in production metadata pipelines — https://community.ibm.com/community/user/security/blogs/shane-weeden1/2021/06/30/isam-fido2-metadata-and-registration-policy-enforc
- OpenAI's own troubleshooting doc now says not all FIDO2 keys qualify: "Are all FIDO2 hardware security keys supported? No. TrustKey T110 and T120 security keys are currently ineligible for individual Daybreak access" — https://community.openai.com/t/daybreak-does-not-recognize-trustkey-t110-physical-fido2-keys-as-hardware-security-keys/1401917
- A real, correctly-attesting physical FIDO2 key that completes PIN+touch enrollment is still listed as "Passkey" and leaves Continue disabled — so a valid vendor attestation chain is *not* sufficient, and the classifier is model-specific — https://community.openai.com/t/daybreak-does-not-recognize-trustkey-t110-physical-fido2-keys-as-hardware-security-keys/1401917
- Classification is not instantaneous: a user with one YubiKey + one passkey saw `/cyber` flip to "You're all set" with no further changes — "some delayed/backend state update rather than the verification being permanently rejected" — https://community.openai.com/t/trusted-access-for-cyber-issue/1399570?page=2
- A major RP library defaults to fail-open on unattested credentials: `allowUntrustedAttestation(true)` is documented as the default in Yubico's java-webauthn-server MDS integration — https://developers.yubico.com/WebAuthn/Concepts/FIDO_Metadata_Service_(MDS).html
- Since WebAuthn L3 (REC 2026-08-25) the AAGUID is no longer zeroed when `attestation: "none"`, so a server can obtain a model label with *no* attestation whatsoever — https://ssojet.com/blog/webauthn-level-3-changes-for-passkey-implementers (L2 behaviour: "Replace the AAGUID … with 16 zero bytes", https://www.w3.org/TR/webauthn-2)
- Documented real-world X.509 path-building fragility: a FIDO verifier failed on the current MDS chain purely because Java's PKIX validator builds root→leaf rather than leaf→root — https://github.com/Yubico/java-webauthn-server/issues/498

## EXPERIMENTS

1. Download `https://mds3.fidoalliance.org/`, base64url-decode the JWT payload, and emit a table of every entry's `aaguid`, `attestationTypes`, `keyProtection`, number of `attestationRootCertificates`, and for each root: `basicConstraints` CA flag, `keyUsage`, whether subject==issuer, and whether the root's SPKI/subject matches anything in `attestationCertificateKeyIdentifiers`. Bucket into: (A) roots absent/empty, (B) roots present but `CA:FALSE` end-entity, (C) normal CA roots. | expect: 36±few in A matching `basic_surrogate`; a small non-zero group in B (single-batch vendors who published their attestation leaf as its own anchor); B entries with `keyProtection` containing `hardware`/`secure_element` are the targets | proves: the candidate AAGUID set exists at all, and how many entries are anchored on a *publicly obtainable* certificate rather than a private-key-backed CA

2. Take one class-B AAGUID (end-entity anchor). Enrol with that AAGUID, `fmt: "packed"`, and `x5c = [that exact public MDS anchor certificate]` — no leaf of your own, no private key for it; put random bytes in `attStmt.sig`; credential public key = your own emulator key; authData flags UP|UV|AT, BE=0, BS=0. | expect: enrolment 200 (consistent with row 3); if the verifier anchors by cert identity and skips `attStmt.sig`, `is_non_exportable_hardware_key` flips true and Continue enables | proves: whether "chain to anchor" is satisfied by *possessing* a certificate rather than by signing with it — this is the one path that needs no vendor key

3. Repeat experiment 2 with the class-B anchor's SPKI deliberately unrelated to the credential public key, and with `credentialPublicKey` = P-256 while the anchor is RSA (and vice versa). | expect: same result as 2 if no SPKI/alg binding is enforced | proves: whether leaf-SPKI↔credential-key binding is checked, which is the second precondition for the anchor-as-leaf mechanism to be exploitable

4. Take one class-A AAGUID (empty `attestationRootCertificates`, `basic_surrogate`) and enrol twice, once with `fmt: "none"` (empty attStmt) and once with `fmt: "packed"` and no `x5c` (true self-attestation, sig by credential key). Keep BE=0/BS=0. | expect: false for both under a fail-closed verifier; true for either would mean "no anchor ⇒ no check ⇒ trusted" | proves: whether OpenAI's classifier fails open when there is nothing to validate, i.e. whether the 36 self-attestation entries are a free pass or a hard block

5. Same credential as experiment 4, poll `GET /api/accounts/advanced-account-security/passkeys` and `POST /backend-api/cyber_verification/status` at t=0, 2, 10, 30 and 120 minutes without re-enrolling. | expect: either frozen false (synchronous classifier, rows 1–9 genuinely failed) or a late flip | proves: whether any prior row was a false negative caused by the asynchronous backend state update reported by other users — this can invalidate conclusions drawn from rows 1–9

6. Enrol with `fmt: "tpm"` using a swtpm-generated AIK cert plus a self-made CA appended, with the AAGUID of one of the two `attca` entries (or a TPM-family entry like a Microsoft Pluton/platform entry). | expect: 200 enrolment, flag false | proves: whether the TPM branch is routed through the same anchor check (it should be, but the two `attca` entries have unusual metadata and may hit a different code path)

## NEW ANGLES

- Audit open-source authenticator firmware and tooling for *committed* attestation keypairs (OpenSK's in-repo test attestation CA, SoloKeys' build-your-own-attestation-key flow, Nitrokey's open firmware). A TPM-based OpenSK build running against swtpm is a fully software virtual authenticator that emits a genuine `fmt: "tpm"` statement, and its AAGUID is a fixed constant we can also test against the class-A/B list from experiment 1.
- Enumerate OpenAI's AAGUID allowlist empirically: the account API's `authenticator_name` echoes the MDS description for whatever AAGUID we send, so enrolling a batch of MDS AAGUIDs (Yubico family, Feitian, Token2, Thetis, Excelsecu, Swissbit, G+D, HID Crescendo) and reading back names maps the label space; any AAGUID where the label is *not* "Passkey" is a strong allowlist candidate worth spending attestation effort on.
- MDS entries whose anchor is an *intermediate* rather than a root are explicitly legal and are the ones most likely to be mishandled: a verifier that only compares `x5c.last()` against the anchor will reject, one that builds a path will accept — worth a dedicated sweep of class-B/C boundary cases plus a cross-check of the Yubico issue-498 direction bug.
- Check whether OpenAI requests enterprise attestation or `attestationFormats`/`attestation: "direct"` at all by inspecting the CredentialCreationOptions their client sends (capture via a local CTAP2 proxy logging `makeCredential` plus a browser-side `navigator.credentials` wrapper). If it is `none` with the L3 no-zeroing rule, the classifier is AAGUID-only and the entire attestation avenue is the wrong battlefield.
- Registry 2.3's `none` and `anonca` attestation types are new enough that server-side policy code likely has a default branch; entries adopting them (Apple `apple-appattest`, Android Key) are the most probable place for a policy bypass, and Apple/Android Keystore attestations can be produced without a purchased FIDO key.
- Practical cost of becoming the vendor: MDS portal requires each authenticator to have a unique attestation root certificate and a certification record before publish, so the question to nail down next is whether FIDO L1 certification can be granted to a software authenticator and what `keyProtection` claim it may make.
