## NEW ANGLES
- The flag's namespace is vendor-written metadata, not vendor-signed cryptography — so the correct ask is a metadata registration, not a signature. Every avenue so far assumed we need a key we don't have; row 28 says we need a *line in a JSON file we can't write*.
- MDS is BLOB-signed by the FIDO Alliance, so a vendor cannot silently add your key hash — the change is visible in the next BLOB and attributable. That makes it auditable and therefore *askable*: a small OEM with nothing to lose in reputation might do it, a silicon vendor never will.
- Snapshot-age as an exploit surface: any AAGUID added to MDS after OpenAI's snapshot is invisible to them now but will be visible later, and hardware-list membership appears to be assigned by a human at OpenAI. A newly admitted OEM model that ships with a *customer-signable* attestation mode would be the first case where both halves could hold.
- `fido-u2f` and `android-key` remain entirely unmeasured as formats; the all-zero AAGUID means those entries are unreachable by AAGUID and reachable only by cert key id — which is the same namespace the flag appears to test.
- Watch `attestationTypes: ["basic_surrogate"]` entries: they assert hardware key protection from an attestation cert that is *not* the credential key, and no row has tested whether the classifier treats surrogate attestation as non-exportability.
- The deny component (TrustKey) is the only observed *subtractive* rule; nothing has probed whether it is keyed on AAGUID, model string, or cert key id — a deny test with a mismatched AAGUID/model pair would reveal which field it reads and therefore which field the allow side reads too.
