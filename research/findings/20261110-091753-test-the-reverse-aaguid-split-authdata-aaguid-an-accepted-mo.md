## FOUND
- The packed-attestation verification step for OID `1.3.6.1.4.1.45724.1.1.4` (`id-fido-gen-ce-aaguid`) is **conditional on presence**: "If attestnCert contains an extension with OID … verify that the value of this extension matches the `aaguid` in authenticatorData" — a leaf without the extension passes the match check vacuously, and the same conditional wording exists in the TPM procedure (against `aikCert`) as well as in packed. — https://www.w.org/TR/webauthn-2 (§8.2, §8.3) / https://www.w3.org/TR/webauthn-3
- The spec explicitly frames the leaf extension as the **cross-check against** authenticator data, and frames trust-anchor selection as a *separate* lookup keyed on the claimed AAGUID: "This value is used by the FIDO Server to lookup the trust anchor for verifying this AttestationCore object"; extension-vs-claimedAAGUID matching is its own numbered step (step 8 in the UAF-era procedure). Nothing in any spec mandates that admission-list lookup and anchor lookup read the same field. — https://fidoalliance.org/specs/fido-v2.0-ps-20150904/fido-key-attestation-v2.0-ps-20150904.html
- The Metadata Statement spec defines **three distinct keying schemes** for deriving the model from an attestation: AAGUID extension, `id-fido-gen-ce-aaid`, or `attestationCertificateKeyIdentifier` — used "in the case [where] the trust anchor certificate might cover multiple authenticator models." A verifier can therefore resolve the model (and its anchor set) from the cert while a policy list reads the authData AAGUID, or vice versa. — http://fidoalliance.org/specs/mds/fido-metadata-statement-v3.0-ps-20210518.html
- A trust anchor "can be a root certificate, an intermediate CA certificate **or even the attestation certificate itself**", and for surrogate-basic attestation the anchor array **MUST be empty** ("no attestation trust anchor is required/used") — a spec-legal anchorless class distinct from the end-entity-anchor class that row 10–11 exercised. — http://fidoalliance.org/specs/mds/fido-metadata-statement-v3.0-ps-20210518.html / https://fidoalliance.org/mds-portal-user-guide-for-vendor-users
- The MDS Portal accepts metadata statements for **"FIDO2 Non-CTAP: A protocol that is coupled with WebAuthn APIs and typically backed by a software authenticator"** — software authenticators are certifiable and registrable in MDS as first-class models, so "in MDS" and "software-holdable attestation material" are not mutually exclusive categories. — https://fidoalliance.org/mds-portal-user-guide-for-vendor-users
- Reference verifier behavior diverges on exactly this split: python-fido2 hard-fails on mismatch ("AAGUID in Authenticator data does not match attestation certificate!"), silently passes when the extension is absent (`except x509.ExtensionNotFound: pass`), and decodes the extension by blindly slicing `ext.value.value[2:]` (double-OCTET-STRING assumption). — https://developers.yubico.com/python-fido2/API_Documentation/_modules/fido2/attestation/packed.html
- SimpleWebAuthn only began verifying authData-vs-extension AAGUID agreement in v11.0.0 (#609) — before that release a mismatched split passed a widely deployed verifier — and separately shipped GHSA-6hxq-p678-4hr2 fixing `verifyRegistrationResponse()` accepting "a maliciously-crafted attestation statement's `x5c` … containing a self-signed 'root certificate' instead of chaining back to an RP-specified trust anchor." Real verifiers demonstrably bind anchors to `x5c` rather than to a policy set. — https://github.com/MasterKale/SimpleWebAuthn/blob/master/CHANGELOG.md
- FIDO's own attestation white paper states the AAGUID conveyance "provides no proof of its integrity or authenticity" and "the RP must trust the specific authenticator to provide truthful information" absent signature binding — the spec authors treat the two AAGUID carriers as independent trust objects. — https://fidoalliance.org/fido-attestation-enhancing-trust-privacy-and-interoperability-in-passwordless-authentication
- X.509 encoding of the extension is documented as ambiguous in practice ("the AAGUID MUST be wrapped in two OCTET STRINGS"), which creates a parse-failure-vs-absent distinction most code collapses — a malformed extension may be treated as "not present," silently skipping the match check and switching model derivation to root-based lookup. — https://www.w3.org/TR/webauthn-2 (§8.2.1)
