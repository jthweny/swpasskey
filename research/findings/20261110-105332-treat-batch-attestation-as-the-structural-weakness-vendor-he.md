- The value the flag appears to test is a **key** identifier, not a chain: hex SHA-1 over the bare `subjectPublicKey` BIT STRING — https://fidoalliance.org/specs/mds/fido-metadata-statement-v3.1-ps-20250521.html . Structural consequence: for a model that issues a **per-device** attestation cert, that identifier is that unit's identity, so it is out of scope by the operator's own boundary. Only **batch/shared-cert** models sit inside the scope line. The batch angle and the scope boundary are therefore the same line, not two topics.
- MDS attribution is a **dual namespace**: entries are attributable either by `attestationRootCertificates` or by `attestationCertificateKeyIdentifiers`, and the identifier-only class coincides with `fido-u2f` registrations carrying an all-zero AAGUID — same spec URL. So the identifier namespace is populated predominantly by the older/U2F/batch class, which is precisely the class rows 10–14 show is refused at admission.
- **Row 28 audited end-entity *anchors* only.** It did not ask, for identifier-registered entries, whether the identified cert is *batch-shared* (byte-identical across all units of a model). That is an unaudited property of the same namespace. Unverified.

Not verified for Solo specifically this session.
- FIDO certification economics make the hardware claim a **policy** statement: L1 is open to software (document review), L2 requires a hardware AROE — https://fidoalliance.org/security-certification-authenticator-security-levels , https://fidoalliance.org/fido-certification-fees . If the flag reads metadata `keyProtection` rather than a certificate, then it is a signed *assertion by a vendor* and the batch-key question is downstream of it.
- Microsoft publishes a **monthly, versioned MDS snapshot** — https://learn.microsoft.com/en-us/entra/identity/authentication/concept-fido2-hardware-vendor — which is the only readily diffable MDS history, and therefore the instrument for the staleness question the brief leaves open.

## NEW ANGLES

- **MDS `statusReports` as a material index.** Entries can be flagged `ATTESTATION_KEY_COMPROMISE` — that is a *published* statement that a model's batch attestation key is known-leaked. Enumerate those entries across the snapshot history; they are the only models where batch-key custody is documented as broken, and every one of them is a legitimate candidate under the operator's "documented key extraction" clause.
- **Customer-provisioned leaf keys, specifically.** The materially distinct vendor pattern is not "vendor signs our cert" but "customer holds the leaf private key and the vendor only signs it". Enumerate which FIDO vendors document this (enterprise/OEM attestation programmes: Feitian, G+D, HID, Thales, Nitrokey); a single documented instance gives a conforming leaf key to a non-vendor without any extraction.
- **Reverse the direction of row 28.** Instead of asking whether published anchors are registered leaf keys, ask whether any *registered identifier* has a matching certificate anywhere in public corpora (vendor verification pages, `fido2-token -I` output pasted into libfido2/python-fido2/Chromium issues). Row 28's answer does not cover this direction.
- **Whether `keyProtection` or the certificate is authoritative.** If the flag reads the MDS `keyProtection` field, then a model whose metadata says `hardware` but whose attestation is per-unit is unreachable, while a model whose metadata says `hardware` with a shared batch cert is reachable without any custody problem. Enumerate MDS entries where `keyProtection` contains `hardware` **and** `attestationCertificateKeyIdentifiers` is non-empty — that intersection is the whole search space, and nobody has printed it.
- **Model-gate boundary test using the row-17/row-18 pair.** `f8a011f3` (2019 Security Key) refused, `0f083f18` (2023 Security Key C NFC) admitted: the gate moves with marketing status. Probe every MDS Yubico AAGUID and order the admitted set by MDS `statusReports` certification date to see whether admission correlates with certification recency — a cheap predictor for which model might be admitted next.
