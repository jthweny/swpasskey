## FOUND
- FIDO MDS listing does **not** require FIDO certification: “FIDO Certification is an optional service and is not required for listing your metadata statement” — https://fidoalliance.org/mds-portal-user-guide-for-vendor-users
- MDS listing is a self-service registration (corporate email domain → account → upload statement → Analyzer → Publish → MDS-admin approval → added to global MDS3 BLOB) — https://fidoalliance.org/mds-portal-user-guide-for-vendor-admins ; https://fidoalliance.org/metadata
- FIDO’s own metadata requirements doc states submission to MDS is optional and separate from certification — https://fidoalliance.org/specs/fido-security-requirements/fido-authenticator-metadata-requirements-v1.6-fd-20250312.html
- Certification cost, if we ever want it: Authenticator (Functional) $6,000 member / $9,000 non-member, L1 included; L1+ $7,500 / $13,000; Derivative $1,000 / $1,500 — https://fidoalliance.org/fido-certification-fees ; https://fidoalliance.org/certification/authenticator-certification-levels/authenticator-level-1-2
- There is an MDS-listed **software** authenticator: OpenSK, AAGUID `664d9f67-84a2-412a-9ff7-b4f7d4b7d8ee6d05`, FIDO_CERTIFIED_L1, `keyProtection: Hardware`, `matcherProtection: On Chip`, attestation type **Basic Surrogate**, and its published trust anchor is a **self-signed end-entity** cert (`CN=OpenSK CA`, serial `CF00DDE85DA6216E`, 2020-09-14→2080-09-14, SHA-256 `62:CC:6C:9C:…:21:14`) whose full PEM is readable — https://www.token2.com/tools/fido2-mds/664d9f6784a2412a9ff7b4f7d8ee6d05
- OpenSK’s attestation cert, attestation key and AAGUID are **builder-supplied**, not silicon-bound: `crypto_data/opensk_cert.pem`, `crypto_data/opensk.key`, `crypto_data/aaguid.txt`, injected with `tools/configure.py --certificate --private-key --aaguid`; missing material is regenerated randomly by `setup.sh` — https://raw.githubusercontent.com/google/OpenSK/develop/docs/customization.md ; https://raw.githubusercontent.com/google/OpenSK/develop/tools/configure.py ; https://raw.githubusercontent.com/google/OpenSK/develop/setup.sh
- OpenSK’s repo does **not** commit `crypto_data/` (generated via `tools/gen_key_materials.sh generate_pki`), so Google’s certified anchor key is not in the tree — https://raw.githubusercontent.com/google/OpenSK/develop/tools/gen_key_materials.sh
- Attestation certs are per-**batch**, not per-device, by design: “all YubiKey 5 series devices created within the same production batch possess the same attestation certificate”, and FIDO guidance is ≥100,000 devices per cert — https://developers.yubico.com/Developer_Program/WebAuthn_Starter_Kit/Attestation.html ; Yubico staff: “The attestation certificate is unique per batch, not per model” — https://forum.yubico.com/viewtopicc98c.html?p=9709
- Vendor-side key custody is explicit: Token2 ships RP2350 keys **without** attestation “because Token2 cannot export the private attestation key required by FIDO Alliance”, and its certified keys carry per-key certs issued by Token2’s CA that are also in MDS — https://www.token2.com/pages/token2-pico-rp2350-based-fido2-security-keys ; https://www.token2.com/pages/how-to-verify-your-token2-fido2-key
- A small vendor signs per-device leaves at manufacture and takes custom orders from ~40 units: SoloKeys “each device comes with both a P256 and Ed25519 attestation certificate, unique for the device, signed by our root CA during manufacture… For orders of 40 keys or more and for personalized cases please contact sales@solokeys.com” — https://www.indiegogo.com/en/projects/hadenpatrick/solo-v2-safety-net-against-phishing ; https://solokeys.com/pages/solo-2-guide
- A vendor mints attestation artifacts tied to a **customer’s** identifier on request: Yubico Enterprise Attestation, fw 5.7.4+, only on “custom-programmed keys”, lets an IdP read “the serial number (or other unique identifier specific to the organization)” — https://docs.yubico.com/hardware/yubikey/yk-tech-manual/yk5-firmware-5.7.html ; https://www.yubico.com/press-releases/yubicos-key-product-innovations-empower-enterprise-security-and-phishing-resistant-passwordless-authentication-at-scale
- OEM attestation-key control is a documented product feature at silicon vendors: NXP SE050 “a customer has the possibility to define own attestation keys. Attestation certificates signed by an attestation CA are included in certain SE050 configurations” — https://www.nxp.com/docs/en/data-sheet/SE050-DATASHEET.pdf ; format/commands in https://www.nxp.com/docs/en/application-note/AN13254.pdf
- Infineon’s turnkey FIDO2 Java Card line is sold for OEM customization (“comprehensive customization options”, applet collection incl. FIDO2, Java Card IDE/personalization tools), world-first CTAP2.1 L3+ — https://www.infineon.com/products/security-smart-card-security-solutions/secora-security-solutions/secora-id-key-security-solutions ; https://www.infineon.com/technology-news/2026/ifxtn202607-119
- RPs pin MDS blob versions and refresh on a schedule: Microsoft “ingests the latest version of the FIDO Alliance MDS every month… maximum four-week delay” — https://learn.microsoft.com/en-us/entra/identity/authentication/concept-fido2-hardware-vendor ; an observed deployment pinned BLOB 281 while a newer cert was published in BLOB 127 — https://community.cloudflare.com/t/fido2-security-key-enrollment-fails-with-attestation-certificate-chain-is-not-sign/959209
- New, untested-but-accepted-family model: YubiKey 5 Series fw 5.7.4 AAGUID `ff4dac45-ede8-4ec2-aced-cf66103f4335`, FIDO_CERTIFIED_L2, six root certs incl. Yubico Attestation Root 1 — same Cloudflare thread (same URL as above).
- The MDS3 BLOB is publicly fetchable with no registration or token, so the full anchor set is enumerable offline — https://developers.yubico.com/WebAuthn/Concepts/FIDO_Metadata_Service_(MDS).html

## EXPERIMENTS
1. Genuine-leaf replay (the one untested variable in rows 1–9): register a real YubiKey 5C NFC (fw 5.7.4+) to a local RP with `attestation: direct`, capture `attStmt.x5c[0..n]`, verify `openssl verify` against Yubico Attestation Root 1, then enrol with AAGUID `f4ce5fc0…`, our own credential/attestation key (sig therefore wrong, as in row 3), and that exact genuine leaf+chain as `x5c` | expect: 200 enrolment; `is_non_exportable_hardware_key` true at t+2/10/30 min if the flag is chain-validation-only, false if it is bound to the attesting key | proves: whether the flag is “does it chain to the model’s MDS anchor” or “is the statement signed by the anchor’s key” — this is the discriminator the whole matrix is missing.
2. Same replay using the other accepted family: harvest a **Google Titan v2** (`42b4fb4a…`) attestation object published in any public test corpus, and repeat | expect: same outcome as #1 with a different vendor, confirming vendor-agnostic chain validation | proves: the flag is a property of the chain, not of Yubico-specific cert shape.
3. Self-signed end-entity anchor test (OpenSK): enrol `664d9f67-84a2-412a-9ff7-b4f7d4b7d8ee6d05` with (a) `x5c=[published OpenSK CA PEM]` verbatim, then (b) `x5c=[our leaf, OpenSK CA PEM]` | expect: (a) replicates row 10’s 400 or returns 200/false; (b) 400 | proves: whether the 400 class in rows 10–11 is caused by the anchor being end-entity/self-signed, or by the AAGUID not being in OpenAI’s bundle — separates “model gate” from “anchor shape”.
4. MDS self-listing dry run: build a metadata statement for our own AAGUID (own root in `attestationRootCertificates`, `attestationTypes:["basic_full"]`, `keyProtection:["hardware","secure_element"]`, `authenticatorVersion` matching our `getInfo` firmware 0x050704), upload to the MDS Portal and run **Analyze** only (no Publish) | expect: validation passes with our self-signed root | proves: we can become the vendor of record for our AAGUID for free and without certification; then Publish and test enrolment against that own anchor at t+0/t+1d/t+1w to measure whether OpenAI follows the live BLOB (row-19 hypothesis, zero forgery involved).
5. Bundle-snapshot differential: pick an AAGUID (a) present only in the newest MDS3 BLOB, and (b) one removed/renamed across blobs; enrol each with our self-signed cert | expect: 400 for both if a chain is required regardless of listing; 200/false for listed-only if the gate is a static AAGUID membership test | proves: whether the gate consults MDS membership at all, and whether it is a pinned or live snapshot — directly answers “what exactly is on the accepted list”.
6. Anchor-key-reuse sweep: fetch the MDS3 BLOB, filter entries whose `attestationRootCertificates[0]` is a self-signed end-entity cert (no CA:TRUE) — same shape as OpenSK — then grep open-source authenticator trees (Solo 2 / Nitrokey 3 / Mooltipass / OpenSK forks, all tags/branches) for the private key matching any of those anchor public keys | expect: at least one entry with a published matching key (the class exists for open builds shipping a shared batch key) | proves: a *legitimately held* key can yield a real chain to a real MDS anchor, giving a packed statement whose signature is genuine — no forgery, and it directly tests whether that flips signal 1.
7. Vendor-issuance quote in parallel: email Yubico sales requesting EA-enabled custom-programmed **YubiKey 5C NFC** (accepted AAGUID) at minimum order, and SoloKeys (sales@solokeys.com, ≥40 units) asking whether they will sign a customer-supplied attestation public key under their MDS-listed root for a listed AAGUID | expect: Yubico yes at some MOQ with an org identifier minted into the cert; SoloKeys a firm yes/no on customer-key signing | proves: whether a customer can *legitimately* obtain a vendor-signed leaf (the private key problem disappears if the key is ours), on a model already on the accepted list.
