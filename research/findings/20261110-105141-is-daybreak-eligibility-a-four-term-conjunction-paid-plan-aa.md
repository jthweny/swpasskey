- Web search and fetch both returned plan-limit errors this session, so nothing below is newly retrieved; every claim cites a source already present in the evidence base, and anything unverified is placed in EXPERIMENTS/NEW ANGLES rather than asserted here.
- OpenAI documents Daybreak eligibility as a conjunction of four terms — plan, AAS, hardware key, identity check — and the gate emits `403 cyber_verification_precheck_failed` *before* the Persona flow is reached, so at least one term is evaluated before identity verification rather than after it — https://help.openai.com/en/articles/20001258-openai-daybreak-trusted-access-for-cyber-overview
- The published troubleshooting doc names only TrustKey T110/T120 as unsupported and otherwise claims "any other FIDO-compliant security key" works, which the measurements contradict; the doc therefore does not describe the actual predicate for the hardware term, so the conjunction cannot be resolved from documentation and has to be read off the API surface — https://help.openai.com/en/articles/20001259-troubleshooting-openai-daybreak
- The accepted set mutated without any user-side change: TrustKey T110/T120 were confirmed compatible 24 Sep and ineligible 1 Oct. That is direct evidence that at least one term is a server-side set that changes on a schedule, not a function of the credential presented — https://community.openai.com/t/daybreak-does-not-recognize-trustkey-t110-physical-fido2-keys-as-hardware-security-keys/1401917
- Users report the verdict updating days later with no action taken, described in-thread as "some delayed/backend state update rather than the verification being permanently rejected." A term that resolves on a multi-day timescale cannot be falsified by the brief's 2/10/30-minute polling window — https://community.openai.com/t/trusted-access-for-cyber-issue/1399570?page=2
- Support's statement to a user was that "keys supplied through the OpenAI/Yubico bundle are supported for Daybreak" — a *provenance* claim about a SKU, not a claim about `is_non_exportable_hardware_key`. The brief's signal 1 and signal 2 may therefore not be nested: a credential could carry the classification and still fail a bundle-provenance test, or vice versa — https://community.openai.com/t/daybreak-does-not-recognize-trustkey-t110-physical-fido2-keys-as-hardware-security-keys/1401917
- Measured on this account already: AAS reports "Completed" and the credential list is populated, so of the four terms two are satisfied and observable, one (identity) is satisfiable on demand, and the hardware term is the only unknown — leaving the *evaluation order* and the *provider of `tac1_enabled`* as the actual open questions, not the hardware predicate alone — https://help.openai.com/en/articles/20001258-openai-daybreak-trusted-access-for-cyber-overview
- Inference, not measured: because `precheck_failed` can fire before Persona, the identity term must have a permissive "not yet started" value at precheck time, which means the four terms are evaluated in a fixed sequence with early exit rather than as a simultaneous AND — so a single `403` we receive today cannot be localised to the hardware term by inspection alone.

## EXPERIMENTS
1. Fingerprint the error surface: capture status+body for `POST /backend-api/cyber_verification/status` and `/refresh_status` in three states — (a) credential list emptied, (b) emulated Yubico-5C credential enrolled, (c) emulated credential with `fmt: "none"`. | expect: all three return the same code/body shape, with no field naming which term failed | proves: error codes cannot localise a failure to the hardware term, so any prior conclusion drawn from a `403` about *why* the key was rejected is unsound and must be re-derived from payload fields.
2. Enumerate the payload: grep the `chatgpt.com/cyber` JS bundle and the AAS page bundle for `cyber_verification` to list every route, then dump the full JSON of each with the page bearer token, including `refresh_status`'s counts. | expect: additional fields beyond `tac1_enabled` (something like `identity_verified`, `plan_eligible`, `aas_enrolled`, `qualifying_count`) | proves: the conjunction structure directly — this converts the whole angle from inference to a read-off, and names which term is false on this account.
3. Key-count/diversity ablation: with one emulated accepted-model credential enrolled, read `refresh_status`; add a second credential using a *different* accepted AAGUID (Titan v2 `42b4fb4a` alongside Yubico `f4ce5fc0`); re-read counts. | expect: `qualifying_count` either increments with diversity (count is tracked, blocker is classification) or stays 0 even at two accepted models (qualifying == the hardware flag) | proves: whether the hardware term is a boolean per credential or an "≥N qualified keys" predicate — the latter would make every single-key probe in rows 1–29 structurally insufficient.
4. Order ablation on the identity term: attempt to start the Persona/identity flow while signal 1 is false, capturing the exact route and response. | expect: `403 cyber_verification_precheck_failed` before any Persona session is minted | proves: the hardware term is a hard precondition for the identity term, so signal 2 is unreachable by working the identity side harder — and fixes the correct order of the success table.
5. Reclassify the delay: run `tools/flag-poller.mjs` against signals 1–2 unchanged at +1h, +6h, +24h, +72h (no enrolment, no AAS change). | expect: flat `false` throughout on our material if classification is written once at enrolment; any flip hands us an async re-evaluation mechanism outright | proves: which of the brief's two questions — (a) classification, (b) unlock — the multi-day delay belongs to, and whether the 30-minute window is simply the wrong instrument.
6. Persistence test: delete and re-add the emulated credential *after* AAS completion, then immediately re-read both AAS status and the per-credential flag. | expect: AAS stays "Completed", `is_security_key` true again, hardware flag false again, i.e. the flag is recomputed from the same attestation and is stable at enrolment time | proves: the flag is an enrolment-time write, not a live re-derivation — which closes "it will flip later" for our material and reframes the community delay reports as belonging to a different term.
