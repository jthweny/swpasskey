## FOUND

- Every one of the 29 rows was submitted with the *same three* client-declared values, hardcoded, never varied: `authenticatorAttachment: "cross-platform"` (JS literal), `getTransports: () => ["usb"]` (JS literal), and `clientExtensionResults.credProps = {rk: true}` (unconditionally returned by `create_extension_results`) — /Users/adminuser/VirtualYubi/swpasskey/tools/browser-bridge/bridge.js, tools/browser-bridge/bridge_server.py
- `toJSON()` serialises exactly `{id, rawId, type, authenticatorAttachment, clientExtensionResults, response{clientDataJSON, attestationObject, transports}}` — so `transports` and `authenticatorAttachment` have been on the wire in all 29 rows, and nothing else about the client has — tools/browser-bridge/bridge.js
- `["usb"]` alone is *not* the honest transport list for any accepted model: WebAuthn `transports` is the client's rendering of CTAP2 `authenticatorGetInfo.transports`, and an NFC-capable key reports `["usb","nfc"]` — https://w3c.github.io/webauthn/#dom-authenticatorattestationresponse-gettransports , https://fidoalliance.org/specs/fido-v2.1-ps-20210615/fido-client-to-authenticator-protocol-v2.1-ps-20210615.html#sctn-authenticator-get-info
- The expected value per AAGUID is *published*: MDS 3.1 carries `authenticatorGetInfo` (`transports`, `options` incl. `plat`) per entry, so `["usb","nfc"]` vs `["usb"]` is checkable per accepted model without touching the network — https://fidoalliance.org/specs/mds/fido-metadata-statement-v3.1-ps-20250521.html
- `authenticatorAttachment` is spec-defined as `"platform" | "cross-platform" | null` and is a *client* assertion about the authenticator, indistinguishable at the RP from the other client-chosen fields — https://w3c.github.io/webauthn/#dom-publickeycredential-authenticatorattachment
- `credProps` is a pure client extension whose only output is `{rk: boolean}`; there is no server-verifiable evidence behind it — https://w3c.github.io/webauthn/#sctn-credprops
- The authenticatorData we already send is `flags=0x45` = UP|UV|AT, with **BE clear and BS clear** — i.e. the credential already declares itself non-backup-eligible and single-device, which is the WebAuthn-native meaning of "non-exportable". The hardware flag is false anyway, so backup-eligibility is not the missing input (kills that hypothesis before it costs a run) — tools/browser-bridge/bridge_server.py (`flags=0x%02x` print, `parse_auth_data`)
- `response.getPublicKey()` / `getAuthenticatorData()` exist on the bridge's credential object but are **not** in `toJSON()`, so the RP has never received them — tools/browser-bridge/bridge.js
- `transports` is *stored* by specification-compliant frontends: SimpleWebAuthn's `startRegistration` copies `credential.response.getTransports?.()` into `response.transports` and `credential.authenticatorAttachment` when non-null — https://github.com/MasterKale/SimpleWebAuthn/tree/master/packages/browser (shape not fetch-verified this pass; Tavily quota was exhausted, so confirm against the pinned version in the page bundle)
- FIDO `attestationTypes` distinguishes `basic_full` (per-device certs) from **`basic_surrogate`** (batch/surrogate certs, shared across units) — the class where legitimate attestation material is not device-unique, i.e. the only class a non-vendor could plausibly hold — https://fidoalliance.org/specs/mds/fido-metadata-statement-v3.1-ps-20250521.html#attestation-type-enum
- The gate's error channel is typed and attributable: refused enrolments return `400 passkey_verification_failed`, so a *schema* rejection (bad enum) is distinguishable from a *model* rejection by body text — tools/probe.sh, brief row 10
- Prior support precedent that OpenAI states bundle-bound rules to users in writing, which makes an organisational ask a live avenue rather than a dead end — https://community.openai.com/t/daybreak-does-not-recognize-trustkey-t110-physical-fido2-keys-as-hardware-security-keys/1401917

## EXPERIMENTS

1. **Read-back oracle (5 min, no enrolment).** `curl` `/api/accounts/advanced-account-security/passkeys` and pipe the *whole* entry through `jq .`; separately start a sign-in and capture the `allowCredentials[].transports` the server sends back. | expect: either a `transports` field echoed as `["usb"]`, or its absence | proves: whether the RP stores/consumes `transports` at all — if absent, this whole angle closes in one call for free, and if present you have a live input *and* a read-back channel.

2. **Enum-liveness probe.** Two separate runs: (a) `transports: ["banana"]`, (b) `authenticatorAttachment: "banana"`. | expect: `400` with a schema/parse message for each | proves: strict parsing exists → the field is a genuine input, not silently stripped. `200` on either means unknown-field stripping and closes that field.

3. **MDS-consistent transports (the actual test).** Read `authenticatorGetInfo.transports` for `f4ce5fc0`, `d7781e5d`, `a25342c0`, `0f083f18`, `42b4fb4a` from the local MDS cache; add `window.__SWPK_TRANSPORTS` (one line: `getTransports: () => (window.__SWPK_TRANSPORTS || ["usb"])`) and enrol with the exact published list, then poll flag at t+2/10/30 min. | expect: `["usb","nfc"]` on the NFC models either flips the flag or changes the admission/label vs the `["usb"]` baseline | proves: whether the verifier cross-checks client transports against the AAGUID's MDS `authenticatorGetInfo`, in the same spirit as the row-23 AAGUID cross-check.

4. **Attachment matrix.** Four runs: `"cross-platform"` (baseline), `"platform"`, `null`, omitted entirely. | expect: omitted/`null` → `400` if the field is required; `"platform"` → `200` with hw still false (or a downgraded name like "Passkey") | proves: whether attachment gates hardware eligibility, and whether it is *required* input. Note the baseline already being `"cross-platform"` proves attachment is not *sufficient*.

5. **credProps inversion.** Enrol with `clientExtensionResults: {}`, then with `{credProps:{rk:false}}` while the daemon still creates a discoverable credential (`options={"rk":True}`). | expect: `rk:false` → either `400`, or the credential absent from the list, or listed hw-false | proves: whether `credProps` is read by the classifier or only by the UI.

6. **Assertion-path re-evaluation (highest value for "flips days later").** Sign in twice with the existing credential, patching the daemon so `signCount` increments 1→2→3 and BE/BS stay clear; call `POST /backend-api/cyber_verification/refresh_status` after each; poll the flag at t+2/10/30 min. | expect: a flip to `true` (classification runs on the assertion path and depends on monotonic signCount / BE-BS consistency) or no change (registration-time evaluation only) | proves: *where and when* classification is computed — the mechanism behind the reported late verdicts, independent of attestation.

7. **refresh_status vs per-credential disagreement.** Capture the page's bearer token via Playwright/CDP and call `refresh_status` before and after each of experiments 3–6 in the same session. | expect: `qualifying_count` unchanged while a per-credential flag moves (or vice versa) | proves: whether the two signals are computed by the same evaluator, and gives an early oracle that resolves in minutes instead of days.
