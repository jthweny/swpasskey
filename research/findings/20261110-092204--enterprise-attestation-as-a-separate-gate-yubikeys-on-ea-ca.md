## FOUND
- WebAuthn L2 §5.4.7 `AttestationConveyancePreference.enterprise`: "User agents MUST NOT provide such an attestation unless the user agent or authenticator configuration permits it for the requested RP ID. If permitted, the user agent SHOULD signal to the authenticator (at invocation time) that enterprise attestation is requested, and convey the resulting AAGUID and attestation statement, **unaltered**, to the Relying Party" — the EA channel is a per-RP-ID client configuration gate, and its output to the RP is the attestation statement itself — https://www.w3.org/TR/webauthn-2
- The `create()` algorithm sets "enterpriseAttestationPossible be `true` if the user agent wishes to support enterprise attestation for `options.rp.id`", else `false` — i.e. the *client*, not the RP or the authenticator, decides per RP ID — https://www.w3.org/TR/webauthn-2
- There is **no** `enterpriseAttestation` WebAuthn extension: WebAuthn's registered extensions are appid/appidExclude/uvm/credProps/etc., and MDN's extension reference contains no such entry; EA is expressed only through the `attestation` preference — so `getClientExtensionResults().enterpriseAttestation` has no spec-defined existence, and any server check on that name would be reading a nonstandard key of `clientExtensionResults` (which the JSON form is required to carry verbatim) — https://www.rfc-editor.org/info/rfc8809 , https://developer.mozilla.org/en-US/docs/Web/API/Web_Authentication_API/WebAuthn_extensions , https://www.w3.org/TR/webauthn-3
- CTAP2.1/2.2 `authenticatorMakeCredential` takes a top-level `enterpriseAttestation (0x0A)` Unsigned Integer parameter; an EA-capable authenticator signals via the `ep` Option ID in `authenticatorGetInfo`, and platforms check `ep` before ever sending 0x0A — so EA capability and EA request are both observable at the CTAP layer by our daemon — https://fidoalliance.org/specs/fido-v2.2-ps-20250714/fido-client-to-authenticator-protocol-v2.2-ps-20250714.html
- CTAP EA semantics: value 1 = vendor-facilitated (EA only for a non-updateable, vendor-burned RP ID list; "If enterprise attestation is requested for any RP ID other than the pre-configured RP ID(s), the attestation returned … is a regular privacy-preserving attestation"); value 2 = platform-managed (returns EA for platform-vetted RP IDs; vendor-facilitated-only authenticators MAY treat 2 as 1) — https://fidoalliance.org/specs/fido-v2.1-ps-20210615/fido-client-to-authenticator-protocol-v2.1-ps-20210615.html
- `authenticatorReset` disables the EA feature; it is re-enabled via `authenticatorConfig`'s enable-enterprise-attestation subcommand — https://fidoalliance.org/specs/fido-v2.1-ps-20210615/fido-client-to-authenticator-protocol-v2.1-ps-errata-20220621.pdf
- Chrome's behaviour table (chromium.org): webauthn `"enterprise"` with RP ID **not** listed → "Same as for `direct`"; RP ID listed in `SecurityKeyPermitAttestation` policy → "Attestation from device is returned (with 'individual attestation' hint sent to the device)" — the *only* delta EA makes toward the RP-visible statement is the hint to the device, and it is gated per RP ID — https://www.chromium.org/security-keys
- The per-RP-ID gate is **user-controllable without enterprise policy**: chrome://flags `web-authentication-permit-enterprise-attestation` is an `ORIGIN_LIST_VALUE_TYPE` flag plus a `kPermitEnterpriseAttestationOriginList` command-line switch ("a switch and associated UI flag that lets a user permit individual attestation on a per-origin basis"); vendor docs instruct adding "the full domain name including the HTTPS prefix" — so `https://chatgpt.com` can be EA-permitted on our own Chrome — https://chromium.googlesource.com/chromium/src/+/4c6070768bab73dc25a4a8d1c0e31db761624174%5E%21 , https://developers.yubico.com/WebAuthn/Concepts/Enterprise_Attestation/Getting_Started.html , https://docs.intercede.com/Public/CMS/Release/12.16/Enterprise/Content/Passkey%20Integration%20Guide/Enterprise%20attestation/Enabling%20platform-managed%20EA%20in%20Chrome.htm
- Chrome actively classifies "individually identifying certificates" (e.g. issuer `FT FIDO 0100`): such certs are stripped to "an empty, 'none' attestation in webauthn—even when direct attestation is requested" — Chrome maintains a concrete notion of which attestation certs are per-device — https://www.chromium.org/security-keys
- Yubico EA exists only on **custom-programmed** (enterprise-programme) YubiKeys on firmware ≥ 5.7(.4): the per-device certificate carries the serial in the subject DN and in extension `1.3.6.1.4.1.45724.1.1.2`; both CN-regex and OID extraction are documented — this is the exact artifact shape an "EA gate" could key on — https://developers.yubico.com/WebAuthn/Concepts/Enterprise_Attestation/Getting_Started.html , https://docs.yubico.com/hardware/yubikey/yk-tech-manual/yk5-firmware-5.7.html
- Yubico: "authenticators which support Enterprise Attestation are not available to consumers" — a real EA YubiKey is not a retail purchase, and even one would only EA-attest to its burned-in RP IDs — https://developers.yubico.com/WebAuthn/Concepts/WebAuthn_Level_2_Features_and_Enhancements.html
- **FIDO itself publishes EA attestation material including the private key**: the official conformance-test-tools-resources repo gives the "FIDO2 Enterprise Attestation TEST ROOT1" chain, the "FIDO2 Enterprise Attestation BATCH KEY prime256v1" certificate, **and its EC private key**, with test RP ID list `enterprisetest.certinfra.fidoalliance.org, ep.fidoalliance.co.nz` — a genuine vendor-signed EA-format chain a software authenticator can legitimately hold and sign with — https://github.com/fido-alliance/conformance-test-tools-resources/blob/main/docs/FIDO2/Authenticator/README.md
- The FIDO conformance tool ships a "Download Test Metadata" bundle (test AAGUIDs + these roots) that imports as standard `MetadataBLOBPayload` — meaning test AAGUIDs and test anchors exist in MDS-format entries — https://github.com/Yubico/java-webauthn-server/discussions/437 , sample AAGUID `0132d110-bf4e-4208-a403-ab4f5f12efe5` ("FIDO Alliance Sample FIDO2 Authenticator") — http://fidoalliance.org/specs/mds/fido-metadata-statement-v3.0-ps-20210518.html
- FIDO attestation white paper §4.5: EA "binds a unique authenticator key pair to a serial number or equivalent unique identifier"; baseline FIDO explicitly prohibits uniquely identifying attestation — per-device shape is a *deliberate, recognizable class* of attestation — https://fidoalliance.org/fido-attestation-enhancing-trust-privacy-and-interoperability-in-passwordless-authentication
- Adam Langley: the EA certificate is returned only "if the security key has an enterprise attestation certificate, and if the request meets at least one of the two requirements" (burned-in RP ID match, or platform config) — both conditions are testable locally with the daemon — https://www.imperialviolet.org/tourofwebauthn/tourofwebauthn.html
- Browser landscape on macOS: Chrome works with the flag/origin-list config; Firefox has no EA; Safari 18.3 with an EA key and no RP ID config "behaved similarly to `direct`" (per vendor test notes, unconfirmed) — a second, differently-gating client is available for A/B — https://www.yubion.com/en/blog/fido2-enterprise-attestation-technical-deep-dive
- EA per-device leaves are themselves pinned in MDS: platform-managed EA assumes "devices … manufactured with an attestation certificate that is available in the online global MDS3 FIDO Alliance metadata", i.e. listed by `attestationCertificateKeyIdentifiers` — so a verifier can require *leaf identity*, not just chain shape — https://docs.intercede.com/Public/CMS/Release/12.16/Enterprise/Content/Passkey%20Integration%20Guide/Enterprise%20attestation/Enabling%20platform-managed%20EA%20in%20Chrome.htm

## EXPERIMENTS
1. Bridge injects a pre-page shim wrapping `navigator.credentials.create` to log `options.attestation`, `options.extensions`, `rp.id`, while the daemon dumps each `authenticatorMakeCredential` (0x0A presence/value, extensions map) during a normal enrolment on the "Add a hardware security key" page | expect: `attestation` is `"none"`/`"direct"` and no 0x0A arrives on stock Chrome | proves: whether OpenAI's client requests EA conveyance at all — the upstream precondition of the whole EA-gate theory; a logged `"enterprise"` immediately elevates it.
2. Enable `chrome://flags/#web-authentication-permit-enterprise-attestation` with origin `https://chatgpt.com` (or relaunch Chrome with `--permit-enterprise-attestation-origin-list=https://chatgpt.com`), add `ep: true` to the daemon's `authenticatorGetInfo`, repeat experiment 1 and log 0x0A | expect: 0x0A=2 at the daemon if the RP uses `"enterprise"` (or if Chrome emits the individual-attestation hint for listed origins under `"direct"` per its behaviour table); absent otherwise | proves: the EA signalling channel can be driven end-to-end against chatgpt.com from our side, and acts as a conveyance oracle independent of page JS.
3. Mint an EA-shaped per-device leaf on accepted AAGUID `d7781e5d`: subject DN `CN=<decimal serial>`, extension `1.3.6.1.4.1.45724.1.1.2` = serial, returned only when 0x0A present (full vendor-facilitated emulation); variant B signs the leaf with FIDO's published EP batch key chained to "FIDO2 Enterprise Attestation TEST ROOT1". Re-query signals 1–2 at t+2/10/30 | expect: 200 with flag false under the anchor model; first `true` in nine attempts if the flag keys off uniquely-identifying attestation artifacts | proves: whether EA-class (per-device) attestation shape is signal 1's discriminator — the one variable rows 1–9 never presented.
4. Userscript patches `PublicKeyCredential.prototype.getClientExtensionResults` and `toJSON` to inject `enterpriseAttestation: true` (variant: base64url SHA-256 of `chatgpt.com`) into `clientExtensionResults` before OpenAI's script reads it; enrol with accepted AAGUID and the usual chain | expect: flag false | proves: directly falsifies (or confirms) the `getClientExtensionResults().enterpriseAttestation` mechanism — if `true`, signal 1 is driven by client JSON and is forgeable from the page.
5. Accepted-AAGUID enrolment with authenticator extension output `{"enterpriseAttestation": true}` CBOR inside authData's ED block | expect: 200, flag false | proves: whether the verifier parses authenticator extension output — a 400 would prove strict ED inspection (a new verifier fact), a `true` would prove an ED marker is the gate.
6. Enrol claiming the FIDO conformance sample AAGUID `0132d110-bf4e-4208-a403-ab4f5f12efe5` with the published EP certificate chain (real signatures under the published key) | expect: 400 `passkey_verification_failed` from the model gate | proves: whether OpenAI's accepted-model bundle contains FIDO conformance entries; a 200 instantly yields a flag test where the chain is signed by a key any software authenticator may legitimately hold.
