## FOUND
- `attestationCertificateKeyIdentifiers` is a **parallel attribution namespace keyed on the leaf's key, not the model**: hex-encoded RFC 5280 §4.2.1.2 *method 1* keyIdentifier, i.e. SHA-1 over the value of the `subjectPublicKey` BIT STRING excluding tag, length and unused-bits count — https://fidoalliance.org/specs/mds/fido-metadata-statement-v3.1-ps-20250521.html , https://www.rfc-editor.org/rfc/rfc5280#section-4.2.1.2
- The namespace exists because `fido-u2f` registrations carry an **all-zero AAGUID** (U2F has no AAGUID to publish), so those entries are addressable *only* by certificate key id — https://fidoalliance.org/specs/mds/fido-metadata-statement-v3.1-ps-20250521.html
- Consequence for our target: a verifier doing MDS attribution by SKI cannot use the AAGUID as its input, because the input is zero. Any `zero-AAGUID` credential therefore **cannot be refused by an AAGUID-keyed model gate** (rows 10–19 behaviour) — it either falls through to the SKI lookup or fails closed as "unknown". That branch is unreachable by every shape in rows 1–29, all of which carried a real AAGUID.
- `fido-u2f` is the one WebAuthn attestation format **never measured here** (rows cover `packed`, `none`, `tpm` ×2, `apple`). Its verification base string is `0x00 ‖ rpIdHash ‖ clientDataHash ‖ credentialId ‖ publicKeyU2F`, DER-encoded as the signed message, and the attested-credential-data AAGUID is required to be all zeroes — https://www.w3.org/TR/webauthn-3/#sect-fido-u2f-attestation
- Because row 3 established `attStmt.sig` is not verified, the only thing `fido-u2f` must satisfy to be *parsed* is format shape: `x5c` present, zero AAGUID, optional `id-fido-gen-ce-aaguid` absent. Format adoption, not cryptography, is the variable.
- The distinct new hypothesis this opens: an SKI lookup is a **string match on an identifier the client supplies inside a certificate**, not a signature check. Two implementations are indistinguishable for genuine devices yet wildly different for us — (a) recompute SHA-1 over the presented SPKI (row 28's model, unfalsifiable without a key), (b) read the leaf's `subjectKeyIdentifier` extension (`2.5.29.14`) and use it directly. Genuine U2F leaves set the extension *to* that same hash, so no vendor chain is required to satisfy (b) — only a chosen 20-byte value.
- MDS 3.x statements carry `keyProtection`, `matcherProtection`, `attestationTypes` per entry, so if a spoofed identifier selects an entry, the hardware classification is decided from **that entry's metadata**, independent of chain — https://fidoalliance.org/specs/mds/fido-metadata-statement-v3.1-ps-20250521.html
- Tooling note: `web_search` and `web_fetch` both returned plan-quota errors this pass, so nothing above is a paraphrase of a page I could not open — it is spec text and the prior digest, and every enumerable claim is converted into a local measurement below.

## NEW ANGLES
- Formalise the SKI implementation-bug matrix and test each variant with one probe arm: (i) SHA-1 of full certificate DER, (ii) `subjectKeyIdentifier` extension passthrough, (iii) SHA-1 over the SPKI *including* the BIT STRING header bytes, (iv) SHA-1 over subject DN, (v) match on `authorityKeyIdentifier` instead. Each variant that hits is a forgery-free acceptance and invalidates row 28's "unpublished material" conclusion rather than contradicting it.
- Cross-corpus SKI search, which row 28 never did: it compared MDS anchors against MDS identifier lists (1102 × set, internal). Compare the *union of all* `attestationCertificateKeyIdentifiers` against certs published outside the MDS — vendor U2F attestation CA docs, FIDO U2F interoperability tooling, `u2f-ref-code` test material, old firmware-source attestation fixtures from software-first vendors (SoloKeys, Nitrokey, Pico FIDO), and any repo shipping an attestation cert *with* its key. A single hit is a legitimate private key for a registered leaf.
- Zero-AAGUID as a gate bypass in its own right, format-independent: does the admission gate treat `00000000-…` as "no model to gate on" and defer to chain/format, or refuse it? Test with `fmt: none` and zero AAGUID first (cheapest arm, no cert at all) to read the gate's answer before spending an attestation shape on it.
- Fingerprint the verifier stack from its error strings and parse behaviour: send an x5c whose leaf has an unparseable `subjectKeyIdentifier`, a duplicate `aaguid` extension, and a cert with `subjectKeyIdentifier` present but empty — the specific failure modes name the library (python-fido2, java-webauthn-server, Duo, custom Go), which decides whether the extension passthrough is even plausible.
- MDS `attestationTypes` of the zero-AAGUID hardware entries: if any is `basic_surrogate` or `attestation_basic_full` *without* a chain, the entry is documented as not requiring proof of possession, and the flag would be reachable by metadata alone — enumerate this class before minting anything else.

Re-run the accepted-set survey (`f8a011f3`, `2fc0579f`, `4599062e`, `0f083f18`) once per week and log the blob `no` alongside each result, so any future addition to the hardware list is caught within one cycle instead of re-derived.
