## FOUND
- Surrogate basic attestation is defined as: the authenticator has no attestation key and self-signs the attestation message with the authentication (= credential) key — `basic_surrogate` ≡ WebAuthn packed self-attestation (`x5c` absent), the one attestation form verifiable with zero vendor material — https://fidoalliance.org/specs/fido-v2.0-ps-20150904/fido-key-attestation-v2.0-ps-20150904.html
- python-fido2's packed verifier branches exactly on `x5c`: present → `AttestationType.BASIC` + `_validate_packed_cert(cert, aaguid)`; absent → `AttestationType.SELF`, sig verified against the credential public key taken from authData — https://developers.yubico.com/python-fido2/API_Documentation/_modules/fido2/attestation/packed.html
- WebAuthn §8.2 defines three outcomes for the `x5c`-present branch: "Basic, AttCA **or uncertainty**", and a distinct `x5c`-absent self-attestation branch validated with `credentialPublicKey` — rows 1–20 never targeted the self-attestation branch or the "uncertainty" outcome — https://www.w3.org/TR/webauthn-2
- Registry codes: `basic_full` 0x3E07 (15879), `basic_surrogate` 0x3E08 (15880), ECDAA 0x3E09, `attca` 0x3E0A = PrivacyCA attestation per TCG CMC AIKCertEnroll, `anonca` 0x3E0C — https://fidoalliance.org/specs/common-specs/fido-registry-v2.2-rd-20210525.html
- MDS Portal User Guide: "When supporting surrogate basic attestation only, no attestation trust anchor is required/used, so you just need to update the metadata statement with no certificates specified" — surrogate-only vendors publish zero anchors by design — https://fidoalliance.org/mds-portal-user-guide-for-vendor-users
- MDS census: `basic_full` 475, `basic_surrogate` 36, `attca` 2; exactly three entries carry no root certificates at all, all `basic_surrogate`: Windows Hello Software Authenticator, TruU, Sherlocked — https://github.com/sebadob/rauthy/issues/1618
- Windows Hello Software Authenticator (`6028b017-b1d4-4c02-b4b3-afcdafc96bb2`) MDS entry: Attestation "Basic Surrogate", Key protection "Software", FIDO_CERTIFIED_L1, zero anchors — the minimal anchorless surrogate entry — https://www.token2.com/tools/fido2-mds/6028b017b1d44c02b4b3afcdafc96bb2
- Windows Hello Hardware Authenticator (`08987058-cadc-4b81-b6e1-30de50dcbe96`) declares `attestationTypes: [15879, 15880]` = `basic_full` + `basic_surrogate` in one entry — models may declare the chainless type even while publishing anchors — https://github.com/web-auth/webauthn-framework/issues/151
- That entry's only attestation root is "Microsoft TPM Root Certificate Authority 2014" — unreachable to us, yet its declared surrogate path requires none — https://www.token2.com/tools/fido2-mds/08987058cadc4b81b6e130de50dcbe96
- Microsoft treats the Hello AAGUIDs as a protection-class map: `08987058…` (TPM) and `9ddd1817…` (VBS/TPM) = hardware-backed, policy-targetable as high-assurance; `6028b017…` (software) explicitly excludable — precedent that hardware classification is a per-AAGUID metadata property — https://learn.microsoft.com/en-us/entra/identity/authentication/how-to-authentication-entra-passkeys-on-windows
- Entra's published vendor gate mirrors the suspected OpenAI split: "Enforced" = valid packed + full chain to MDS roots; "Not enforced" = `none` / `tpm` / `packed` (AttCA) / custom fmt ≤32 chars — a major verifier whose admission list includes chainless and AttCA-shaped statements — https://learn.microsoft.com/en-us/entra/identity/authentication/concept-fido2-hardware-vendor
- The same Entra table lists "TruU FIDO2 Authenticator | bb878d7b-cf54-4784-b390-357030497043" as an MDS model — confirms row 14's AAGUID string and that TruU is a vendor-registered entry — https://learn.microsoft.com/en-us/entra/identity/authentication/concept-fido2-hardware-vendor
- The third anchorless surrogate entry is "Sherlocked Passkey Provider (iOS) - Stashword Inc.", AAGUID `e8b7f4a2c3d5e6f7890ab1c2d3e4f567`, Not FIDO Certified — https://www.token2.com/tools/fido2-mds
- Apple's platform entry (`f24a8e70-d0d3-f82c-2937-32523cc4de5a`) declares `attestationTypes: [15882]` = `attca` (0x3E0A) — the two `attca` MDS entries are platform models reachable through the same MDS lookup — https://docs.veridiumid.com/docs/v3.9.1/fido-platform-authenticators
- Genuine physical FIDO2 keys outside the accepted set (TrustKey T110/T120) enrol fine but are labelled "Passkey" and fail the Daybreak hardware gate — real hardware construction does not imply the flag — https://community.openai.com/t/daybreak-does-not-recognize-trustkey-t110-physical-fido2-keys-as-hardware-security-keys/1401917
- A second TrustKey T120 datapoint confirms it reproducibly, and OpenAI staff replied that T110/T120 "aren't currently supported for individual Daybreak access" — the gate is per-model and OpenAI maintains a support-visible qualifying list — https://community.openai.com/t/daybreak-trustkey-t110-t120-confirmed-ineligible-compatibility-requirements-were-clarified-too-late/1402777
- Published gate wording: eligible paid plan + Advanced Account Security + "at least one compatible FIDO2 hardware security key"; "A software or synced passkey cannot satisfy the hardware-key requirement" — "compatible" is the undefined term — https://help.openai.com/en/articles/20001258-openai-daybreak-trusted-access-for-cyber-overview
- Yubico's Daybreak announcement adds a second, stricter condition: "Hardware keys must be the user's only registered login methods" — conflicts with the help center's "You can keep your other passkeys" — https://www.yubico.com/blog/openai-daybreak-signals-a-new-era-for-ai-security-and-the-critical-role-of-hardware-security-keys
- Support told one user the effective requirement is two physical hardware keys with software passkeys removed — three mutually inconsistent published criteria, so `tac1_enabled` may have non-credential preconditions (key count, method mix) — https://community.openai.com/t/trusted-access-for-cyber-issue/1399570
- A practitioner writeup documents the full attestation-statement forgery surface (authData assembly, `fmt:"none"` accepted with a valid ECDSA sig over authData‖clientDataHash, credential-key extraction) — reference corpus of verifier-side edge cases — https://nullpt.rs/forging-passkeys
