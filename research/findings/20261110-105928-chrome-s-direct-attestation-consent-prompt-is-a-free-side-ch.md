## FOUND

- (method note — no claim below was re-fetched this session: both `web_search` and `web_fetch` returned "exceeds your plan's set usage limit" on every attempt. Items marked *confirm path* are from source-tree memory and are deliberately written so the experiments verify them rather than depend on them.)
- The client is *required in practice* to throw away the authenticator's attestation when conveyance is `none`: WebAuthn L2 defines the "none" attestation statement as `{fmt:"none", attStmt:{}, authData}` and §5.4.7 says the client replaces the authenticator's statement with it when the RP asked for `none` — https://www.w3.org/TR/webauthn-2/#sctn-none-attestation , https://www.w3.org/TR/webauthn-2/#sctn-createCredential
- The requested conveyance is a plain JS-readable field on the RP's own options object (`PublicKeyCredentialCreationOptions.attestation`, values `"none" | "indirect" | "direct" | "enterprise"`), so the RP's intent is observable without any side channel — https://www.w3.org/TR/webauthn-2/#dom-publickeycredentialcreationoptions-attestation
- Chrome implements that strip in the CTAP layer (request carries `attestation` = none/direct/enterprise and `enterpriseAttestation` = 1/2/3; response is rewritten to `none` when the preference is `none`) — https://source.chromium.org/chromium/chromium/src/+/main:device/fido/ctap_authenticator.cc (*confirm path*), spec side: https://fidoalliance.org/specs/fido-v2.1-ps-20210615/fido-client-to-authenticator-protocol-v2.1-ps-20210615.html#makecredential
- Chrome gates direct attestation behind a per-origin permission, implemented as its own content setting with a request sheet wired through the WebAuthn delegate — https://source.chromium.org/chromium/chromium/src/+/main:chrome/browser/webauthn/attestation_permission_context.cc (*confirm path*), https://source.chromium.org/chromium/chromium/src/+/main:chrome/browser/webauthn/chrome_authenticator_request_delegate.cc (*confirm path*)
- Consequence that matters here: a prior grant or a policy-supplied allowlist suppresses the sheet silently, so "no prompt appeared" is not evidence that `direct` was requested — the permission state must be read, not inferred. Fresh-profile runs are the only clean read.
- The macOS platform authenticator path in Chrome always emits `fmt:"apple"` with the nonce extension `1.2.840.113635.100.8.2 = SHA-256(authData‖clientDataHash)` and cannot be made to emit `packed`, which is why row 29's shape had to be hand-built — https://source.chromium.org/chromium/chromium/src/+/main:device/fido/mac/touch_id_authenticator.mm (*confirm path*)
- Chromium ships its own virtual authenticator that does honour the requested attestation preference, i.e. a fourth client pipeline distinct from the local bridge — https://source.chromium.org/chromium/chromium/src/+/main:content/browser/webauth/virtual_fido_authenticator.cc (*confirm path*, https://chromium.googlesource.com/chromium/src/+/main/content/browser/webauth/ for the directory)
- Chrome has historically had a policy that pre-grants attestation disclosure for listed origins (`SecurityKeyPermitAttestation`), with a separate enterprise-attestation allowlist existing in later builds; the live policy set in this Chrome build is enumerable offline at `chrome://policy` — https://chromeenterprise.google/policies/ (do not assume either name; export the list)
- Because `authData` (and therefore the AAGUID Chrome passes through unchanged) survives a `none` rewrite, the admission findings in rows 10–27 remain sound even under the strip hypothesis; only the *attStmt-material* findings (rows 1–9, 12, 15–16, 21–22, 25, 29) are at risk of having measured Chrome rather than OpenAI.

1. ## NEW ANGLES

- Firefox as a second client whose direct-attestation path can be forced without the shim (there is a testing pref of the form `security.webauth.webauthn_testing_allow_direct_attestation` — verify the exact key in this build); a `packed` statement from Firefox with a real `direct` conveyance is the cheapest clean re-test of the strip hypothesis.

- Whether `enterpriseAttestation` value 1/2/3 ever appears in the CTAP request from OpenAI; if it does, the RP-side EA configuration is a new observable, and EA authenticity rules in the spec differ from plain `packed`.
- If the strip is confirmed, the flag's remaining inputs are the AAGUID and the credential's subject public key — worth re-deriving signal 1 against a *single accepted AAGUID with two different generated key pairs* to see whether anything key-dependent moves at all.
- Chrome's virtual authenticator bypasses the consent sheet and the HID layer entirely; if the CDP path ever flips signal 1 it means the server sees something the bridge cannot produce, and the delta between the two pipelines is diagnosable byte-for-byte.
