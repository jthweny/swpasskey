## FOUND

- OpenAI's bundle is two co-branded, *custom-configured* SKUs — "YubiKey C NFC – OpenAI" and "YubiKey C Nano – OpenAI" — sold through Yubico with "OTP support" removed, i.e. an OEM configuration pass exists in this relationship, which is the same channel vendor-facilitated EA rides on — https://openai.com/index/advanced-account-security · https://help.openai.com/en/articles/20001269-openai-yubico-yubikey-bundle · https://investors.yubico.com/en/openai-and-yubico-partner-to-bring-custom-phishing-resistant-yubikeys-to-openai-users
- Vendor-facilitated EA is *not* a runtime capability of the key: "an enterprise attestation capable authenticator … will provide enterprise attestation to a non-updateable pre-configured RP ID list, as identified by the enterprise and provided to the authenticator vendor, which is 'burned into' the authenticator by the vendor. If enterprise attestation is requested for any RP ID other than the pre-configured RP ID(s), the attestation returned … is a regular privacy-preserving attestation" — https://fidoalliance.org/specs/fido-v2.2-ps-20250714/fido-client-to-authenticator-protocol-v2.2-ps-20250714.html
- Consequence: if OpenAI were not on the key's burned-in list, requesting EA would silently return an ordinary `packed` statement — indistinguishable from what we already submit. Absence of an EA cert never proves "not an EA RP"; only presence does — same spec section.
- EA-capable YubiKeys are a *separate AAGUID family* branded "(Enterprise Profile)", disjoint from the consumer set: `1ac71f64`, `6ab56fad`, `9ff4cc65`, `79f3c8ba`, `b2c1a50b`, `41e39911` — https://learn.microsoft.com/en-us/entra/identity/authentication/concept-fido2-hardware-vendor · https://rublon.com/doc/attestation-for-fido2-vendors · https://www.powershellgallery.com/packages/entraYK/0.6.0/Content/Private%5CGet-YubiKeyInfo.ps1
- A retail key cannot be promoted into that family: `ykman fido config enable-ep-attestation` is documented only for "Authenticators pre-configured to support it", and 5.7 retail owners report "Enterprise Attestation is not supported on this YubiKey" — https://docs.yubico.com/software/yubikey/tools/ykman/FIDO_Commands.html · https://docs.yubico.com/software/yubikey/tools/ykman/webdocs.pdf
- OpenAI's four admitted AAGUIDs are the *consumer / non-enterprise-profile* entries: `f4ce5fc0` is literally named "YubiKey 5 Series with NFC (Consumer Profile)", `a25342c0`/`d7781e5d` are the plain profile entries, plus Titan v2 — https://learn.microsoft.com/en-us/entra/identity/authentication/concept-fido2-hardware-vendor
- No public source states OpenAI is a Yubico EA-allowed RP. Searched: Yubico's OpenAI announcements, OpenAI help centre, the Yubico EA developer docs (which list no third-party RP registry), and the EA "Getting Started" page (which describes RP lists as private and vendor-imprinted) — https://developers.yubico.com/WebAuthn/Concepts/Enterprise_Attestation · https://www.yubico.com/blog/openai-daybreak-signals-a-new-era-for-ai-security-and-the-critical-role-of-hardware-security-keys
- **New and load-bearing: the MDS anchor for each admitted AAGUID is on a different Yubico sub-CA branch, and row 5 used the wrong branch.** `f4ce5fc0` (admitted) anchors to *"Yubico FIDO Attestation A 1"* (issued by "Yubico Attestation Intermediate A 1"), i.e. the **A** branch — https://www.token2.com/tools/fido2-mds/f4ce5fc057d346f5a736efb7d5bc63b5
- By contrast `6ab56fad` (EA profile, 5.7.4) anchors to *"Yubico Attestation Intermediate **B** 1"* + Intermediate A 1 + Root 1, and `1ac71f64` (EA profile, 5.7) anchors *only* to the legacy self-signed "Yubico FIDO Root CA Serial 450203556" — https://www.token2.com/tools/fido2-mds/6ab56fad881f4a43acb20be065924522 · https://www.token2.com/tools/fido2-mds/1ac71f64468d4fe0bef10e5f2f551f18
- So experiment row 5 ("issuer DN set to `CN=Yubico FIDO Attestation B 1`") attacked the B branch against a model whose MDS entry is anchored on the A branch. A/B mismatch alone would produce a silent verification failure, and the "chip has EA for OpenAI" hypothesis was never separated from "we chained to the wrong Yubico CA".
- `1ac71f64`'s anchor is the *legacy* Yubico FIDO root, not the 2025 root — meaning EA-profile keys of that generation chain to a different (older, more widely distributed) root than the model we are admitted on — https://developers.yubico.com/U2F/Attestation_and_Metadata (root table: "Yubico Attestation Root 1 | 5.7.4+", "Yubico FIDO Root CA Serial 450203556")
- EA attestation certificates are structurally detectable in any captured statement: a serial appears in the cert subject *and* in the FIDO OID `1.3.6.1.4.1.45724.1.1.2`, which "is only present on the Enterprise Attestation certificate, and is otherwise not included" — https://docs.yubico.com/hardware/oid/oid-u2f-fido-arc.html · https://developers.yubico.com/WebAuthn/Concepts/Enterprise_Attestation/Getting_Started.html
- Relying parties must independently obtain the EA chain from the vendor; no public download endpoint exists — deployments list "YubiKeys ordered from Yubico with Enterprise Attestation, **plus the attestation certificates Yubico provides**" as a prerequisite — https://secureauth.com/resources/product-blog/yubikey-enterprise-attestation
- The hardware flag is not a property of MDS key protection: `a25342c0`/`f4ce5fc0` are published as *Hardware, Secure Element* and still classify false, and a genuine IDmelon credential (hardware + secure_element in MDS) also classifies false — https://www.token2.com/tools/fido2-mds/a25342c03cdc44148e46f4807fca511c
- Independent confirmation the flag is a narrow model list, not "any real hardware key": TrustKey T110 *and* T120 (genuine physical FIDO2 keys) register and are still told "add a hardware key"; OpenAI support confirmed only bundle keys as supported — https://community.openai.com/t/daybreak-does-not-recognize-trustkey-t110-physical-fido2-keys-as-hardware-security-keys/1401917
- Two logical gaps in the existing evidence table: rows 3 and 12 both used *bundle* AAGUIDs, which are admitted on sight, so neither proves the verifier skips `attStmt.sig` nor that attestation is optional — the only rows that expose the verifier are 10/11/19/20. Signature verification for admitted models remains unmeasured — https://www.token2.com/tools/fido2-mds/f4ce5fc057d346f5a736efb7d5bc63b5 (anchor list is what a verifier would use)
- MDS is machine-readable and self-refreshing: `curl -Ls --output md.jwt https://mds3.fidoalliance.org/` then decode the JWT body to JSON, per Yubico's own walkthrough — https://archive.fosdem.org/2023/schedule/event/security_fido_beyond/attachments/slides/5669/export/events/attachments/security_fido_beyond/slides/5669/FOSDEM2023_securityRoom.pdf
- Genuine device attestation leaves are publicly published as a side effect of `ssh-keygen -t ed25519-sk -O write-attestation=attest.bin` (Yubico's own demo flow), i.e. real Yubico leaf certs exist in public repos — same FOSDEM slide deck

## EXPERIMENTS

1. Instrument the enrolment page: hook `navigator.credentials.create`, dump `publicKey.attestation`, and log CTAP `authenticatorMakeCredential` param `0x04` (`enterpriseAttestation`) in the bridge | expect: `attestation: "direct"` and no `0x04` present | proves: OpenAI does not request EA at all, which closes the entire EA avenue with one measurement instead of nine inferences
2. Enrol AAGUID `1ac71f64` then `6ab56fad` (both EA-capable Enterprise Profile) with the existing self-signed packed statement | expect: 400 on both | proves: the admitted list excludes the EA family, so even a burned-in OpenAI RP ID would never be admitted; if either returns 200 the EA avenue is live and branch B becomes worth chaining
3. Re-chain the forged leaf onto the **A branch**: leaf issuer `CN=Yubico FIDO Attestation A 1`, `x5c = [leaf, Yubico FIDO Attestation A 1 (real PEM), Yubico Attestation Intermediate A 1, Yubico Attestation Root 1]`, AAGUID `f4ce5fc0`, valid packed sig; poll flag at t+2/10/30 | expect: 200, flag false | proves: row 5's failure was branch isolation, not EA — and a chain-valid-to-the-right-anchor statement is still insufficient
4. Graft a genuine leaf: `x5c[0]` = a real Yubico device attestation leaf pulled from a public `attestation.bin`/published PEM, AAGUID taken from that leaf's AAGUID extension, credential public key = our emulator's, `sig` signed by our emulator over `authData‖clientDataHash` | expect: either flag flips true, or 400/flag false | proves: true ⇒ the flag needs only a valid chain, not key binding, and any public genuine leaf is sufficient; false ⇒ the flag requires an SPKI-bound signature, i.e. the vendor's private key
5. Same as 4 but replace `sig` with random bytes while keeping the genuine `x5c[0]` | expect: identical outcome to 4 if signatures are unchecked, 400/false if checked | proves: isolates chain-validation from signature-validation, which rows 3 and 12 cannot distinguish
6. Enrol the *same* AAGUID `f4ce5fc0` twice: once via the generic passkey add flow, once via the "Add a hardware security key" page that gates **Continue** — compare the flag on each credential | expect: different flags | proves: the hardware classification is applied by a flow-specific verification path, not globally per credential, which would explain false on all nine generic-flow enrolments
7. Add the C Nano counterpart AAGUIDs (YubiKey 5C Nano fw 5.7.4 generation) to the admission sweep alongside `f4ce5fc0`/`a25342c0`/`d7781e5d` | expect: 200 only for the generation shipped in the bundle | proves: whether the admitted list is keyed to the physical bundle SKUs rather than to the 5C NFC model
