- `attestationCertificateKeyIdentifiers` is defined as a hex SHA-1 over the certificate's `subjectPublicKey` BIT STRING, and is a *parallel* attribution namespace to AAGUID — so the set of registered keys is not the set of AAGUIDs and is addressable independently of them — https://fidoalliance.org/specs/mds/fido-metadata-statement-v3.1-ps-20250521.html
- Row 28's "0 of 1102" is a null result *by construction*: it intersected `attestationRootCertificates` (roots/intermediates, i.e. anchor material) against a field populated from *end-entity attestation certificates*. A disjoint pair of sets cannot produce a hit, so row 28 did not measure whether the registered-SPKI class is publicly reachable — https://fidoalliance.org/specs/mds/fido-metadata-statement-v3.1-ps-20250521.html
- Consequence of row 3 (attStmt signature not verified) combined with the SPKI definition: an SPKI-equality check needs only a *public certificate to copy the public key bytes from*, plus any signing key of our own for both the certificate's own signature and `attStmt.sig`. The "vendor attestation private key" out-of-scope condition therefore overstates the requirement — the real requirement is a published *end-entity attestation certificate* (batch or device), not a private key — https://fidoalliance.org/specs/mds/fido-metadata-statement-v3.1-ps-20250521.html
- Enterprise attestation is not a server-side choice: the client only conveys it when the RP asks for `attestation: "enterprise"` **and** the authenticator's vendor-managed EA list contains the RP ID, so an EA certificate for `openai.com`/`chatgpt.com` cannot exist unless that RP ID was provisioned into the key — https://www.w3.org/TR/webauthn-3/
- Yubico's attestation model is batch-based (a per-model/per-batch attestation certificate whose public key is the registered identifier) with device-specific leaves as the alternative model, which is why the registered-SPKI population is small enough for a public-corpus intersection to be tractable — https://developers.yubico.com/U2F/Attestation_and_Metadata/
- The MDS BLOB is served from a live endpoint distinct from the spec, so identifiers can be enumerated offline against a pinned snapshot — https://mds.fidoalliance.org/

## NEW ANGLES
- Harvest registered SPKIs outside the MDS: firmware images and vendor "verify your key" utilities (Token2, Nitrokey, SoloKeys) embed attestation certificates, and U2F-era FIDO metadata mirrors preserve identifier lists whose certificates may exist in unrelated repos.
- Row 3 means the certificate's own signature and `attStmt.sig` are both free: any published *batch* attestation certificate (not a root) for an accepted model is a complete solution — search vendor docs, sample-code repos, and bug reports for such leaves rather than for keys.
