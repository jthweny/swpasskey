## EXPERIMENTS

1. **Yubico AAGUID sweep, one statement, many AAGUIDs.** Replay the exact row-9 packed statement with only the AAGUID swapped, in one script, and log HTTP status: `4599062e` (5C Nano 5.7.4 — *OpenAI's own bundle key, never tested*), `ff4dac45` (5C 5.7.4), `19083c3d` (5C 5.7), `fa2b99dc` (5 NFC 5.1), `6d44ba9b` (Security Key NFC 5.1), `6b8dd8a4`/`b92c3f9a` if present. | expect: 200 for `4599062e` and the 5.7.x set, 400 for the 5.1/older set → accept set = the models OpenAI ships/uses (fw≥5.7 NFC), not "Yubico". | proves: whether the gate is a bundle-model allowlist (then no emulatable model exists, ever) or a firmware-generation/metadata-freshness filter (then it is a cache question, and the cache can be observed changing).
2. **Repeat signal-1 at t+2/10/30/24h for the two AAGUIDs that return 200**, after deleting and re-adding the credential, and diff `GET /api/accounts/advanced-account-security/passkeys`. | expect: either `is_non_exportable_hardware_key` never flips (gate ≠ async job) or it flips within one cycle for one model only. | proves: whether the flag is late-bound per-credential (matching the community "delayed/backend state update" report) — that alone changes the retry strategy for everything else.
3. **Token2 PIN+ bracket, three armatures.** Enrol `eabb46cc` with (a) x5c = the published *end-entity anchor bytes themselves* (so x5c[0] IS the MDS anchor, a legitimate partial-chain case), (b) our own leaf with subject/issuer DN forced to `C=CH, O=TOKEN2 Sàrl, CN=token2.com`, (c) anchor appended after our self-signed leaf. | expect: (a) 400 or 200-with-flag-false, (b) 400, (c) 400 — replicating row 10. | proves: whether the end-entity-anchor class is refused by *policy* (matching Securitag) or by *chain-building*; if (a) is 200 the verifier uses partial-chain trust and end-entity anchors are a live class, which would make Token2's own toolchain reproducible.
4. **Thetis PRO purchase (₹/~$33), real credential, no emulator.** Buy one Thetis PRO (`a3975549`), enrol through the normal flow, then poll signals 1–2 at t+2/10/30 min and 24 h. | expect: 200 + MDS-derived name "Excelsecu…"; flag either true (classification is chain-based, → all our 400s were pure X.509 failures and the emulator problem is only "get a Yubico-signed leaf") or false (classification is an internal model allowlist, matching row 20). | proves: the single discriminator between the two surviving hypotheses, for $33, with zero cryptographic work.
5. **Token2 PIN+ purchase as the counter-arm** (`eabb46cc`, L2, newest entry 2024-12-30, end-entity anchor) — same polling, same account, different credential. | expect: false / 400. | proves: if Thetis flips and Token2 does not, then "recency" and "certification level" are both non-causes and anchor **class** is; if both flip, the gate is chain+hardware and only Yubico-class leaves are the blocker.
6. **Publish our own AAGUID in MDS, then re-enrol.** Register on MyMDS (certification explicitly optional), upload a metadata statement with our self-generated root in `attestationRootCertificates`, `keyProtection: ["hardware","secure_element"]`, `attestationTypes: ["basic_full"]`, our own AAGUID; hold until the BLOB `no` increments past the current serial and `nextUpdate` has passed, then enrol with the matching chain and poll. | expect: if the rule is "chain validates to an MDS anchor with hardware keyProtection" → 200 and flag true, first ever; if the rule is an internal allowlist → 200/400 with flag false. | proves: definitively whether the flag consumes MDS at all, and whether we can *be* the vendor of an accepted model. Note the honest-claim hazard: publishing `keyProtection: hardware` for a software authenticator is a false statement to the registry, plan accordingly.
7. **Control timing with one real accepted key** (borrow any YubiKey 5 NFC/5C NFC fw 5.7.x): enrol, poll the same way, and record the exact latency to `true`. | expect: true within minutes-to-hours. | proves: the achievable baseline and the polling window, and whether `tac1_enabled` flips off the credential alone or needs the identity step — i.e. answers question (b) separately from (a).
