## FOUND
- WebAuthn gates enterprise attestation at the request layer: `enterpriseAttestationPossible` is `true` only when `pkOptions.attestation == "enterprise"` **and** the user agent chooses to support EA for that `pkOptions.rp.id`; any other conveyance value forces it `false` before the authenticator is ever consulted — https://www.w3.org/TR/webauthn-3/
- CTAP2.1 carries EA as a discrete response flag: `epAtt (0x04)` in the authenticatorMakeCredential response ("Indicates whether an enterprise attestation was returned for this credential"), request parameter `enterpriseAttestation (0x0A)` with value 1 = "non-updateable pre-configured RP ID list ... burned into the authenticator by the vendor" and value 2 = "The platform is enterprise-managed and has already performed the necessary vetting of the RP ID", capability advertised via the `ep` option in `authenticatorGetInfo` — https://fidoalliance.org/specs/fido-v2.1-ps-20210615/fido-client-to-authenticator-protocol-v2.1-ps-errata-20220621.html
- Platforms expose EA as a boolean distinct from attestation validity: Windows `WEBAUTHN_CREDENTIAL_ATTESTATION.bEpAtt` — "TRUE if the credential has enterprise attestation" — https://learn.microsoft.com/en-us/windows/win32/api/webauthn/ns-webauthn-webauthn_credential_attestation
- The RP server can see the EA signal without any chain evidence: `RegistrationResponseJSON.clientExtensionResults` "MUST be set to the output of `getClientExtensionResults()`", so `enterpriseAttestation` rides to the server in the registration JSON alongside `attestationObject` — https://www.w3.org/TR/webauthn-3/
- That client-extension channel is browser-asserted, not authenticator-signed: Langley notes servers should extract extension outputs "directly from the authenticator data ... rather than use the browser's reflection of them in the `PublicKeyCredential` object, in order to ensure that it's getting authentic extension results" — https://www.imperialviolet.org/tourofwebauthn/tourofwebauthn.html
- Chrome sends the "individual attestation" hint (CTAP `enterpriseAttestation` param) only when the RP ID is in the `SecurityKeyPermitAttestation` policy or the caller origin is in the newer per-origin list (`kPermitEnterpriseAttestationOriginList`, UI flag "Web Authentication Enterprise Attestation", `chrome://flags/#web-authentication-permit-enterprise-attestation`); otherwise `"enterprise"` behaves exactly like `"direct"` — https://www.chromium.org/security-keys , https://chromium.googlesource.com/chromium/src/+/4c6070768bab73dc25a4a8d1c0e31db761624174%5E%21 , https://developers.yubico.com/WebAuthn/Concepts/Enterprise_Attestation/Getting_Started.html
- FIDO publishes EA attestation material **with the private key**: the conformance repo's FIDO2 Authenticator README ships "EP Certificate" (`FIDO2 Enterprise Attestation BATCH KEY prime256v1`, issued by `FIDO2 Enterprise Attestation TEST ROOT1`) and "EP Certificate Private KEY" (EC PEM), for test RP ID list `enterprisetest.certinfra.fidoalliance.org, ep.fidoalliance.co.nz` — https://github.com/fido-alliance/conformance-test-tools-resources/blob/main/docs/FIDO2/Authenticator/README.md
- FIDO test metadata (test AAGUIDs + test roots) is served from a separate endpoint, `https://mds3.fido.tools/getTestMetadata`, distinct from the production MDS3 BLOB (GlobalSign R46-signed) — https://github.com/fido-alliance/conformance-test-tools-resources/issues/698 , https://fidoalliance.org/metadata
- Yubico EA certificates are per-device with the serial in the subject DN ("the serial number was stored in the subject field of the X.509 certificate in the form of a Distinguished Name (DN)", CN extracted by regex), chain mechanism "the same as a normal Attestation Statement" — https://www.yubion.com/en/blog/fido2-enterprise-attestation-technical-deep-dive
- Yubico EA requires pre-provisioned hardware: fw 5.7.4+ "custom configured keys" for YubiKey 5 Series ("EA enables ... read the YubiKey serial number (or other unique identifier specific to the organization) on custom-programmed keys"), and "SCP03, SCP11, Enterprise Attestation, and Serial Number Support are only available on the Security Key Series Enterprise Edition" — https://docs.yubico.com/hardware/yubikey/yk-tech-manual/webdocs.pdf , https://docs.yubico.com/hardware/yubikey/yk-tech-manual/yk5-firmware-5.7.html
- EA enablement is itself a vendor-preconfigured device setting, locally toggled only on keys pre-configured to support it: `ykman fido config enable-ep-attestation` — "Enables Enterprise Attestation for Authenticators pre-configured to support it" (ykman ≥ 5.3.0) — https://docs.yubico.com/software/yubikey/tools/ykman/FIDO_Commands.html
- Two EA delivery modes exist, matching CTAP values 1/2: vendor-facilitated (RP ID list "may only be updated by the vendor/manufacturer", imprinted at manufacture) and platform-managed (enterprise-managed browser holds the RP ID list) — https://developers.yubico.com/WebAuthn/Concepts/Enterprise_Attestation
- Question (b) context — TAC/Daybreak enrollment mandates "a hardware security key, plus another either software or hardware FIDO passkey", permanently disables SMS/email recovery, "supports other FIDO-compatible hardware keys", hardware passkeys required for TAC from 2026-09-01 — https://www.forrester.com/blogs/openai-makes-hardware-passkeys-mandatory-for-its-highest-end-cyber-model , https://www.itpro.com/security/everything-you-need-to-know-about-chatgpts-new-advanced-account-security-features
- Browser matrix constrains the client-side EA channel: Chrome supports platform-managed EA (flag-gated), Edge shows serial via Windows WebAuthn API, Firefox had no EA as of Feb 2025, Windows 10's WebAuthn API lacks EA entirely (Win11+ only) — https://www.yubion.com/en/blog/fido2-enterprise-attestation-technical-deep-dive
