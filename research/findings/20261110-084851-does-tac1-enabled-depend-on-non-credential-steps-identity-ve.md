## FOUND
- Individual Daybreak/TAC access is a **four-term conjunction**, and the order is enforced: eligible paid plan → Advanced Account Security → ≥1 compatible physical FIDO2 key → *then* identity verification → then review. "The individual application flow checks these requirements before identity verification" — https://help.openai.com/en/articles/20001258-openai-daybreak-trusted-access-for-cyber-overview
- The ordering is stated as a hard block, not a suggestion: "You must complete any unfinished plan or account-security steps before you can start identity verification." — https://help.openai.com/en/articles/20001259-troubleshooting-openai-daybreak
- There is a **pre-identity-check endpoint** that hard-fails with a machine code before Persona is ever reached: HTTP 403, `{"code":"cyber_verification_precheck_failed","message":"Your account isn't currently eligible for Daybreak. You can still use ChatGPT."}` — reported by an account that *already had* AAS enabled and **two physical YubiKeys registered** — https://community.openai.com/t/daybreak-id-verification-failing/1400087?page=2
- That precheck can be cleared **without any credential change**: after a support escalation was told to "retry if the option was available," the same account went from 403 at precheck to reaching and submitting Persona — https://community.openai.com/t/daybreak-verification-fails-repeatedly-and-support-escalation-is-stuck-in-a-duplicate-case-loop-category/1402936
- **Delayed backend state is confirmed at the IDV stage, not just the key stage:** two failed Persona attempts, no user action, then `/cyber` "had updated itself to the completed state… 'You're all set', with Advanced Account Security, identity verification, and Daybreak keys all marked as completed" — https://community.openai.com/t/trusted-access-for-cyber-issue/1399570?page=2
- Second independent delayed-flip report: "magically, when I went back in there, my identity is confirmed… maybe my support ticket worked, but they never told me they did anything. Or they realized how screwed up everything was and fixed in bulk" — https://community.openai.com/t/daybreak-id-verification-failing/1400087?page=2
- The eligibility page is a **three-item checklist with independent state**, and it can sit in `AAS: Completed / Identity verification: Completed / Daybreak keys: Incomplete`, i.e. `tac1_enabled` is downstream of a *third*, separate key-binding step — https://community.openai.com/t/previously-approved-daybreak-blue-access-lost-after-fido2-key-change-re-verification-repeatedly-denied/1413971
- That third step re-triggers its own verification ("the Daybreak key setup requires another verification that gets denied") — same thread, above.
- **The flag is recomputed continuously against the live key set**: removing a single broken FIDO2 key on an already-approved account revoked Daybreak access, and re-adding hardware did not restore it — https://community.openai.com/t/previously-approved-daybreak-blue-access-lost-after-fido2-key-change-re-verification-repeatedly-denied/1413971
- Docs state fixing the key setup "does not automatically restore Trusted Access"; reverification/reapplication plus fresh review is required — https://help.openai.com/en/articles/20001259-troubleshooting-openai-daybreak
- OpenAI ran a documented mass-revocation incident (19 Aug 2026) that removed Daybreak Blue from a limited user set and forced re-verification; accounts still fail to restore months later — https://community.openai.com/t/daybreak-blue-verification-broken-for-a-month-only-getting-automated-please-wait-replies-across-4-case-numbers/1397981 · https://www.aichatdaily.com/ai-security/openai-revokes-cyber-researcher-access-daybreak-blue-blames
- **No manual route exists.** "Support cannot override the decision, grant Daybreak access, or provide details about the checks behind the eligibility result" — https://community.openai.com/t/daybreak-verification-fails-repeatedly-and-support-escalation-is-stuck-in-a-duplicate-case-loop-category/1402936
- The failure message is deliberately **non-diagnostic** — the same string covers "IDV failed" and "account not eligible", and support will not say which; "Daybreak verification does not support retries or appeals" — https://community.openai.com/t/daybreak-individual-verification-rejected-without-indicating-whether-identity-verification-failed/1396918
- One AI-support answer claimed software passkeys make the account noncompliant and demanded two physical keys; **Tier-3 support retracted it** — one qualifying physical key is sufficient, other passkeys may remain — https://community.openai.com/t/trusted-access-for-cyber-issue/1399570
- **The docs now contain an explicit denylist** — "Unsupported FIDO2 hardware security keys: TrustKey T110 and T120 security keys are currently ineligible for individual Daybreak access" — https://help.openai.com/en/articles/20001259-troubleshooting-openai-daybreak · https://community.openai.com/t/daybreak-trustkey-t110-t120-confirmed-ineligible-compatibility-requirements-were-clarified-too-late/1402777
- A TrustKey T110 is a genuine external authenticator (`getInfo`: AAGUID `e3512a8a-62ae-11ea-bc55-0242ac130003`, `usb`, `plat:false`, `clientPin:true`, `packed`, fw `213.11.139`) yet ChatGPT lists it only as "Passkey" and Daybreak keeps "To continue, add a hardware key" with Continue disabled — https://community.openai.com/t/daybreak-does-not-recognize-trustkey-t110-physical-fido2-keys-as-hardware-security-keys/1401917
- Therefore `is_non_exportable_hardware_key` is **not** derived from attestation format, transport, or genuine hardware-ness — a real `packed` hardware key is classified identically to a software passkey.
- Working hardware is broader than the 5C family: a community member confirms the **US$29 "Yubico Security Key C NFC"** completes Daybreak setup "without any trouble" — https://community.openai.com/t/daybreak-individual-access-from-latam-countries-does-the-us-29-yubico-security-key-c-nfc-qualify/1411105
- **Organization access is a separate onboarding track** — "Organization-level access follows a separate onboarding process" — https://help.openai.com/en/articles/20001259-troubleshooting-openai-daybreak
- Geography is an independent variable: purchase-availability gates (Peru), jurisdiction restrictions being tightened, and a Nigeria-based applicant with a correctly registered YubiKey 5C NFC stuck in permanent rejection — https://www.yubico.com/blog/openai-daybreak-signals-a-new-era-for-ai-security-and-the-critical-role-of-hardware-security-keys · https://community.openai.com/t/daybreak-verification-fails-after-persona-completion-human-review-requested-for-case-18020913/1409595
- Surfaces diverge: accounts report `/cyber` says unavailable while Codex still shows access, implying per-surface provisioning rather than one boolean — https://community.openai.com/t/trusted-access-for-cyber-issue/1399570
- Individual flow requires age ≥18 and "identity and trust verification, risk considerations" — review is human/graded, not a pure predicate — https://help.openai.com/en/articles/20001258-openai-daybreak-trusted-access-for-cyber-overview
- Deadlines: mandate effective 1 Sep 2026 for new members; existing individuals had to comply by 1 Oct 2026 — https://fidoalliance.org/openai-will-gate-its-most-capable-cyber-models-behind-a-physical-security-key · https://www.forrester.com/blogs/openai-makes-hardware-passkeys-mandatory-for-its-highest-end-cyber-model

## EXPERIMENTS
1. **Re-auth as the recompute trigger.** Sign out of all sessions, sign in *using the emulated key only*, then query `GET /api/accounts/advanced-account-security/passkeys` and `POST /backend-api/cyber_verification/status` at t+0, t+10m. | expect: at least one field changes on the auth event rather than on a timer; a `last_authenticated_with`-style field appears | proves: classification/recompute is bound to an authentication event, not to enroll time — explains every "delayed update" report and gives us a deterministic trigger instead of waiting.
2. **Capture and diff the precheck call.** Load `chatgpt.com/cyber` in a proxy, record every XHR, isolate the call that yields `cyber_verification_precheck_failed`, then replay it with (a) current key set, (b) zero credentials, (c) two emulated creds. | expect: identical generic body in all three cases, or a per-condition array | proves: whether the hardware flag is even inside the precheck predicate, and whether `tac1_enabled` is program-provisioning rather than credential-derived.
3. **Probe the "Set up your Daybreak keys" step directly.** From the same HAR, take the request the Daybreak-keys checklist item fires and POST it with the credential ID of the accepted-AAGUID emulated key. | expect: a 4xx with a specific code (`daybreak_key_not_qualifying`-class) rather than the generic eligibility message | proves: the classifier is a named server-side predicate on the credential record, and the error taxonomy leaks which field it reads.
4. **Sign-out/in plus key-removal ordering.** Record `tac1_enabled`; delete the emulated credential; re-query immediately and at t+2/10/30m; re-enroll the same AAGUID; re-query on the same schedule. | expect: `is_non_exportable_hardware_key` and `tac1_enabled` unchanged, but a transient `null`/absent state during the window | proves: whether the third "Daybreak keys" step is recomputed eagerly (per-change) or lazily (per-auth), and whether our earlier single-shot `false` was simply read during a rebuild.
5. **Transports and attachment as input, not attestation.** Register via the browser bridge while forcing `response.transports: ["nfc","usb"]` and `authenticatorAttachment: "cross-platform"` (and a control run returning `["internal","hybrid"]` / `"platform"`), holding AAGUID `d7781e5d` constant. | expect: flag stays false in both, but `authenticator_name` or a hidden field changes | proves: whether the classifier consumes the client-reported transport/attachment channel at all — if none of those inputs move it, the only remaining input is server-side attestation state.
6. **Firmware-epoch sweep of the accepted set.** Pull every FIDO MDS entry whose `authenticatorGetInfo.firmwareVersion` is ≥ 5.7.4 / whose description contains "Consumer Profile," and batch-enroll each AAGUID with our self-signed packed statement, 5 per minute. | expect: a clean binary split (200 vs 400) whose boundary is firmware epoch, not vendor or product line | proves: the enroll gate is an epoch/vendor-programme allowlist that the MDS exposes completely — this maps the operator's open question in one run.
7. **Enterprise-attestation (EA) variant.** Re-enroll `d7781e5d` requesting `enterpriseAttestation: 1` and emit a leaf carrying the RP-ID attestation marker plus the enterprise-profile OID. | expect: 200 with flag false, or a distinct 4xx | proves: whether the 5.7.4 "Consumer/Enterprise Profile" split (which is exactly the wording in the accepted AAGUID's MDS description) is the discriminator OpenAI is reading.
8. **Cross-account precheck control.** Run the precheck on a second account that has a paid plan but no hardware key at all. | expect: same `cyber_verification_precheck_failed` 403 | proves: the precheck fires before the credential is consulted, so the credential can never be the term that unblocks IDV — the UI `Continue` gate and `tac1_enabled` are provably different predicates.

## NEW ANGLES
- Test whether a fresh **session minted from the qualifying key** (not the credential record) is what `tac1_enabled` keys on — the Forrester read that practitioners must perform a live ceremony suggests a per-session, not per-credential, term.
- Treat the incident history as a lever: the 19 Aug 2026 mass-revocation cohort had access restored "in bulk" without user-visible action. Watch `tac1_enabled` for cohort-wide flips during OpenAI status incidents — a window where the predicate is being rebuilt may admit states it otherwise wouldn't.
- Organization/TAC-org onboarding is documented as a separate process. Enumerate whether an Enterprise workspace admin can bind a member's credential to TAC without the individual Daybreak keys checklist; if so, the credential gate is bypassed by design rather than by exploit.
- Determine whether `tac1_enabled` is per-surface by comparing a Codex CLI token minted before the key change against `/cyber` — divergence proves independent provisioning and gives a second, less-guarded read of the same state.
- Model-family hypothesis worth killing or confirming: accepted AAGUIDs (`f4ce5fc0`, `d7781e5d`, `a25342c0`, `42b4fb4a`) may correspond to hardware whose attestation includes a **unique device identifier** usable for revocation — that would explain why a legitimate-but-anonymous TrustKey is refused while a phone app with a real chain (IDmelon) is reportedly accepted. Search MDS `attestationTypes` + cert extensions for a serial/device-identifier field on exactly those five AAGUIDs.
