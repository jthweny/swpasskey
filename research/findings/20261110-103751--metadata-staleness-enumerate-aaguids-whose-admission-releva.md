## FOUND
- The MDS3 BLOB is served with a `localCopySerial` parameter that returns `304 Not Modified`, and downloads are rate-limited to **once per hour per IP** — so any RP, including one that refreshes dutifully, is holding a snapshot that can be up to an hour stale, and a naive poller can 429 itself into a longer gap — https://fidoalliance.org/mds-changelog
- BLOB serials can be dated: an archived mirror's commits are titled `Metadata 174 July 2025` (committed 2025-06-12), `Metadata v226` (2026-02-05), `Metadata v230` (2026-02-19), and 2026 commits on Nov 1 and Nov 8 — i.e. reissue cadence is roughly weekly, not the "once a month" FIDO recommends to RPs — https://github.com/adricasti/fido-metadata/commits/main/mds_metadata.json , https://fidoalliance.org/metadata
- MDS content is **additive only**: published statements cannot be deleted, and a vendor's update flow states that "change of Authenticator Version, and addition of the new Attestation Root Certificates can NOT be reversed" (checkbox wording in the update dialog); post-certification edits require a support request — https://fidoalliance.org/mds-portal-user-guide-for-vendor-users
- Roots are added to existing entries **without touching `timeOfLastStatusChange`**: the entry `6ab56fad` (YubiKey 5 Series with NFC, Enterprise Profile) reports `MDS last updated 2025-01-10` yet publishes an anchor `Yubico FIDO Attestation B2 1` whose `notBefore` is 2025-08-01 — https://www.token2.com/tools/fido2-mds/6ab56fad881f4a43acb20be065924522
- Same pattern externally: the 5.7.x Yubico roots "were first available in BLOB 127 available January 9, 2025" while the 5.7.4 entries' certification date is 2024-12-22 — anchor first-appearance, not statement date, is the only reliable blob-recency fingerprint — https://community.cloudflare.com/t/fido2-security-key-enrollment-fails-with-attestation-certificate-chain-is-not-sign/959209
- Descriptions are volatile and get *rewritten* by vendors: the mds-dump history shows diffs like `-GoTrust Idem Key FIDO2 Authenticator / +GoTrust Idem Key` and `+YubiKey 5 Series with NFC (Consumer Profile) KVZR57-2` appearing as added lines — https://github.com/opotonniee/fido-mds-explorer/commits/main/js/mds.js
- OpenAI's echoed credential names are **main-MDS descriptions, not Convenience-MDS friendly names**: the convenience metadata entry for `d7781e5d` is plain "YubiKey 5 Series with NFC" (no profile suffix) — https://developers.yubico.com/WebAuthn/Concepts/FIDO_Metadata_Service_(MDS).html — while row 26's admitted credential came back as "Security Key Series with NFC (Consumer Profile)", which is exactly the main-MDS description of `0f083f18` (statusReport `FIDO_CERTIFIED_L2` effective **2026-04-25**, `MDS last updated 2026-05-01`, authenticatorVersion 329728) — https://www.token2.com/tools/fido2-mds/0f083f18410543a8ad6924e812e38141
- A whole Yubico family was (re)certified at **2026-04-25** with profile-suffixed descriptions and fresh AAGUIDs: `f4ce5fc0` "YubiKey 5 Series with NFC (Consumer Profile)", `7dab85a5` "…(Consumer Profile) KVZR57-2", `41e39911` "…(Enterprise Profile)", `0ebd9f2c` "…Enhanced PIN (Consumer Profile)", `24083bcb`/`ab7d1767` "Enterprise Security Key Series with NFC (Consumer|Enterprise Profile)", `9806a2c8` "YubiKey Bio Multi-protocol Edition (Consumer Profile) 1VDJSN-2" — https://www.token2.com/tools/fido2-mds
- So a **dated floor exists for OpenAI's snapshot**: any name containing "(Consumer Profile)" implies a blob no older than the 2026-04/05 reissue. That is measurable per credential, and none of rows 1–29 recorded it.
- Status layers are legible to conformant verifiers and are read from the same blob: `REVOKED` — "Relying parties SHOULD reject any future registration of this authenticator model"; `ATTESTATION_KEY_COMPROMISE` — if no certificate is set, "reject all new registrations of the compromised authenticator"; `UPDATE_AVAILABLE` — RP "MUST reject the Metadata Statement if the authenticatorVersion has not increased" — https://fidoalliance.org/specs/mds/fido-metadata-service-v3.1-ps-20250521.html
- Reference implementations actually filter on it: Yubico's `FidoMetadataService` default prefilter drops any `REVOKED` entry and its registration filter drops matching `ATTESTATION_KEY_COMPROMISE` entries — https://developers.yubico.com/java-webauthn-server/webauthn-server-attestation ; a current RP implementation states "`REVOKED` and the compromise statuses reject the model regardless of level" — https://github.com/keycloak/keycloak/issues/54136
- Untested members of the accepted families, with authoritative IDs: `ff4dac45-ede8-4ec2-aced-cf66103f4335` = "YubiKey 5 Series" fw **5.7.4** (MDS description per https://www.token2.com/tools/fido2-mds/ff4dac45ede84ec2acedcf66103f4335 — and per Yubico's own AAGUID table this is **YubiKey 5C Nano 5.7.4 / 5C 5.7.4**, one of the two OpenAI-bundle models) — https://www.powershellgallery.com/packages/entraYK/0.6.0/Content/Private%5CGet-YubiKeyInfo.ps1
- Also untested: `20ac7a17` (5C Nano 5.7, "EA capable"), `420/6ab56fad` "5 Series with NFC (Enterprise Profile)" (EA capable), `b7d3f68e-88a6-471e-9ecf-2df26d041ede` "Security Key NFC by Yubico" fw 5.7.4 L2 2024-12-22 — the same AAGUID a Cloudflare user presented with a valid `Yubico FIDO Attestation B 1 → Intermediate B 1 → Root 1` chain — https://www.token2.com/tools/fido2-mds/6ab56fad881f4a43acb20be065924522 , https://community.cloudflare.com/t/fido2-ssh-enrollment-fails-attestation-failed-on-yubikey-fw-5-7-4-valid-chain/966332
- Enterprise Profile is a separate SKU family by Yubico's own wording ("These devices are known as enterprise profile"), so EA-profile AAGUIDs are distinct models, not renames of the consumer ones — https://support.yubico.com/s/article/YubiKey-hardware-FIDO2-AAGUIDs
- New MDS enums landed after your row set: `AttestationType` gained **`none`** and **`anonca`**, `KeyProtectionType` gained `sync_fabric`, `AttachmentHint` gained `smart-card` (FIDO Registry 2.3 / CTAP 2.3 statement support) — https://fidoalliance.org/mds-changelog
- Since 2026-09-29 the MDS accepts **credential-manager** metadata statements, and entries from the community `passkey-authenticator-aaguids` repo are being migrated into the official MDS — https://fidoalliance.org/mds-changelog

## EXPERIMENTS
1. Enrol `7dab85a5-d16d-4eaf-a7ef-4c1385b151c5` ("YubiKey 5 Series with NFC (Consumer Profile) **KVZR57-2**") and `41e39911-c669-4811-b860-c6ad0b411b96` ("…(Enterprise Profile)") with a full `leaf → Yubico FIDO Attestation A 1 → Intermediate A 1 → Root 1` x5c, and in the same run fetch `https://c-mds.fidoalliance.org` and record the friendlyNames for the same two AAGUIDs | expect: 200 with `authenticator_name` reproducing the **suffixed** description (⇒ snapshot ≥ the blob carrying the 2026-04/05 rename, and names come from the main blob) or 200 **without** the `KVZR57-2` suffix while the c-mds name is suffix-free (⇒ names come from c-mds, and every "they echo MDS" inference in rows 1–29 needs re-basing) | proves: which blob, and which *service*, supplies the name OpenAI displays — the cheapest dated probe of their snapshot available
2. Build the anchor first-appearance index from `js/mds.js` commit history (first commit each PEM appears in, joined to the archived blob serials), then enrol Securitag `5df66f62` (authData AAGUID + matching cert extension) four times with x5c terminating in, respectively: (a) `Yubico FIDO Attestation A 1` (notBefore 2024-12-01), (b) `…B 1` (2024-12-01), (c) `…B2 1` (notBefore **2025-08-01**, first public in a post-Aug-2025 blob), (d) the newest 2026-era anchor in the index from a non-Yubico vendor | expect: (a),(b) → 200 as in row 27; (c) → 200 if the pool was refreshed after Aug 2025, 400 if it is frozen before it; (d) discriminates "refreshed generically" from "refreshed for Yubico only" | proves: the age of the global anchor set, by binary search — the one mechanism that turns a model-gate 400 into a 200
3. Enumerate from the current blob every AAGUID with a `REVOKED` statusReport and every one with `ATTESTATION_KEY_COMPROMISE` (and no `batchCertificate`), pick the two with the most recent `effectiveDate`, plus one entry that carries only `UPDATE_AVAILABLE`, and enrol all three with a chain ending in a genuine Yubico anchor (row 27's trick, which admits non-bundle models by name) | expect: 200 for `UPDATE_AVAILABLE`; for the compromised/revoked pair either 400 (statuses are read and honoured — then the effectiveDate gives you a second, independent snapshot bound) or 200 (statuses ignored entirely, which is the only branch where a pre-revocation snapshot could matter) | proves: whether `statusReports` participate in OpenAI's admission at all, which decides if status staleness is a live lever or a dead branch
4. Enrol `ff4dac45` (YubiKey 5 **C Nano** 5.7.4 — the bundle model) twice: full genuine A-1 chain, and `fmt: none`; poll `/api/accounts/advanced-account-security/passkeys` and `/backend-api/cyber_verification/refresh_status` at t+2 min, t+10 min, t+30 min, then daily for 7 days, logging the blob serial each poll via `GET https://mds3.fidoalliance.org/?localCopySerial=<lastSeen>` (200 vs 304) | expect: 200 + `is_non_exportable_hardware_key: false` at every poll, with `qualifying_count` unchanged at 0 and no state change across blob rollovers | proves: whether the bundle SKU's own AAGUID is treated like its siblings (⇒ the list is model-family, not bundle-specific), and closes the "flips days later" report for software material with a time series rather than a single read
5. Freeze one known-accepted shape (row 1) and one known-refused shape (`f8a011f3`, row 17) as controls; re-submit both within the hour before and the hour after the next blob rollover (detected by `localCopySerial` flipping 304→200) | expect: both verdicts identical across the boundary | proves: whether the classifier re-evaluates per blob, which is the only way staleness could change a verdict on an already-measured credential
6. For each AAGUID in experiment 1 and 4, capture the in-page `/backend-api/cyber_verification/refresh_status` response immediately before and 5 min after enrolment (bearer token read from the page context in the same browser-bridge session) | expect: `qualifying_count` never increments and always agrees with the per-credential flags | proves: whether the count oracle is a strictly derived view (⇒ it adds no detection power) or a separate backend path that can disagree (⇒ new attack surface)

## NEW ANGLES
- **`anonca` / `none` attestation types**: MDS now supports non-chain attestation types; grep the current blob for accepted-family entries whose `attestationTypes` include `anonca` or `none` — a hardware-classified entry that legitimately requires no chain would delete the chain half of the classifier outright.
- **Credential-manager listings**: the 2026-09-29 MDS change lets password managers register statements, and `passkey-authenticator-aaguids` is being migrated in — monitor for a software provider whose MDS entry claims `keyProtection: secure_element` (phone-SEP-backed) and later appears on OpenAI's accepted list.
- **The only mutable layer is OpenAI's own**: MDS is additive and cannot be un-published, so staleness can only ever *refuse* newer material, never grant the flag. Schedule a weekly panel probe (bundle AAGUID, EA-profile AAGUID, `b7d3f68e`, `f4ce5fc0` as control) with blob serial logging so OpenAI-side list churn (the TrustKey Sep 24→Oct 1 move) becomes visible within one week instead of by accident.
- **Anchor-class map**: run experiment 2(d) across Feitian / HID / G+D / Infineon / NXP / Token2 anchors added in 2025–2026 — if any of them admits a non-bundle AAGUID, the anchor pool refresh is vendor-generic and the "accepted hardware list" is narrower than the pool, which separates admission from classification definitively.
- **`attca` + enterprise-profile entries**: test `41e39911` / `ab7d1767` with a statement carrying a serial-style extension under `attestationTypes: attca` — if EA-typed entries behave differently from consumer ones for the same model, the classifier is keyed on the MDS attestation type rather than the key itself.
- **Microsoft's monthly MDS snapshot list** as a differential oracle: their "supported hardware vendor" set is versioned monthly — diff it against whatever set OpenAI's admissions imply, to see whether OpenAI's hardware list is a copy of a published one we can read.
