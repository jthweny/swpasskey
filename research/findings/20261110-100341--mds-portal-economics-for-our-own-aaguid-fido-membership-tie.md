## FOUND
- MDS Portal registration is plain self-registration: corporate email + Company Info, first user of the vendor domain becomes Vendor Admin; no FIDO membership ID or certification number is demanded at registration — https://fidoalliance.org/mds-portal-user-guide-for-vendor-admins
- Publication flow is: add statement → request publication → **MDS Admin final approval** → Published → added to MDS3 BLOB; certification validation is a *separate, later* step ("Once your statements are added and published, you can request certification validation. An MDS Admin will check to verify certification, add the level..."), i.e. **an entry can live in the BLOB uncertified** — https://fidoalliance.org/mds-portal-user-guide-for-vendor-users
- Published statements are irreversible (cannot be edited/deleted except statement-detail updates), and "Each authenticator must have a unique attestation root certificate" — the root is vendor-supplied and only has to be unique per authenticator, not vendor-signed by anyone — https://fidoalliance.org/mds-portal-user-guide-for-vendor-users
- MDS spec defines `NOT_FIDO_CERTIFIED` and `SELF_ASSERTION_SUBMITTED` ("vendor has completed and submitted the self-certification checklist... if publicly available, the URL in `StatusReport.url`"); FIDO's own metadata-requirements doc says "Default status to 'not FIDO Certified'" and "Submission of Metadata to MDS is optional" — https://fidoalliance.org/specs/fido-v2.0-rd-20170927/fido-metadata-service-v2.0-rd-20170927.pdf , https://fidoalliance.org/specs/fido-security-requirements-v1.2-2018/fido-authenticator-metadata-requirements-v1.0-wd-20180629.html
- **What a software authenticator may claim: exactly `["software"]`** (MUST be set for software key management; exclusive in metadata with `hardware`/`tee`/`secure_element`; `remote_handle` may only be *added* to another flag, for server-held key handles) — https://fidoalliance.org/specs/common-specs/fido-registry-v2.2-rd-20210525.html
- The metadata-statement spec makes that semantic binding explicit: "The keyProtection specified here denotes the **effective security** of the attestation key and UAuth private key... key extraction... only possible if the specified protection method is compromised" — an exportable software-held key must be claimed `software` regardless of intent — https://fidoalliance.org/specs/mds/fido-metadata-statement-v3.1-ps-20250521.html
- Certification ceiling for pure software: L1/L1+ "allow the Authenticator Application to run in any operating environment" (L1+ = white-box crypto), but **L2 through L3+ require an Allowed Restricted Operating Environment** — so a legitimate `hardware`/`secure_element` claim is reachable only if the keys physically live in an SE/TEE-class ROE (this is exactly how the phone-app IDmelon entry claims `hardware`+`secure_element`) — https://fidoalliance.org/specs/fido-security-requirements/fido-authenticator-security-requirements-v1.5-fd-20211102.html
- L1 security evaluation is document-only (Vendor Questionnaire reviewed by the FIDO Security Secretariat, no lab); L2+ requires a FIDO Accredited Security Laboratory, and L2 is described as a fast-track design review keyed to an already-approved ROE — https://fidoalliance.org/certification/authenticator-certification-levels , https://www.redalertlabs.com/blog/top-10-things-you-should-know-about-the-fido-authenticator-certification-program
- Prices (Authenticator track): Functional $6,000 member / $9,000 non-member; **L1 included free**; L1+/L2+ security cert $9,000 / $13,500; Derivative $1,000 / $1,500; Delta $1,200 / $1,800 — https://fidoalliance.org/fido-certification-fees
- Membership dues (Jan 2026): Associate **$3,250** (≤100 employees) or $18,000 (101+); Government $18,000; Sponsor $30,250; Board $60,500 — https://fidoalliance.org/members/become-a-member
- Priced paths (arithmetic on the two fee tables above): **Path A — uncertified/self-assertion MDS entry: $0 in published fees** (no MDS submission fee exists in any fee table; registration is free) — https://fidoalliance.org/metadata-submission-terms-for-authenticator-vendors-2 , https://fidoalliance.org/fido-certification-fees | **Path B — L1-certified entry: $9,250 first year as Associate ($3,250+$6,000+L1 free) vs $9,000 as non-member ($9,000 functional, L1 free)** — membership is *not* economic for one model and only pays off from the 2nd model via $1,000 derivatives vs $1,500 | **Path C — L2 (minimum level that legitimately backs `hardware` claims): $18,250 published fees ($3,250+$6,000+$9,000) + accredited-lab evaluation, which is quote-only** (Applus+, Brightsight, atsec, UL, TTA, DPLS, Beijing Unionpay Card Tech publish no rates) — https://fidoalliance.org/fido-certification-fees , https://www.appluslaboratories.com/global/en/what-we-do/service-sheet/fido-security-evaluations , https://www.atsec.com/wp-content/uploads/2024/04/11-atsec-FIDO-services-en.pdf | **Path D — become the lab ourselves: accreditation $11,500 initial + $3,800/yr (member rates)**, but the accreditation policy bars evaluating one's own designs ("must not evaluate an implementation that the Laboratory has been involved in designing") and vendor-owned labs need "prior agreement from FIDO" — https://fidoalliance.org/fees-for-fido-accredited-labs , https://fidoalliance.org/specs/biometric/Biometric-Lab-Accreditation-Policy-v1.0-wd-20180830.pdf
- Timeline costs: functional cert is gated on Conformance Self-Validation (official FIDO test tool, self-run) then an **Interop Testing Event — remote, quarterly-ish windows with hard registration cutoffs and an NDA — or On Demand Testing within 90 days** of passing self-validation — https://fidoalliance.org/wp-content/uploads/Functional_Certification_Program_Policy_v1.3.4_20180306_FINAL.pdf , https://fidoalliance.org/event/fido-user-authentication-interop-testing-event-2 , https://idtechwire.com/fido-opens-june-interoperability-testing-window-for-certification-candidates
- Scarcity datapoint: as of Jan 2025 MDS held ~148 FIDO-certified FIDO2 authenticators and only 8 companies held L2 — https://www.token2.com/site/page/blog?p=posts%2F87
- Software/SDK entries demonstrably survive MDS review: "Hideez Key 4 FIDO2 SDK" is an MDS model Microsoft Entra treats as attestation-eligible, and the "Hideez Key U2F SDK" entry is sloppy enough to carry a malformed cert — FIDO's admin review is a publication gate, not a claims audit — https://learn.microsoft.com/en-us/entra/identity/authentication/concept-fido2-hardware-vendor , https://github.com/tweag/webauthn/issues/68
- RP-side precedent for what an "MDS entry" buys: Microsoft's hardware-vendor eligibility is literally "chains back to the attestation roots extracted from the FIDO Alliance MDS" against a versioned MDS snapshot (v285) — https://learn.microsoft.com/en-us/entra/identity/authentication/concept-fido2-hardware-vendor ; current BLOB scale ~501 entries / 333 with AAGUID (no. 270) — https://github.com/sebadob/rauthy/issues/1618
