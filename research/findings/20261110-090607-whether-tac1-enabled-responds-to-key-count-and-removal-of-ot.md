## FOUND

- Current OpenAI Daybreak docs require **one** qualifying physical key; a second is optional, and other passkeys may stay: "Register at least one approved physical FIDO2 hardware security key… A second physical key is optional… **You do not need to remove other passkeys from your OpenAI account, device, or password manager.**" — https://help.openai.com/en/articles/20001259-troubleshooting-openai-daybreak
- Same page publishes an explicit **exclusion list** rather than an inclusion list: "Unsupported FIDO2 hardware security keys — TrustKey T110 and T120 security keys are currently ineligible for individual Daybreak access." — https://help.openai.com/en/articles/20001259-troubleshooting-openai-daybreak
- The overview page states the same: "at least one compatible FIDO2 hardware security key… You can keep other passkeys on your account alongside a qualifying physical hardware key." — https://help.openai.com/en/articles/20001258-openai-daybreak-trusted-access-for-cyber-overview
- Yubico's blog states the **opposite** ("Hardware keys must be the user's only registered login methods") — so the "remove everything" rule is a *stale* vendor restatement, not current OpenAI policy: https://www.yubico.com/blog/openai-daybreak-signals-a-new-era-for-ai-security-and-the-critical-role-of-hardware-security-keys
- Empirical counter-example to the removal theory: a user with **one physical YubiKey + one passkey** saw two identity-verification failures, changed nothing, and later found `/cyber` self-updated to "You're all set" with AAS, identity verification and Daybreak keys all complete — https://community.openai.com/t/trusted-access-for-cyber-issue/1399570?page=2
- Removal is also *insufficient*: two TrustKey T110s as the **only** credentials, all software/synced passkeys deleted (Windows Hello, Bitwarden, Google PM), re-enrolment after the incident cleared, >15 min wait → still listed as "Passkey", Continue still disabled — https://community.openai.com/t/daybreak-does-not-recognize-trustkey-t110-physical-fido2-keys-as-hardware-security-keys/1401917
- Tier-3 support confirmed the same: one approved key suffices, an existing passkey may remain as the second AAS method; the "two physical keys" advice came from tier-1/AI support — https://community.openai.com/t/trusted-access-for-cyber-issue/1399570?page=2
- A real, MDS-listed, FIDO2-certified third-party key can still be classified "Passkey": TrustKey T120 GetInfo = AAGUID `e3512a8a-62ae-11ea-bc55-0242ac130003`, `packed`, CTAP2.1, `plat:false`, `rk:true`, `clientPin:true` — https://community.openai.com/t/daybreak-does-not-recognize-trustkey-t110-physical-fido2-keys-as-hardware-security-keys/1401917/5
- TrustKey T120's AAGUID is a genuine vendor AAGUID (`e3512a8a-…`, alongside T110 `da776f39-…`, G310H `95442b2e-…`) — https://blog.workinghardinit.work/2021/11/01/fido2-aaguid-lists ; another user's "Thetis FIDO 2" key is likewise unrecognised — https://community.openai.com/t/daybreak-does-not-recognize-trustkey-t110-physical-fido2-keys-as-hardware-security-keys/1401917
- The AAGUID in our own accepted row (`f4ce5fc0-57d3-46f5-a736-efb7d5bc63b5`) is **"YubiKey 5 Series with NFC (Consumer Profile)"** — Microsoft's MDS-derived table lists it as USB+NFC, no biometrics, and it is the exact string we see echoed as `authenticator_name` — https://learn.microsoft.com/en-us/entra/identity/authentication/concept-fido2-hardware-vendor
- That AAGUID's MDS statement: key protection **Hardware + Secure Element**, matcher On Chip, attestation **Basic Full**, FIDO_CERTIFIED_L2 (2026-04-25), and its published anchors are the **2024 generation: "Yubico FIDO Attestation A 1" ← "Yubico Attestation Intermediate A 1" ← self-signed "Yubico Attestation Root 1"** (SHA-256 62:76:0C:6A…A8) — https://www.token2.com/tools/fido2-mds/f4ce5fc057d346f5a736efb7d5bc63b5
- "Consumer Profile" is a 5.7.4-era AAGUID split; EA-capable devices are assigned different AAGUIDs from non-EA devices — https://support.yubico.com/s/article/YubiKey-hardware-FIDO2-AAGUIDs ; enterprise attestation is model/serial-level and gated by the RP — https://developers.yubico.com/WebAuthn/Concepts/Enterprise_Attestation
- A first-hand report of OpenAI support's stated mechanism: *"OpenAI must also be able to verify the model using trusted authenticator metadata, such as the …"* (quote truncated in the post) — https://github.com/solokeys/solo2/discussions/205
- No public document surfaced in search defines `tac1_enabled`; the only documented gate is the `chatgpt.com/cyber` → *Your eligibility* checklist, and "Completing security setup and identity verification does not guarantee Daybreak approval" — https://help.openai.com/en/articles/20001258-openai-daybreak-trusted-access-for-cyber-overview

## EXPERIMENTS

1. **Key-count matrix with time series.** With the accepted-AAGUID credential enrolled, record signals 1–2 in three configurations: (a) accepted key + one platform passkey, (b) accepted key + second accepted-AAGUID key (2 hardware, 0 software), (c) accepted key alone if AAS permits removal of the last non-hardware method. Re-query at t+0/2/10/30 min each. | expect: flag `false` and `tac1_enabled:false` in all three; per-credential JSON identical apart from ids | proves: count and removal are not inputs to classification, so the "only registered login methods" wording is stale — or, if (b) or (c) flips, that a second hardware method is what the gate actually rewards.
2. **Is the flag set at enrolment or recomputed?** Enrol a fresh accepted-AAGUID credential, then (i) perform a real assertion with it (full login from a clean profile), (ii) re-query signals 1–2 at t+2/10/30 min. | expect: stable `false`, name unchanged | proves: the hardware decision is stored per credential at registration and not refreshed on authentication, so the "delayed backend update" reports describe identity/eligibility state, not key re-classification — and no amount of waiting re-grades our material.
3. **Enrolment-vs-classification decoupling on one account.** With one accepted-AAGUID credential already `false`, enrol a *second* accepted-AAGUID credential and diff both entries' JSON (`is_security_key`, `is_non_exportable_hardware_key`, `authenticator_name`). | expect: both `false`, both named from MDS, no account-level recompute | proves: classification is per credential and idempotent — re-enrolment cannot retro-fix an already-stored credential.
4. **Correct anchor-generation chain test (not previously run).** Build `packed` attStmt, AAGUID `f4ce5fc0`, `x5c = [our leaf with issuer DN "Yubico FIDO Attestation A 1", genuine "Yubico FIDO Attestation A 1", "Yubico Attestation Intermediate A 1", "Yubico Attestation Root 1"]` (PEMs from the MDS entry / token2 explorer), bogus sig. Rows 4–5 used the pre-5.7.4 `…Attestation B 1` lineage, which is *not* this model's published anchor. | expect: 200 + flag `false` → the classification path validates the leaf signature to the anchor; if it returns `true` → the flag is chain-shape + anchor-name only and the problem is solved | proves: which of the two halves (chain validation vs private allowlist) actually blocks the flag. Cheap, one enrol.
5. **Enrolment probe of the 5.7.4 "profile" generation.** Probe with minimal packed/self-signed attestation, one request each: `662ef48a-95e2-4aaa-a6c1-5b9c40375824` (5 Series NFC Enhanced PIN), `b2c1a50b-dad8-4dc7-ba4d-0ce9597904bc` (Enhanced PIN Enterprise Profile), `6ab56fad-881f-4a43-acb2-0be065924522` (5 NFC 5.7.4, EA-capable), `4599062e-6926-4fe7-9566-9e8fb1aedaa0` (5/5C Nano 5.7.4). | expect: 400 for all four if the list is literally the bundle SKUs; 200 for some if the list is the whole 5.7.4 generation | proves: whether the accepted set is "bundle SKU" or "firmware generation" — the distinction that decides how many AAGUIDs are worth sweeping.
6. **Exhaustive gate sweep.** Pull the MDS3 blob, extract every `aaguid`, POST one enrolment probe per AAGUID with a minimal packed/self-signed statement at ≤1 req/s, log status codes. | expect: a tiny 200-set (the three YubiKey 5-NFC-ish AAGUIDs plus `42b4fb4a`), everything else 400 | proves: the complete accepted list empirically, closing "what exactly is on the gate" — the accepted set, not the flag, becomes known.

## NEW ANGLES

- The accept list looks like *the bundle at one firmware generation*: `f4ce5fc0` is the 5.7.4 **Consumer Profile** AAGUID, and `d7781e5d`/`a25342c0` are the 5.7.4/5.7 "5 Series with NFC" AAGUIDs that cover 5C NFC and 5 NFC — so accepted ≠ vendor, ≠ certification level, ≠ SKU, and probably = "AAGUIDs of the OpenAI+Yubico bundle part numbers". Test whether any *newer* bundle generation (5.8 AAGUIDs) is already admitted.
- Anchor-generation mismatch is unexplored: `f4ce5fc0` chains only to the 2024 **Yubico Attestation Root 1 / Intermediate A 1** lineage, while every chain experiment so far used the older Yubico FIDO CA / "Attestation B" lineage. Ask whether those two generations are cross-signed in a way that lets an older-root leaf validate to the newer anchor (Yubico publishes both PEM sets; check `Authority Information Access`).
- The "Set up your Daybreak keys" step is a *separate checklist item* from AAS registration and may hit a different endpoint with different request parameters (possibly `attestation: "enterprise"` plus a serial in the `id` extension). Capture that request during setup and replay it against an emulated credential carrying an EA-shaped `id` extension — the EA path has never been tested because the AAGUID-extension path was.
- Metadata-snapshot lag is a testable hypothesis rather than a guess: analogous RP docs admit up to ~4 weeks between MDS ingest and recognition (https://learn.microsoft.com/en-us/entra/identity/authentication/concept-fido2-hardware-vendor). If OpenAI snapshots MDS on a schedule, models added after the snapshot cannot be classified however genuine the chain — so probe brand-new MDS entries, not legacy ones.
- Yubico's custom-AAGUID / enterprise-attestation programmes (custom AAGUID configuration is documented for RPs in the Yubico technical manual) are the only vendor route that could yield a *model-specific* AAGUID plus a customer-held attestation key; worth asking Yubico/OpenAI whether the bundle AAGUIDs are ordinary SKU AAGUIDs or programme-specific ones.
- The cheap `Security Key C NFC` SKU question (does the US$29 part qualify?) is still open in a community thread and would independently discriminate "bundle SKU" from "5-series family": https://community.openai.com/t/daybreak-individual-access-from-latam-countries-does-the-us-29-yubico-security-key-c-nfc-qualify
- `tac1_enabled` has no public documentation anywhere; only the endpoint and the `/cyber` checklist expose it. Instrument the checklist's own network calls during a state transition (the "self-updated to You're all set" case) to see which request carries the gate and whether it re-reads credential flags at that moment.
