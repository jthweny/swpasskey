- Daybreak eligibility is documented as a **conjunction** — plan, AAS, hardware key, identity check — with a `403 cyber_verification_precheck_failed` raised *before* the Persona step — https://help.openai.com/en/articles/20001258-openai-daybreak-trusted-access-for-cyber-overview
- **[derived]** Since the precheck failure is a distinct, client-observable 403 that fires *before* Persona, the server evaluates the conjuncts separately and returns at least one machine-readable reason. That makes the conjunction enumerable by probing rather than by inference — the single cheapest way to answer this iteration's angle.
- AAS enrolment reports "Completed" on the strength of a credential whose signal-1 flag is **false** — https://help.openai.com/en/articles/20001259-troubleshooting-openai-daybreak (troubleshooting/"approved keys" language; the *measured* Completed-with-false-flag state is from the brief's own probe log)
- **[derived]** Therefore AAS completion and the hardware flag are produced by **different predicates** in different code paths. If Daybreak reads AAS completion (as the docs' conjunction implies) it never reads `is_non_exportable_hardware_key` at all, and signal 1 may be a *UI-only* gate for the "Add a hardware security key" page — this reframes the whole target and is directly testable (Experiment 4).
- Verdicts update **days later** with no user action, attributed to delayed/backend state rather than rejection — https://community.openai.com/t/trusted-access-for-cyber-issue/1399570?page=2
- The accepted set changed within a week (TrustKey T110/T120 compatible 24 Sep, ineligible 1 Oct) — https://community.openai.com/t/daybreak-does-not-recognize-trustkey-t110-physical-fido2-keys-as-hardware-security-keys/1401917
- A major RP runs a **monthly-versioned MDS snapshot** rather than the live blob, which is the published precedent for the snapshot-staleness hypothesis — https://learn.microsoft.com/en-us/entra/identity/authentication/concept-fido2-hardware-vendor
- MDS entries carry `statusReports` (`status`, `effectiveDate`) and a top-level `status`/`timeOfLastStatusChange`, i.e. per-AAGUID state that **legitimately changes over time** — the structure that makes a snapshot-vs-live divergence observable — https://fidoalliance.org/specs/mds/fido-metadata-statement-v3.1-ps-20250521.html

## EXPERIMENTS
1. **Read the oracle's full shape instead of one boolean.** `curl -s 'https://chatgpt.com/api/auth/session' -b <cookies>` → take `.accessToken`; then `curl -s 'https://chatgpt.com/backend-api/cyber_verification/status' -H "authorization: Bearer $T"` and the same for `/refresh_status`; dump with `jq 'paths(scalars) as $p | [$p|join("."), getpath($p)]'`. | expect: 200 and a JSON body containing more than `tac1_enabled` — most likely an `eligible`/`checks`/`precheck` object or a `qualifying_count` alongside per-conjunct booleans. | proves: whether signal 2 is a scalar aggregate or an exposed conjunction. If the conjuncts are named in the body, this iteration's question is answered outright and no enrolment is needed.
2. **Enumerate the conjuncts by differential 403.** With the same bearer, POST empty and near-empty bodies to `/backend-api/cyber_verification/precheck` and any sibling path surfaced by Experiment 1, plus `GET .../refresh_status` with and without `Authorization`. Record status code *and* body keys for each. | expect: at least one response distinguishes "no hardware key" from "identity not verified" via a reason string or differing body keys. | proves: whether identity/Persona is a *parallel* conjunct (so a true credential flag alone can never flip `tac1`) or a *downstream* one (so signal 1 is the binding constraint). This is the cheapest possible kill-or-confirm of the whole hardware hunt for signal 2.
3. **Triangular key-count test.** Three states, each polled at t+2/10/30 min: (a) one credential, AAGUID `f4ce5fc0`; (b) a *second* credential, same AAGUID, fresh key pair and credential ID; (c) delete both, enrol `f4ce5fc0` + `42b4fb4a` so two *distinct vendors* are present. Log `qualifying_count` and `tac1_enabled` in each state. | expect: `qualifying_count` identical (0) in all three, `tac1_enabled` unchanged — i.e. neither count nor vendor-diversity is an input. **Discriminating alternative:** if `qualifying_count` rises with n while `tac1_enabled` stays false, the count is *admitted-credential* count, not hardware-flag count, and enrolling many accepted-model credentials becomes a live lever. | proves: whether signal 2 is credential-gated (aggregating signal 1) or account-gated on a separate quantity — and if the latter, whether that quantity is reachable with credentials we can mint today.
4. **Capture the UI predicate.** On the "Add a hardware security key" page, monkeypatch before navigation (Selenium `add_init_script` or a devtools snippet): wrap `window.fetch` and `XMLHttpRequest.prototype.open/send` to push `{url, status, body}` into `window.__log`, then reload, wait for the disabled Continue button, and dump `__log` plus `performance.getEntriesByType('resource').map(e=>e.name)`. Then diff which response field changes when a credential of an accepted model is added/removed. | expect: one endpoint whose body carries a boolean adjacent to the "hardware" naming that exactly tracks the button's disabled state. | proves: whether **Continue** reads the per-credential flag or a different account-level boolean. If it reads a different field, flipping `is_non_exportable_hardware_key` was never the requirement for signal 3, and the 26 failure rows were aimed at the wrong variable.
5. **Retrospective staleness sweep over rows 1–29.** With the credentials from all prior enrolments still on the account, re-pull `GET /api/accounts/advanced-account-security/passkeys` and `POST /backend-api/cyber_verification/status` now, and again at t+24 h; diff against the archived values from each row. | expect: all `false`, unchanged — unless any older entry has flipped, which would prove evaluation is periodic. | proves: whether classification is evaluated once at enrolment or re-evaluated server-side over time. If any row has flipped since recording, the t+30 protocol is too short and up to 26 of the failure rows are provisional rather than closed.
6. **Plan/entitlement control.** From an account with **zero** passkeys (and, if available, a different plan tier), run Experiments 1–2. | expect: `tac1_enabled: false` with either an explicit missing-conjunct reason or the same generic 403. | proves: whether signal 2 is even *measurable* on our test account — if `tac1` is plan-gated upstream, then every `tac1: false` recorded so far is uninformative about credentials and must be discarded as evidence, which changes the reading of the whole ledger.
7. **`refresh_status` write-vs-read test.** Call `refresh_status` 1× vs 10× spaced 30 s apart, capturing the `passkeys` payload's any timestamp/`last_updated`-shaped fields before and after. | expect: either byte-identical responses (pure read) or a changed timestamp/`qualifying_count` after N calls (a write that triggers re-evaluation). | proves: whether the reported "flips days later" is caused by a client-side refresh trigger — if so, an active trigger loop replaces passive waiting, which changes the failure protocol itself.

## NEW ANGLES
- **Entitlement confound first, credentials second.** Before any further forgery work, establish that the test account is Daybreak-*eligible* in principle; if `tac1` is gated on plan entitlement upstream, the signal-2 ledger collected so far measures the wrong account state and should be re-baselined. Run Experiment 6 before Experiment 3.
- **Two-predicate split.** AAS completion ignores the hardware flag while Daybreak's docs describe AAS as one conjunct — so the "hardware key" requirement may live entirely in the *UI* page, with the backend gate reading (AAS ∧ identity). Test which endpoint the Daybreak gate calls; if it calls AAS status only, the correct target is whatever flips AAS's own internal hardware sub-state, not this flag.
- **`qualifying_count` as the real name of the game.** If it counts *admitted* credentials rather than flagged ones, the cheapest untried lever is multiplication: N credentials from accepted models (bundle-list models enrol on sight, so N is free) rather than one perfect credential.
- **Historical MDS blob diffing** (carried from the brief, now with a concrete method): many third-party repos vendor `blob.jwt` files under version control; diff two snapshots to find AAGUIDs whose `status`/`statusReports` changed (deprecated ⇄ active, certification withdrawn). Then test the *old* state's AAGUID: admission tracking a stale state would be direct proof of which snapshot OpenAI serves, and would identify any AAGUID that was refused-then-admitted (or the reverse) inside their window.
- **Community JSON harvest for signal 1 = true.** Search GitHub issues, HAR pastes and support threads for the literal string `is_non_exportable_hardware_key` — a single posted response body with a `true` names both the model and the exact attestation that produced it. External search was unavailable this iteration; queue it for the next one with a broader tool.
- **`extensions` / `credProtect` and `hmac-secret` flags.** These ride in `authData` unauthenticated by any check we know of, and no row has varied them; if the classifier consumes the authenticator's asserted `options`/`extensions` rather than only the attestation, the space of untried inputs is larger than "certificate shape" implies.
