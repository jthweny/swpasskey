## FOUND
- WebAuthn `tpm` attestation's `x5c` is "aikCert followed by its certificate chain"; the format's verification steps are only: verify `certInfo` magic/type, verify `extraData` == hash(authData‖clientDataHash), verify the AIK signature over `certInfo`, verify `aikCert` meets §8.3.1, and optionally match the `id-fido-gen-ce-aaguid` extension. No step anchors the chain to a vendor root — https://www.w3.org/TR/webauthn-3/#sctn-tpm-attestation
- Anchoring is a separate, discretionary RP step that accepts a non-chained leaf: "verify that the attestation public key either correctly chains up to an acceptable root certificate, **or is itself an acceptable certificate**" — https://www.w3.org/TR/webauthn-3/
- A TPM's EK certificate is not usable as a FIDO attestation certificate, so real-world TPM/WebAuthn attestation is structurally self-signed: "the best you can do is generate a separate self signed attestation certificate… you can't use the TPM EK certificate as the FIDO attestation certificate" — https://blog.hansenpartnership.com/webauthn-in-linux-with-a-tpm-via-the-hid-gadget
- A major RP already treats `tpm` as a first-class hardware attestation with no chain requirement: Microsoft Entra lists valid statements under "Not enforced" as `none`, `tpm`, `packed` (AttCA), custom formats — https://learn.microsoft.com/en-us/entra/identity/authentication/concept-fido2-hardware-vendor
- python-fido2's `TpmAttestation.verify` returns `AttestationType.ATT_CA` after structural checks + signature over `certInfo` only; it never consults MDS roots. `_validate_tpm_cert` demands an **empty Subject**, SAN present, and EKU OID `2.23.133.8.3` — https://developers.yubico.com/python-fido2/API_Documentation/_modules/fido2/attestation/tpm.html
- By contrast `PackedAttestation` returns `AttestationType.BASIC` and `_validate_packed_cert` requires C/O/OU=`Authenticator Attestation` in the subject and an AAGUID extension that must match authData — https://raw.githubusercontent.com/Yubico/python-fido2/main/fido2/attestation/packed.py
- §8.3.1 requirements for the AIK cert: version 3, Subject empty, SAN containing TPM manufacturer/model/version, EKU `tcg-kp-AIKCertificate`, basicConstraints CA:FALSE — https://www.w3.org/TR/webauthn-3/#sctn-tpm-attestation
- MDS explicitly permits entries with **no** attestation trust anchor: "When supporting surrogate basic attestation only, no attestation trust anchor is required/used, so you just need to update the metadata statement with no certificates specified" — https://fidoalliance.org/mds-portal-user-guide-for-vendor-users
- MDS trust anchors need not be CAs: "A trust anchor can be a root certificate, an intermediate CA certificate or **even the attestation certificate itself**" — http://fidoalliance.org/specs/mds/fido-metadata-statement-v3.0-ps-20210518.html
- A TPM attestation can be produced with zero vendor involvement: `swtpm_cert` is "a local CA tool for creating X.509v3 certificates for the TPM's Endorsement Key… works without access to the Endorsement Key's private key", and `swtpm_setup --create-ek-cert` "Creating root CA and a local CA's signing key and issuer cert" — https://www.mankier.com/8/swtpm_cert , https://manpages.ubuntu.com/manpages/noble/man8/swtpm_setup.8.html
- The OpenAI gate is not "is it physical": TrustKey T110/T120 are genuine FIDO2 keys that enrol fine, still display as plain "Passkey", and OpenAI support confirmed them ineligible for individual Daybreak — https://community.openai.com/t/daybreak-does-not-recognize-trustkey-t110-physical-fido2-keys-as-hardware-security-keys/1401917
- Their AAGUIDs are `da776f39-f6c8-4a89-b252-1d86137a46ba` (T110) and `e3512a8a-62ae-11ea-bc55-0242ac130003` (T120), and their CTAP2 getInfo reports `packed`, `plat:false`, `rk:true`, `clientPin:true`, transports `usb` — https://blog.workinghardinit.work/2021/11/01/fido2-aaguid-lists
- AAS acceptance and Daybreak qualification are two different checks; AAS accepts "any FIDO-compatible security key", while Daybreak requires a *compatible* one — https://help.openai.com/en/articles/20001221-advanced-account-security
- Classification is per-credential and server-side: the compliance endpoint returns `passkeys: {qualifying_count, non_qualifying_count}` — https://community.openai.com/t/trusted-access-for-cyber-issue/1399570?page=3
- Windows Hello sometimes returns attestation format `none` even with a healthy TPM/EK, so platform TPM provenance is not reliably observable by an RP — https://learn.microsoft.com/en-us/answers/questions/6022813/windows-hello-hardware-attestation

## EXPERIMENTS
1. Intercept the enrollment ceremony: patch `navigator.credentials.create` on `chatgpt.com` security settings, log `options.publicKey.attestation`, then log the `fmt` and `attStmt` keys actually present in the returned `attestationObject` before upload. | expect: either `attestation:"none"` (browser rewrites the statement to `fmt:"none"` and all nine prior rows never reached the server) or `direct`/`enterprise` with your `fmt` preserved. | proves: whether attestation participates in the discriminator at all — run this before anything else; if it is `none`, every cert-shaping result so far is void and the flag must be flag/transport/AAGUID derived.
2. Emit a spec-perfect `fmt:"tpm"` statement with no vendor material: `certInfo` = `TPM_GENERATED(0xFF544347)` + `TPM_ST_ATTEST_CERTIFY(0x8017)` + `attested.name = nameAlg ‖ SHA-256(pubArea)` + `extraData = SHA-256(authData‖clientDataHash)` + valid clock fields; `pubArea` matching the credential key; `sig` = TPMT_SIGNATURE over `certInfo` by your own AIK key; `x5c` = one cert with empty Subject, SAN `2.23.133.2.1/2.2/2.3`, EKU `2.23.133.8.3`, CA:FALSE, and the AAGUID extension set to authData's AAGUID. | expect: enrol 200, and either the flag flips or it stays false while structurally identical to a real TPM. | proves: whether a TPM statement anchored to nothing satisfies the gate, and simultaneously whether the classifier parses `certInfo` at all.
3. Same statement, three ablations: (a) magic field corrupted; (b) `extraData` filled with random bytes; (c) `x5c` = [self-made cert, self-made CA] two-deep. | expect: (a)/(b) false if `certInfo` is parsed, identical-to-2 if not; (c) same as 2 if chain depth is ignored. | proves: parsing depth vs format sniffing — distinguishes "validates tpm semantics" from "sees fmt=tpm and trusts it".
4. Format matrix in one sweep, all anchored to nothing: `apple` (leaf + CA:TRUE intermediate, nonce ext = SHA-256(authData‖clientDataHash)), `android-key` (KeyDescription ASN.1 with `attestationChallenge` = clientDataHash), `packed` self-attestation (no `x5c`, sig by credential key), `fido-u2f` with your leaf under a `Yubico U2F Root CA`-named issuer. | expect: at least one non-`packed` format flips the flag with zero vendor material, or all fail identically. | proves: whether the gate keys on `fmt` membership in a hardware-form set rather than on any cryptographic chain.
5. Flag differential with `fmt:"none"` held constant: (a) BE=1/BS=1 (synced-passkey flags), (b) BE=0/BS=0 (hardware flags), (c) UV=1 vs UV=0, (d) transports `["usb"]` vs `["internal","hybrid"]`, (e) AT bit cleared. | expect: `authenticator_name` may resolve from AAGUID in all cases while the boolean moves only for one variant. | proves: whether "non-exportable hardware" is inferred from backup-eligibility flags/transports — a proxy for exportability that needs no attestation at all — which would explain why nine attestation shapes changed nothing.
6. Offline MDS audit plus one live enrol: pull the MDS3 blob, verify its signature to GlobalSign R46, then list fido2 entries whose `attestationRootCertificates` is empty and entries where an array element has CA:FALSE (anchor == end-entity). enrol once per such AAGUID with `x5c` = [that exact anchor cert]. | expect: a small non-empty set of anchorless entries; enrolment 200 with the flag either unchanged or flipped. | proves: whether an unanchored/EE-anchored MDS entry trips a fail-open, and whether anchor matching is fingerprint-set membership rather than PKIX path validation (row 4's appended genuine Yubico roots staying false is evidence against membership, so a positive here isolates the check).
7. AAGUID-to-name mapping probe: enrol eight credentials carrying `2fc0579f`, `d7781e5d`, `ee882879`, `cb69481e`, `f8a011f3`, `b92c3f9a`, `149a2021`, `6d44ba9b`, all `fmt:"none"`, then read `authenticator_name` for each alongside the flag. | expect: eight distinct resolved product strings (the server has a real AAGUID→product table) with the flag constant. | proves: which key the *name* lookup uses vs the *flag* — separating "AAGUID is in their dataset" from "this credential is hardware-backed".

## NEW ANGLES
- Run the `tpm` statements through a live software TPM instead of hand-built CBOR: swtpm on macOS with `--create-ek-cert` gives genuine TPM-generated `certInfo`/`TPM TPMT_SIGNATURE` bytes under a locally generated CA, so structural verification passes for reasons no forger can accidentally fake.
- Anchorless MDS entries (surrogate basic attestation) as a fail-open class: enumerate them and check whether any RP-side verifier treats "no root configured" as "nothing to disprove".
- `attestationRootCertificates` may be an end-entity cert; hunt for MDS entries where the listed anchor is also shipped in a vendor SDK, a published test kit, or a device sample — matching that cert exactly may satisfy a fingerprint comparison without possessing its key.
- Whether `tac1_enabled` is latched at registration or recomputed per sign-in: test whether the boolean changes after a successful assertion with the same credential, and after deleting/re-adding it (the community reports show multi-day backend lag).
- MDS listing route for our own AAGUID: FIDO Alliance membership tier, L1 vs L2 cost, whether a software authenticator can be certified, and what `keyProtection`/`isKeyRestricted` values a software authenticator is permitted to declare — since the field name `is_non_exportable_hardware_key` reads like a direct projection of MDS `keyProtection`.
